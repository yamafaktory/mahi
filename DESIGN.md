# mahi — design

> *mahi* (te reo Māori): work.

mahi is a single Rust binary that lets multiple engineers collaborate in real time with **any** terminal coding agent (Claude Code, Codex, Gemini CLI, …), peer-to-peer, with the full history of the work stored encrypted in the project's own git remote.

## Thesis

Review shouldn't be a gate at the end. When teammates watch, steer and prompt each other's agents while the work happens, design problems are caught at turn 3 instead of in a finished PR. By the time a branch lands, the discussion has already happened; the PR on GitHub/GitLab becomes a quick skim of changes people already saw being made.

## Principles

- **Agent-agnostic.** Wrap the agent's own terminal UI; never require a specific agent or editor.
- **Peer-to-peer.** No mahi server. Realtime traffic goes directly between peers.
- **Git-native.** All durable state lives in git refs on the project's existing remote. The result of a thread is one ordinary remote branch.
- **Private by default.** Rich history (transcripts, agent state) is end-to-end encrypted before it becomes a git object.
- **Sandboxed.** Every agent runs inside an OS-level sandbox, so teammates can prompt each other's agents safely.
- **Fuzzed.** Everything that reads untrusted input is fuzzed as well as unit-tested (see Testing).
- **Use the forge for what it's good at.** Final diff viewing and approval happen in GitHub/GitLab. mahi does not rebuild review tooling.

## Non-goals (decided)

- Signed review attestations / `allowed_signers` trust roots: overhead with little value when repo access already defines the team. May return later as an optional compliance layer built on forge identities.
- Implicit review-coverage tracking: dropped; the forge's PR diff covers the final look.
- Multiple agents editing the same worktree simultaneously.

## Architecture

### Core (agent-independent)

- **PTY wrapper**: launches the agent in a pseudo-terminal, passes it through to the user's terminal, and maintains a virtual screen (`vt100`) for late joiners and crude text snapshots. The pseudo-terminal is opened with `rustix` and the agent is spawned by `mahi-sandbox` itself, not by `portable-pty`, because the sandbox must act between fork and exec on the same spawn. The agent starts with an empty environment plus what mahi passes on, in its own session and process group, and killing it kills the whole group.
- **Sandbox**: the whole agent process runs inside an OS sandbox: namespaces, Landlock and seccomp on Linux (and WSL2), Seatbelt through `sandbox_init` on macOS. Same pattern as Anthropic's sandbox-runtime (`srt`), implemented natively in Rust with no helper program such as `bwrap`. All `unsafe` code in mahi lives in this one crate. On Linux the agent starts in new user, mount, PID and network namespaces, mapped to the user's own effective uid and gid, with an empty read-only root: the host's programs and libraries (`/usr`, `/etc`, `/bin`, `/sbin`, `/lib*` and `/opt`, where distribution packages install programs, all read-only), and otherwise only the paths its policy binds (read-only, recursively, or read-write), a private `/tmp`, its own `/proc`, and a minimal `/dev` (null, zero, full, random, urandom, tty, `console` as its own terminal, `fd`, a private `devpts` and `/dev/shm`). Each bound path is opened with `openat2` and `RESOLVE_NO_SYMLINKS` after the namespaces exist, so a planted symbolic link cannot redirect a bind, and is cloned with `open_tree` and made read-only with `mount_setattr`, which also covers mounts below it. Mount points are created and reached component by component with `openat2`, so a symbolic link placed in a writable path cannot move a mount elsewhere. Before exec the child locks the securebits (`NOROOT`, `NO_SETUID_FIXUP`), empties the capability bounding and ambient sets, sets `no_new_privs` and marks every inherited descriptor close-on-exec, so the agent holds no capability even when mahi runs as root, and cannot reopen the host through a leaked descriptor. Two small processes watch the agent: one outside the PID namespace, which `mahi` waits on and which passes the agent's exit status up (a signal death arrives as exit code 128 plus the signal), and the namespace's init, which reaps orphans. Both are marked non-dumpable, since they are copies of mahi's memory, and init keeps its capabilities, so the agent can neither trace them nor read their `/proc` entries. The agent leads its own session with the terminal, so terminal keys and a hangup reach it alone, and `kill(0)` cannot reach its watchers. The outer watcher also sees the hangup: if the agent is still running three seconds later, it kills init, so a sandbox does not outlive mahi's terminal by more than that grace period. When the agent exits, init exits and the kernel ends everything left in the namespace, including processes that started their own session; init also dies with the outer watcher. Its network namespace has no route and only loopback up, which init brings up, so the agent reaches nothing outside (DNS fails at once with connection refused) and cannot see the host's sockets in `/proc/net`; outside access goes through mahi's network proxy, whose listening socket is created on this loopback and handed to mahi (see Network proxy). A Unix socket inside any bound path can be connected to, even through a read-only bind, so policies never bind a directory that holds agent sockets (`$XDG_RUNTIME_DIR`, `~/.gnupg`, `/run`): policy is the only guard for sockets at file paths, since neither Landlock nor seccomp can filter `connect` by path. Abstract sockets are already cut off by the network namespace. Init sets `user.max_user_namespaces` to 0 in the sandbox, so the agent cannot create nested user namespaces and gain capabilities over new network or mount namespaces, a common path to kernel exploits. As in OCI runtimes, `/proc/sys`, `/proc/sysrq-trigger`, `/proc/irq`, `/proc/bus`, `/proc/fs` and `/proc/dynamic_debug` are read-only and `kcore`, `keys`, `timer_list`, `vmallocinfo`, `slabinfo` and similar entries are masked, which matters when mahi runs as root. Because of the masks, the agent cannot mount a fresh `/proc` of its own, so nested sandboxes such as `bwrap` or `unshare --mount-proc` do not work inside mahi, and tools that sandbox themselves with a user namespace (Chromium, Electron, Playwright browsers) need their `--no-sandbox` option. `/proc/1/cmdline` shows mahi's arguments, which therefore never carry a secret. On top of the mounts, the agent restricts itself with Landlock before exec, through raw system calls since the rules are built between fork and exec: everything is readable and executable; only the read-write binds, `/tmp` and `/dev/shm` are writable, and no real device node can be created anywhere; files in `/proc` can be written where the kernel allows it (`/proc/sys` stays read-only), since browsers write `oom_score_adj`; and devices under `/dev` and its own terminal can be used, including their `ioctl`s. Rights come from the kernel's highest Landlock ABI, and on ABI 6 abstract Unix sockets and signals are scoped to the sandbox. The sandbox needs ABI 2 (Linux 5.19), because on ABI 1 Landlock forbids moving files between directories; a kernel without it refuses to start the sandbox, with an error that says why, rather than run it weaker. This is defence in depth: a mistake in the mount setup, or a writable mount the policy did not mean outside the read-write binds, still cannot be written through. A read-only bind nested in a read-write one is protected by its mount alone. Last before exec, the agent installs a seccomp filter, written as classic BPF by mahi and built before the fork: it kills the process on a foreign architecture, refuses x32 system calls, and returns `EPERM` for calls a coding agent never needs and that widen the kernel's attack surface (module loading, `kexec`, `bpf`, `perf_event_open`, `userfaultfd`, keyrings, every mount call, `setns`, `clone` and `unshare` with namespace flags, `modify_ldt`, clock and swap changes, `ioperm` and `iopl`, and the `TIOCSTI` and `TIOCLINUX` terminal injections). `io_uring` and `clone3` return `ENOSYS`, so runtimes fall back to plain system calls and to `clone`, whose flags the filter can check. Arguments are compared on their low 32 bits, as the kernel truncates them. The Linux sandbox supports little-endian x86_64 and aarch64, and 32-bit programs (i386 or AArch32) are killed. The agent's terminal comes from the host's `devpts` and is bound at `/dev/console`, as containers do, so glibc's `ttyname` finds it there. On Ubuntu, unprivileged user namespaces must be allowed (`kernel.apparmor_restrict_unprivileged_userns=0`). On macOS the agent's process applies a Seatbelt profile with `sandbox_init` just before exec. The profile is written by mahi before the fork, with every path quoted, and bind paths must be canonical (no symbolic link anywhere) since Seatbelt matches resolved paths. It denies by default and allows reading the bound paths and the system (`/usr`, `/bin`, `/sbin`, `/opt` for Homebrew on Apple Silicon and MacPorts, but not their `var` directories, where local databases and service data live, `/System/Library`, the cryptexes, `/private/etc` and the dyld cache), writing the read-write binds, the usual devices, `ioctl`s on its own terminal (which it inherits open, and cannot reopen), and user lookups through opendirectoryd. A read-only bind inside a read-write one gets explicit write denials, and the directories between them cannot be renamed, since macOS has no mounts to protect it. There is no network access except to the one loopback port of mahi's proxy, and to Unix sockets mahi names (the hook socket): other localhost ports stay closed, since host services such as browser debuggers could run code outside the sandbox, so tests that listen on loopback fail on macOS while they pass on Linux; Unix socket pairs still work. Only an allowlist of system settings can be read through `sysctl` (hardware, OS version, process records by pid, which hold no arguments or environment), and signals reach only the sandbox. One gap remains that no Seatbelt rule closes: the kernel serves `KERN_PROCARGS2` outside Seatbelt's sysctl rules and only checks that the caller runs as the same user (or root), so the agent can read the arguments and the environment every process of the user was started with, mahi's and the user's shells included. Secrets must therefore never be passed in the arguments or environment of any of the user's processes while a macOS agent runs: a token exported in the shell is readable from mahi's own entry and from the shell's. The agent's own credential is exposed only to what it could read anyway, but on macOS it should come from a file that mahi reads (the credential store) rather than from mahi's environment: that keeps it out of mahi's and the shell's environment, though the user's other processes can still read it from the agent's own through the same gap. Closing the gap fully would need the agent to run as its own user. Metadata of every file stays readable, since path lookups need it, so names are visible but contents are not. macOS has no private `/tmp` or process namespace: the caller binds a private temporary directory and sets `TMPDIR`, and a process that leaves the agent's process group survives it, keeping its sandbox. `sandbox_init` compiles the profile, so, unlike on Linux, the child allocates between fork and exec; libSystem's fork resets malloc and dyld in the child and the parent never touches libsandbox, the same pattern as Nix's macOS builder.
- **Network proxy**: the agent reaches the network only through mahi's allowlist proxy, an HTTP `CONNECT` proxy for port 443 that mahi runs on the host. The allowlist is a list of host names and is empty by default: an agent with no profile and no `--allow-host` has no network. mahi never looks inside TLS, so it never sees a credential or a prompt, and it can allow or refuse hosts, not paths. mahi resolves the names itself (the agent has no DNS), connects to the addresses it resolved without a second lookup, and refuses loopback, private, shared, link-local, multicast, reserved and documentation addresses, cloud metadata, IPv6 forms that embed such an IPv4 address (mapped, translated, compatible, NAT64, 6to4), and Teredo and the local-use NAT64 prefix, so an allowed name that resolves into the user's network, or a rebinding trick, reaches nothing. A network whose own NAT64 prefix is not one of these cannot be told apart. Host names are exact DNS names, never IP addresses in any form (dotted, hexadecimal or octal). It refuses plain HTTP, IP literals and other ports, answers `503` past 64 concurrent connections, gives the `CONNECT` request 10 s and all the addresses of a name 10 s together, and closes a tunnel after 5 minutes without traffic either way. The agent gets `HTTPS_PROXY` and `https_proxy`; a program that ignores them has no route at all. On Linux the proxy's listening socket is created inside the agent's network namespace, by the namespace's init right after it brings loopback up, and handed back to mahi over a socket pair made before the fork (`SCM_RIGHTS`): a socket keeps the namespace it was created in, so mahi accepts the agent's loopback connections from the host and no relay process runs in the sandbox. On macOS the proxy listens on the host's loopback, on both `127.0.0.1` and `::1` since Seatbelt's `localhost` covers both and another process must not take the other one, the Seatbelt profile allows connecting to that one port and nothing else on localhost, and the proxy URL carries a random per-run password (`http://mahi:<token>@127.0.0.1:<port>`) that the proxy checks in constant time, since other users' processes can reach the port too. The user's own processes can read the password through the `KERN_PROCARGS2` gap below, as they can read the agent's environment, so it does not keep them out; they can also hold the proxy's connections to deny the agent the network, which only hurts that user.
- **Credentials**: mahi is agent- and LLM-neutral: it knows no provider's authentication and never injects a credential into the agent's traffic. The agent starts with an empty environment plus a fixed list of harmless variables, so nothing from the user's shell reaches it implicitly: an API key exported for other tools never switches an agent from a subscription to per-token billing by accident. Whatever the agent authenticates with reaches it only when named: `mahi run --pass-env NAME` passes one environment variable through unchanged, a profile can declare the same (`pass_env`) or keep a login file in the agent's per-thread state, and the credential store hands the agent a token the user saved, without mahi ever interpreting it. `mahi credential add <name>` reads a token once, hidden from the terminal or piped (`claude setup-token | mahi credential add claude`), and keeps it in `credentials/<name>` in mahi's config directory under the same rules as `identity.pub` (600, a 700 directory owned by the user, written once, opened without following symbolic links); `mahi credential list` shows names only and `mahi credential remove <name>` deletes one. `mahi run --credential <name>=<VARIABLE>` hands a stored token to any agent as that variable, only in the agent's environment, never in mahi's own; a profile can name one too (Claude Code's is `claude`, as `CLAUDE_CODE_OAUTH_TOKEN`), which is used when stored and then wins over the same variable in the user's shell. A named credential that is not stored is an error before any thread exists, and a variable given more than one way (`--credential`, `--pass-env` or the profile) is refused. Injecting a key at the proxy was rejected: it needs each provider's header and TLS interception.
- **Snapshot scheduler**: snapshots of the agent's worktree into hidden refs, taken when the agent's hooks report that a tool ran or a turn ended, and otherwise on a timer that runs every second while the worktree keeps changing and backs off to 30 s while it does not. There is no file-system watcher: a worktree belongs to an agent, and a watcher can be made to follow a swapped-in symbolic link out of the tree, exhaust the user's watch limit, or queue events without bound, all of which were demonstrated against `notify`. The timer is the safety net for changes no hook reports (a background process, a person editing the worktree, an agent without hooks): they show up at the next tick, within a second while the worktree is busy and within 30 s after a long idle spell. Pokes never bring snapshots closer together than one second. With the snapshot cache a tick costs about 10 ms on 5,000 files and 170 ms on 100,000, in a release build.
- **Git storage**: `gix` for objects, refs and worktrees, and for fetch. mahi never runs the `git` program. Push is not in `gix` yet, so mahi implements send-pack itself, over a pure-Rust SSH client (`russh`) and, after the handoff, HTTPS. HTTPS is for networks where only HTTPS gets out, often through a company proxy that SSH, even on port 443, cannot pass, so it goes through the proxy `HTTPS_PROXY` names (HTTP `CONNECT`) from the start; its token comes from the credential store, for the host it was stored for only. A machine with a token but no SSH key is not a case for it: mahi signs every agent commit through ssh-agent.
- **SSH transport** (`mahi-ssh`): SSH remotes come first, since most developers already have one and a key in ssh-agent, so there is nothing to set up. `russh` needs `ring` or `aws-lc-rs` for its AEAD ciphers; mahi uses its pure-Rust `rustcrypto` backend from an upstream pull request (Eugeny/russh#782), pinned by commit in `[patch.crates-io]` until it is released, which keeps C out of the build. `russh` needs `ml-kem` 0.3, and `age` 0.12's `ml-kem` 0.2 cannot share its `kem` crate with it, so mahi uses `age` 0.11, which has everything mahi uses (X25519 and passphrase recipients), until an `age` release moves to `ml-kem` 0.3. mahi reads the remote URL itself (`ssh://[user@]host[:port]/path` and git's `[user@]host:path`), refuses a host, user or path that starts with `-`, a host that is not a DNS name or an IPv6 address, a user with a space or a control character and a path with a control character, and quotes the path for the remote shell as git does. Unlike git it does not percent-decode `ssh://` URLs. It does not read `~/.ssh/config`, so a host alias defined there is not resolved. The host key is checked against the user's `~/.ssh/known_hosts` and the system's `ssh_known_hosts` with mahi's own reader: plain, bracketed `[host]:port`, hashed and wildcard names, negated patterns and `@revoked` keys (a revoked key is refused even when another line lists it). `@cert-authority` lines are skipped and host certificates refused. Only key types `known_hosts` lists for the host are offered, so a server cannot switch to a type the user never saw; with no entry for the host every type is offered and the key is then refused as unknown. RSA host keys are not supported, since verifying them would bring back the `rsa` crate, and a host `known_hosts` lists only with RSA keys is reported as such (GitHub, GitLab and Bitbucket all have ed25519 keys). An unknown, changed or revoked key stops the connection before logging in, with its SHA-256 fingerprint; mahi never adds keys to `known_hosts`. It logs in with the plain keys ssh-agent holds, certificates skipped, at most 6 in the agent's order since OpenSSH's server stops after 6 tries; a key the agent will not sign with is passed over. Connecting and logging in must finish within 20 s, and so must starting a command; what the host sends before saying it runs the command is kept, up to 64 KiB. A quiet connection is closed after four unanswered keepalives 15 s apart. Fetching runs `git-upload-pack` on the session as gix's transport, and mahi's own send-pack will run `git-receive-pack` the same way; both ask for protocol version 2 through `GIT_PROTOCOL` (a host that does not take the variable answers with version 1). A command fails when it exits with another status than 0, is ended by a signal, or the connection ends before it closes its channel. What it writes to its error stream is kept, up to 4 KiB, and shown when it fails, each line marked `remote:`, with control and invisible formatting characters (such as bidirectional overrides) replaced so it can neither drive the terminal nor disguise itself. Reading or writing that makes no progress for 5 minutes ends the transfer. gix's network client is built for its protocol code only: it can also run `ssh` and credential helpers, so mahi never lets gix open a connection itself and always hands it this transport. The tests that run the real `git upload-pack` behind an in-process SSH server run with `just test-git`.
- **HTTPS transport** (`mahi-http`): for networks where only HTTPS gets out. gix speaks git's smart HTTP protocol through its `Http` trait, over `ureq` (blocking HTTP/1.1) with rustls and `mahi-tls` as the crypto provider, and the Web PKI's roots; no curl, no reqwest. Requests go through the proxy `HTTPS_PROXY` names (an `http://` proxy, with HTTP `CONNECT`; `NO_PROXY` lists hosts, and their subdomains, reached directly, or `*` for all). Only `https://` remotes are used, and never with a password in the URL. No redirect is followed, so a token only ever reaches the remote's own host; a remote that moved says so. The token is sent with Basic authentication, as `user:token` when stored that way, else with the URL's user or `x-access-token`; a user in the URL, where some write a token, is kept out of the URL gix sees and reports. A refused request (401, 403) names `mahi credential add`. Connecting, through the proxy and TLS, waits at most 20 s, a response's headers at most 60 s after the request was sent, and any single wait to send or receive at most 5 minutes, so a server or proxy that stops making progress fails the transfer. `NO_PROXY` takes host names and IP addresses, IPv6 ones bare or in brackets, not address ranges. Server certificates are checked against the Web PKI only, so a company proxy that intercepts TLS with its own authority is not supported yet.
- **Live layer**: iroh (QUIC, hole punching, relay fallback) + iroh-gossip, one topic per thread. iroh's TLS runs on `mahi-tls`, a rustls crypto provider built on the RustCrypto implementations (TLS 1.3 only: AES-GCM, ChaCha20-Poly1305, X25519, QUIC packet and header protection, and ECDSA, RSA and Ed25519 signature checks for relay certificates; RSA is only ever used to verify, which keeps it clear of the Marvin timing attack on private keys), because the providers iroh offers, `ring` and `aws-lc-rs`, build C code. It is checked against the RFC 9001 test vectors.
- **Shared state**: a CRDT (Automerge or Loro) for multi-writer data: human chat, claims, comments.
- **Prompt queue**: remote prompts are held and injected into the agent's PTY only when it's idle.
- **MCP server**: exposes the thread to every agent (list agents, read others' transcripts/diffs, merge a branch, claim a file/task).

### Adapters (agent-specific)

An adapter answers: how to launch, where state lives and how to relocate it per thread, what the sandbox must allow, how to get structured events, how to detect idle, and how to resume. What an adapter reads of an agent (its hooks' messages, and for Claude Code where it keeps its sessions, its session log and its hooks' payloads) lives in the `mahi-agent` crate, apart from the binary, so that it can be tested and fuzzed on its own; the profiles that point at it, and everything that touches files or sockets, stay in `mahi`.

```rust
trait Adapter {
    fn launch(&self, ctx: &ThreadCtx) -> LaunchSpec;          // argv, env, config dir
    fn sandbox_needs(&self) -> SandboxNeeds;                   // hosts, paths
    fn install_capture(&self, ctx: &ThreadCtx) -> Result<()>;  // hooks, config
    fn events(&self, ctx: &ThreadCtx) -> EventStream;          // normalized events
    fn idle(&self) -> IdleSignal;                              // hook, pattern, or quiet
    fn resume(&self, session: &SessionRef) -> Option<LaunchSpec>;
}
```

Support is a gradient:

1. **No profile**: sandbox, live terminal view, worktree snapshots. Idle = output quiet + optional prompt regex on the virtual screen.
2. **Declarative profile (TOML)**: state relocation, sandbox rules, resume command, idle signal. Until the TOML format exists, mahi ships its profiles built in, chosen by the agent program's file name (`claude` gets `claude-code`); `mahi run --no-profile` runs an agent bare. A profile adds its hosts to `--allow-host`, passes its variables only when they are set (a missing one is not an error, since the agent may sign in another way), sets its quiet settings, and prepares the agent's state directory, `<common git dir>/mahi/state/<thread-id>/<participant>.<agent>`: private to the user, bound read-write, kept after the run for `mahi resume`, and removed with a thread discarded before its agent ran. The state directory holds what the agent keeps in plaintext, such as Claude Code's own transcripts and a `/login` credential, until `mahi end` removes it. Resume must reopen it without following symbolic links, since on macOS the agent can replace the directory itself with a link, and must replace `settings.json` by writing a new file and renaming it, never by following an existing one.
3. **Parser / external adapter**: structured transcript. External adapters are separate executables speaking JSON lines over stdio, so anyone can add an agent in any language.

Example profile:

```toml
[agent]
name = "claude-code"
command = ["claude"]
resume = ["claude", "--resume", "{session_id}"]

[state]
env = { CLAUDE_CONFIG_DIR = "{thread_dir}/claude" }

[sandbox]
hosts = ["api.anthropic.com"]
pass_env = ["CLAUDE_CODE_OAUTH_TOKEN"]

[capture]
hooks = "claude-code"
transcript = "{thread_dir}/claude/projects/**/*.jsonl"
parser = "claude-jsonl"

[idle]
signal = "hook:Stop"
```

Canonical event format: the ACP (Agent Client Protocol) session-update schema. Adapters normalize into it. Agents with a headless streaming-JSON mode can be driven that way when no human is at the terminal (e.g. agents hosted on an always-on peer).

Notes for Claude Code: a per-thread `CLAUDE_CONFIG_DIR` lets mahi inject hooks without touching the user's global config, and tells it exactly where transcripts land. Its credential decides who pays: `ANTHROPIC_API_KEY` bills per token to a Console account, `ANTHROPIC_AUTH_TOKEN` is a bearer token for a gateway, and both win over a subscription (only cloud-provider settings rank higher), while `CLAUDE_CODE_OAUTH_TOKEN`, the one-year token `claude setup-token` prints, uses the user's Pro, Max, Team or Enterprise plan and can only make model requests. The profile therefore passes only `CLAUDE_CODE_OAUTH_TOKEN`, from the stored `claude` credential when there is one (`claude setup-token | mahi credential add claude`), otherwise from mahi's environment, where on macOS the user's other processes can read it. A login from `/login` lives in `.credentials.json` under `CLAUDE_CONFIG_DIR` (on macOS in a Keychain entry keyed to that directory, which Seatbelt blocks), so a per-thread config dir would need a login per thread; the token avoids that. The built-in profile allows only `api.anthropic.com`, which model requests with the token need, and sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (telemetry, error reports, auto-update), `DISABLE_AUTOUPDATER=1` and `ENABLE_CLAUDEAI_MCP_SERVERS=false`, so Claude Code does not reach its other hosts. Signing in with `/login` inside the sandbox also needs `platform.claude.com` (and `claude.ai`), which `--allow-host` adds. Its `settings.json` in `CLAUDE_CONFIG_DIR` sends `UserPromptSubmit`, `PostToolUse` and `Stop` to `$MAHI_BIN hook prompt`, `tool` and `turn-end`. A fresh config directory would start Claude Code's onboarding (theme picker and a connectivity check against `platform.claude.com`) in every thread, so the profile writes `.claude.json` with `hasCompletedOnboarding` once, when it is missing, and never overwrites what Claude Code keeps there (checked with Claude Code 2.1.281). Claude Code's "do you trust this folder" question is left to the user, once per thread: accepting it lets the repository's own `.claude` settings, hooks and MCP servers run, inside the sandbox. Tested end to end with a real subscription token: `/status` shows `CLAUDE_CODE_OAUTH_TOKEN` as the credential and mahi's proxy, and model requests, hooks, snapshots and transcript turns all work. Claude Code refuses to edit files under a `.git` directory without asking, even with `acceptEdits` or explicitly allowed tools, so a worktree inside the git directory does not work with it. Hooks run inside the sandbox, so the hook handler (`mahi hook`) talks to the host binary over a bind-mounted Unix socket. Hook handlers must never block or fail the agent: log and exit 0.

## Storage layout

```
refs/threads/<id>/meta                              # title, base, participants, wrapped keys, landing branch
refs/threads/<id>/state                             # CRDT blob (encrypted)
refs/threads/<id>/agents/<participant>.<agent>/snapshots   # one commit per edit (worktree trees)
refs/threads/<id>/agents/<participant>.<agent>/transcript  # one commit per agent turn (encrypted)
refs/threads/<id>/agents/<participant>.<agent>/session     # native agent session files (encrypted)
```

- Each author only writes their own refs, so the layout is append-only and conflict-free.
- Agents live under `agents/`, named `<participant>.<agent>`, so an agent can never be called `meta` or `state`, and two people can run the same agent in one thread.
- Thread refs are pushed to the project's remote (the durable backing store) after every turn. They are not in the default refspec, so normal clones never see them.
- Fetching a thread brings its remote refs into a local waiting area, `refs/mahi/fetched/<id>/…`, which mirrors the remote (what an earlier fetch left there is removed first); thread refs are never written by the fetch itself. They are then accepted, `meta` first: the fetched document must be the thread's and signed by the owner key the reader trusts. A newer generation than the local one, or the same document, becomes the local `meta`, moved under the pin's lock with the pin written only once the ref moved; the pin refuses another document of a generation already seen, and an older fetched document leaves the local one in place. The check rests on the signed documents, not on commit ancestry, since a joiner's `meta` (recorded from the host) never shares commits with the owner's; only the tip document is read. If the document is refused, the fetch is refused and reported and no ref moves, so a remote cannot swap `meta`. Then each ref under `agents/` moves only forward (behind moves to the fetched commit, ahead stays, a history that went apart stays and is reported), and only for a participant the resulting `meta` lists, other than the reader: the reader's own agent refs are never moved by a fetch, so no one with push access can put files or transcript turns into them (continuing one's own agent from another machine takes them explicitly, see `mahi resume --take-remote` below), and refs of names `meta` does not list are skipped. `state` is skipped until its writers are settled. A ref that fails its checks (not a commit, a merge, a broken history) is refused on its own and the others go on. A fetch with more than 4096 refs is refused, and all the history walks of one acceptance go through at most 2^20 commits together; past that the remaining refs are refused. Someone with push access can so keep a thread from syncing, as they can by pushing a broken `meta`, but cannot move a ref. The size of what a fetch downloads is not capped yet; that comes with the growth caps of milestone 6.
- Nothing is pushed until the user chooses a remote for the clone: `mahi remote <name> --private` or `--public` keeps the choice in the git directory (`mahi/sync/remote`, a private file), `mahi remote` shows it and `mahi remote --off` stops pushing. The remote must exist in the repository's git configuration with an SSH or `https://` push URL (its `pushurl`, or else its `url`, after git's `insteadOf` and `pushInsteadOf` rewriting); an HTTPS remote's token is the credential named `https-` and its host in lowercase with each `-` doubled and each `.` turned into `-`, then `---` and the port unless it is 443 (`mahi credential add https-github-com`; `mahi remote` names it), so no two hosts share a token and none is an agent's; a remote with no such credential, or whose host is not a plain DNS name or IPv4 address, is reached without one (`HTTPS_PROXY` and `NO_PROXY`, or their lowercase forms, which come first, name the proxy); remote names are ASCII letters, digits, `-`, `.` and `_`. An error about a remote names it, never its URL, which may hold a token. On a remote marked public, the agents' snapshots, which are not encrypted, stay local until encrypted snapshot bundles exist; `meta` and the encrypted transcripts are pushed. Fetching needs no choice: `mahi resume`, and `mahi join -- <agent>` once the host's `meta` is recorded, fetch the thread from the chosen remote, at the URL it pushes to since that is where the threads go, or else from `origin` when it fetches over SSH or HTTPS (quietly skipped otherwise; fetching from `origin` cannot be turned off, and it only ever reads), and accept what checks out (see above) as the participant `meta` lists with the user's key, or node for a joiner, never as the name `USER` gives, so the user's own refs are never moved by it, unless they ask: `mahi resume --take-remote` takes the thread's lock, checks ssh-agent, and fetches before it looks for the user's agent, taking the user's own agents' refs too, forward only and only commits their key signed, as another machine of theirs pushed them. It resumes a thread on a clone that does not have it yet, for a thread the user owns; a joined thread needs its owner remembered, which only its ticket gives. It is refused while the clone has a worktree for the thread, whose files would otherwise be recorded over what was taken; `mahi end` records and removes it first. Each ref is taken on its own, so a snapshot history and a transcript that went apart differently can be resumed together, and nothing stops the same agent from running on two machines at once, whose histories then go apart for good. Since signatures do not name the thread, whoever can push to the remote can also put the user's own signed snapshots of another thread into a clone that has none of the thread's. They then use the `meta` the fetch may have brought. A remote without the thread changes nothing; a fetch says so before it connects, and one that fails is reported, with what the remote said escaped and cut short, and the command goes on with what the clone has. A stop signal during the fetch stops it within about 100 ms over SSH, connecting or transferring alike (a host name still being resolved is left behind rather than waited for), and over HTTPS once the request in flight answers or its wait runs out, and ends the command; nothing is accepted unless accepting had already begun, which then finishes. A second signal ends mahi at once; since each ref move and pin write is atomic, at worst a stale lock file is left behind. If stop signals cannot be listened to, the fetch runs without them. Watching with `mahi join` fetches nothing, since history is not shown yet. Once a remote is chosen, `mahi run`, `mahi resume` and `mahi join -- <agent>` push in the background after each turn the agent ends, a burst of turns being one push, and once more after the agent stops and its last snapshot is taken: the agent's transcript and session refs, its snapshots on a private remote, and `meta` when the user owns the thread (a joiner's `meta` is the owner's to push). A push never holds up the agent. A remote that cannot be used (no ssh-agent for an SSH remote, a plain `http://` one, an unusable proxy) is reported when the run starts and nothing is pushed; what the last push did is told when the run ends, including refs another clone moved on the remote, which are not pushed over. A stop signal while the last push runs stops it within about 100 ms over SSH, even while connecting to or waiting on a remote that has stopped answering; over HTTPS it stops once the request in flight answers or its wait runs out (20 s to connect, 60 s for a response's headers, 5 minutes without progress), so the run may take that long to end unless a second signal ends mahi at once. A push stopped before its pack is fully sent moves no remote ref; one stopped while the remote applies it may still have moved them. A second signal ends mahi at once. The remote and its visibility are read when the run starts; choosing another with `mahi remote` takes effect at the next run.
- Pushing is mahi's own send-pack, since gix has none. It runs `git-receive-pack` (protocol version 0, since version 2 has no push), reads the refs the remote advertises, and sends each ref only as a fast-forward of what the remote has: a ref the remote moved to a commit the local one does not descend from, or that is not here, is left alone and reported, to be fetched first. The updates ask for `report-status`, and for `atomic` when the remote offers it, so either every ref moves or none does. The pack holds the new commits and the objects of their trees that are not in the trees of the remote's `HEAD` and of the thread's refs the remote advertised, when this repository has those commits; compressed objects and deltas are copied from local packs, never thin, so the remote must offer `ofs-delta`, as git does. Of the advertisement, mahi keeps only those tips (at most 65536 lines are read), and of the report only the lines for refs it sent, with the remote's reasons escaped and cut to 200 characters. What the remote refuses is reported per ref, a ref whose local history cannot be checked is reported on its own, and a pack the remote cannot unpack fails the push. An interrupted push sends nothing, or a pack cut short, so no remote ref moves. The size of what a push sends is not capped yet either (milestone 6).
- Thread IDs are random, and thread commits use a generic committer identity, to limit metadata leakage.
- Agent commits (snapshots, transcript turns and session state) are signed by their participant's SSH key through ssh-agent, the way git signs commits with SSH: a `gpgsig` header holding an SSHSIG signature in the `git` namespace, SHA-512, over the commit without that header, so `git verify-commit` with an allowed-signers file checks them too. A fetched agent ref only moves when every commit it adds is signed by the key the signed `meta` lists for its participant, which binds a participant's agents to them; a ref that adds a commit anyone else signed, or no one did, is refused on its own and reported. A signature names the participant, not the thread or the ref, so whoever can push to the remote can still point a participant's ref at other commits that participant signed, such as another thread's snapshots; and since a participant's key cannot change yet, a new key would make their earlier commits unacceptable to a clone that has none of them. So `mahi run`, `mahi resume`, `mahi join -- <agent>` and `mahi end` need ssh-agent holding the signing key, and check that it lists the key before they fetch, ask for the passphrase or start the agent; `mahi resume` and `mahi join -- <agent>` also refuse when `meta` does not list the user with that key (under the name `USER` gives, for `resume`), since what they signed would then be refused by everyone else. If ssh-agent stops signing during a run, the first snapshot and the first turn that fail are reported when the run ends, with the count of agent events the lost turns held. A signature ssh-agent is still making is waited for, up to its 60-second timeout, before a stop signal takes effect; a key that asks for confirmation (`ssh-add -c`) would ask at every snapshot and turn, so it is not suited to mahi. `meta` needs no commit signature, since its document is signed.

## Encryption

- Encrypt at write time, before content becomes a git object: serialize → LZ4 → encrypt → write blob. The encrypted payload is the plaintext length (`u32`, little-endian) followed by one LZ4 block, so a reader checks the length against its limit before allocating, and a hostile blob cannot expand without bound. (zstd was the first choice; the only pure-Rust decoder, `ruzstd`, does not bound how much one block expands to.)
- Each participant has two keys. Their SSH ed25519 key ties them to their forge identity and signs (the owner signs `meta` with it, through ssh-agent, so no prompt). Their mahi key, an age X25519 identity, is what thread keys are wrapped to: ssh-agent can sign but not decrypt, so decrypting with the SSH key would need its passphrase every time, and a separate key also keeps a stolen SSH key from opening every thread.
- The mahi key lives in `identity.age` in the user's config directory (`~/Library/Application Support/mahi` on macOS, `$XDG_CONFIG_HOME/mahi` or `~/.config/mahi` elsewhere), encrypted with a passphrase (age scrypt, work factor 18; files asking for more than 19 are refused, which caps scrypt at 512 MiB). It is written to a temporary file and hard-linked into place, so it is either complete or absent and never overwritten. The file (600) and its directory (700) must be owned by the user, and a file others can read, or a directory others can write, is refused. It works the same on Linux and macOS, with or without a desktop keyring.
- `mahi init` creates the mahi key, then writes two public files beside `identity.age`: `identity.pub` (the mahi key's age recipient) and `signing-key.pub` (the ed25519 SSH key that signs `meta`, chosen from the keys ssh-agent lists, without its comment). `mahi run` reads only these, so starting a thread never asks for the passphrase; it is asked when a thread key must be unwrapped, as on resume, which also checks that `identity.pub` belongs to `identity.age`; until then a replaced `identity.pub` would only show there, which is why its file rules matter. `mahi init` refuses an `identity.pub` left without `identity.age`, which would wrap thread keys to a key nobody holds. Both files are written once, never overwritten, and held to the same rules as `identity.age` (600, in a 700 directory, owned by the user, opened without following symbolic links): their content is public, but whoever could replace them could make new threads trust their key.
- SSH keys other than ed25519 are refused, `ssh-rsa` included. Since thread keys are wrapped to mahi keys, not SSH keys, mahi does not build `age`'s SSH support at all, and with it the `rsa` crate and its unfixed timing advisory (RUSTSEC-2023-0071) are gone.
- `age` (Rust `age` crate): each thread has its own age X25519 identity, the thread key. Content is encrypted to the thread key's recipient. The thread key's secret is itself encrypted to each participant's mahi key and stored in `meta`. Adding a participant wraps the existing thread key once more; nothing else is re-encrypted.
- Always encrypted: transcripts, native session files, CRDT state, screen captures.
- Code snapshots: plaintext for private remotes (keeps dedup and diffs), encrypted bundles per checkpoint for public remotes. Ask when unsure.
- Removing a participant rotates the thread key for future content: a new thread identity, wrapped for the remaining participants. Content written before the removal stays readable to the removed participant.
- Optional team recovery recipient (an offline key).

### The `meta` document

- Encoded with `postcard`, in a versioned envelope: `{ version, body, signature }`.
- The body holds, in plain text: the thread ID, the base commit, the owner's name, the thread recipient, and each participant's name, SSH ed25519 public key, mahi key (age X25519 recipient), iroh node key and the thread key wrapped to that mahi key. The title and the landing branch are sealed to the thread key.
- The owner signs the body with their SSH key (SSHSIG, namespace `mahi-meta`, SHA-512).
- A reader verifies the signature against an owner key it already trusts: its own key when it created the thread, or the key in the invite ticket when it joins. Never against the key the document names. This is what stops someone who can push to the remote from replacing `meta` with a thread key they control.
- After unwrapping, a participant checks that their thread key matches the recipient in the body, so the owner cannot give different participants different keys.
- The body names its thread and carries a generation: 0 for a new thread, one higher for each later version. A reader refuses a document whose thread is not the ref's. It also keeps, per thread and outside git, the highest generation it has accepted and that document's body hash. It refuses a lower generation (a rolled-back `meta` that still lists a removed participant or an old key), and a different body with the same generation. Checking that the ref only fast-forwards is not enough, since a force-push can rewrite it. An invite ticket carries the generation the joiner must accept at least. Pins live in each clone's git directory (`mahi/pins/`), so a fresh clone starts without one, and that minimum is what protects its first load.
- A `meta` document is identified by the hash of its body, not by its git blob id: the envelope around a signed body can be re-encoded without breaking the signature.
- Keys that are points of small order are refused: an SSH ed25519 key of small order lets anyone forge its signatures, and a mahi key of small order gives an all-zero shared secret (age panics on it).
- Reading is bounded: 256 KiB per document, 256 participants, and a 256-byte title.

### Transcripts

- Each agent turn is one commit on `refs/threads/<id>/agents/<participant>.<agent>/transcript`, whose tree holds a single file, `turn`: the turn sealed to the thread key.
- A turn is `postcard` in a versioned record: its number, counted from 0, and its events, each a host-assigned sequence number and an opaque payload (the ACP session update, as the adapter produced it).
- Each sealed turn also stores the running last sequence number of the whole transcript, so an empty turn carries it forward.
- Turn numbers go up by one from commit to commit, and sequence numbers strictly increase within and across turns. Appending checks the new turn against the transcript's tip (its newest commit, turn number and running last sequence number), which the host keeps in memory or recovers by opening only the newest commit; it never opens earlier turns. Reading walks newest first, holds one turn at a time, and checks every commit it walks, which also has to have at most one parent.
- Reading is bounded: 1 MiB per event, 100,000 events and 64 MiB per encoded turn (plus the sealing overhead for the stored blob), and the caller chooses how many turns to read back.

### Native session files

- An agent's own session files (for Claude Code, the conversation it resumes with `--continue`) are recorded on `refs/threads/<id>/agents/<participant>.<agent>/session`, one commit per change, signed like the agent's other commits.
- Each file is cut into 64 KiB pieces, each sealed to the thread key on its own and named in the commit's tree by its tag: a BLAKE3 keyed hash under a key derived from the thread key, so names reveal nothing without it. A piece the previous commit holds is reused rather than sealed again, once that commit is found signed by the user's own key, so a session file that only grew, as a conversation log does, costs the pieces it gained. A sealed `manifest` in the same tree lists each file's path, size and piece tags, in a versioned `postcard` record; paths are relative, `/`-separated, with no empty, `.` or `..` component. A commit whose files are exactly the previous commit's is not written.
- Recording and reading are bounded: 4096 files, 8192 distinct pieces and 512 MiB of file contents per commit, 1024-byte paths 16 components deep. Reading checks the manifest (valid paths in strictly ascending order, none a directory of another or equal to another but for ASCII case, sizes that match their piece counts, every piece present, at most 4096 files as it decodes) before anything is written, then each piece's size and tag as it is copied out.
- The profile names the directory the agent keeps its sessions in, inside its state directory; for Claude Code, `projects/` and the worktree's path with every character but an ASCII letter or digit replaced by `-`, one per UTF-16 unit, as Claude Code names it (a path it would shorten, past 200 characters, is not recorded). Nothing else of the state directory is recorded, so its credentials never are. The directory is recorded after each turn the agent ends and once more when it stops, on a thread of its own so that hook messages keep flowing, a burst of turns being one record. It reads only regular files and directories, never through a symbolic link and skipping what it cannot open; it first walks the directory to count at most 8192 entries and add up the files' sizes, so a session past the limits is refused before anything is sealed.
- Before the agent starts, when its state directory has no session directory for the worktree, as on another machine or after `mahi end`, the latest recorded session, once found signed by the user's own key, is written there: into a new private directory beside it, under a random name, that then takes its name, so an interrupted restore leaves no half session, and under the name the worktree's path gives on this machine, so `claude --continue` finds it. A session directory already there is kept as it is. A session that cannot be recorded or restored is reported and the agent runs all the same.
- What the pieces show without the key: how many there are, which ones repeat from commit to commit (so that a file grew, and its size to 64 KiB), and the compressed size of each, like every sealed blob; a conversation's last piece is sealed again at each change, so its compressed size is seen as it grows.

## Session lifecycle

`mahi run -- claude` (or any agent):

1. Find the repository that holds the current directory, as git does (a repository owned by another user is refused, as git refuses it), and create the thread: ID, thread key, `meta` ref (base commit, creator key, participants, landing branch). `HEAD` must be on a local branch, which becomes the landing branch. The creator's participant name comes from `USER`, lowercased, and the agent's name from the file name of the agent program. Optionally snapshot uncommitted changes as the real starting point.
2. Add a linked worktree at the base with a detached `HEAD`, at `$XDG_DATA_HOME/mahi/worktrees/<repository>-<hash>/<thread-id>` (`~/.local/share/…` when it is unset, on macOS too, since `~/Library` is kept from agents), where `<repository>` is the repository's name made safe (at most 64 bytes) and `<hash>` the first 4 bytes of the SHA-256 of its common git directory's path, in hex. Before the thread is created, mahi refuses a worktree root inside a private directory and opens the repository's directory without following links, as a directory the user owns, reset to mode 700; an empty one is removed when a start fails. The worktree is outside the git directory because agents protect files under a `.git` directory (Claude Code asks before every edit there, whatever its permission mode), and, with the default location, outside the user's checkout so it does not show in `git status`. It is still registered in the repository's `worktrees/` as git does, so no branch appears in the user's branch list; the agent's work is recorded in its `snapshots` ref. mahi writes git's linked-worktree layout itself and checks files out with gix. `.gitattributes` conversions (`text`, `eol`, `ident`, `working-tree-encoding`) apply as in git, so `git status` stays clean, but no filter driver is configured, so no filter program (such as git-lfs) runs: filtered files are checked out as stored. The worktree's git dir and the common git dir are read-only inside the sandbox (git config and hooks can execute code).
3. Start the network proxy and the snapshot scheduler. On macOS the proxy listens before the agent starts; on Linux its listening socket only exists once the sandbox is set up in step 5, and the proxy starts on it then. Snapshot zero, the checked-out base, is committed to the agent's `snapshots` ref as soon as the thread exists; after that a commit is added only when the worktree's tree changed, and a last snapshot is taken when the agent exits. Snapshot errors do not stop the agent: the first one is reported when mahi ends, and so is the number of paths the last snapshot left out. A stop signal during snapshot zero or the last snapshot stops the walk between two files, so no ref update is cut short and no lock is left behind; mahi then ends with that signal, and a second signal ends it at once, which can still cut short a ref update in progress and leave its lock. When a stop signal ended the agent, further signals already queued are dropped, so a terminal that sends `SIGHUP` twice does not lose the last snapshot; a stop signal that arrives as the agent exits on its own counts as the first one. Not yet done: nothing caps how much the snapshots add to the repository's objects.
4. Create the per-thread agent config dir and install capture hooks. The agent sees `MAHI_BIN` (the mahi binary, bound read-only) and `MAHI_HOOK_SOCKET` (a Unix socket in its private scratch directory, the only one it may connect to). A hook runs `mahi hook prompt|tool|turn-end` with the event's details on standard input; for a known event it exits 0 even when mahi cannot be reached, so it never breaks the agent, but it waits for its standard input to close and for mahi to accept the connection. It sends the event's name, a newline, the details' length (four bytes, big-endian) and the details, so a message cut short is refused. mahi reads one connection at a time, with a 2 s deadline, a closed set of event names and at most 1 MiB per event, and drops what does not fit its queue of 16 messages; the number dropped is reported when mahi ends. When the agent has exited, mahi still reads the connections already waiting, for about 5 s at most (under 10 s even when a slow connection is being read), before it seals the last turn. A failed accept counts as a dropped event and does not stop the server. `tool` and `turn-end` ask for a snapshot. Every event is recorded, as its name, a newline and its raw details, until adapters normalise them; `turn-end` seals the events since the last turn into one encrypted transcript commit of at most 64 MiB, and the rest are sealed when the agent exits. Not yet done: nothing caps how many turns an agent can write.
5. Launch the agent in the sandbox → PTY → the user's terminal. Everything that can fail without the thread is checked before step 1, including that the agent is a native program or a `#!` script: libc's `execvp`, which `std::process::Command` uses, would run any other file with `/bin/sh`, so a start that failed would look like an agent that ran and exited. Files run through a `binfmt_misc` handler are refused for the same reason. If the agent still cannot start, the thread's `meta` ref, its pin and its worktree are removed, so a failed start leaves nothing to push. A stop signal (`SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`) during steps 1 and 2 interrupts the checkout, removes what was made, and then ends mahi with that signal. Signing `meta` through ssh-agent cannot be interrupted, since the agent may be waiting for a confirmation or a key touch, so a second stop signal ends mahi at once and may leave the new worktree behind.
6. Start the live layer (milestone 2, see Participants and the live layer), before the agent starts so its whole screen is known: bind the iroh endpoint with the user's node key, serve `meta` to the thread's participants, join the thread's gossip topic and broadcast the agent's terminal. The output goes to the user's terminal first; a copy feeds the host's `vt100` screen, which numbers each chunk it takes, and a queue of chunks for one broadcaster thread, which sends output, resizes and screens in order. A screen says through which chunk it goes, and the broadcaster skips the queued chunks it holds, so a viewer never applies output twice. When the network falls behind, chunks are dropped rather than slowing the agent, and the broadcaster then sends the whole screen, which viewers already following accept. A send that fails counts as a drop too, and a screen skips queued chunks only once it can be sent. Screen requests are answered at most once a second per requester, several at once from one snapshot; a viewer asks again until a screen anchors it. When the agent ends, output still queued is dropped. A live layer that cannot start is reported and the agent runs without it. `MAHI_LIVE=off` turns it off, `MAHI_LIVE=local` runs it without relays, reachable only on the local network, and any value other than those and `public` is refused rather than guessed. Teammates are invited with `mahi invite`, which prints their ticket.
7. Each turn: events get host sequence numbers, are broadcast live, and are flushed as an encrypted turn commit at turn end, then pushed to the remote.

Joining: `mahi join <ticket>` runs in a clone of the project, checks that the ticket was made for this machine's node, fetches `meta` from the host (retrying for about 30 s while the host rereads it), checks it against the owner key and minimum generation in the ticket and that it lists both this node and the host, refuses a thread this repository started (one with a `meta` ref but no remembered owner), records the document as the thread's `meta` ref and pins it, only after checking it against any `meta` ref already there (when milestone 3 fetches the owner's refs, a fetched `meta` that does not verify under the remembered owner key is refused and reported, never silently put in place: a ticket naming a thread the user started in another clone must not take it over), then remembers the ticket's owner key for the thread (in the git directory, write-once: another key for the same thread is refused) (until milestone 3 fetches the owner's refs, which then replace this local copy), asks for the passphrase to unwrap the thread key, shows the host's current screen and then follows the live terminal. The viewer draws on the terminal's alternate screen from its own `vt100` copy, follows one agent of the host's participant, asks for the screen again whenever frames were dropped or a sender restarted, and leaves on `q`, Ctrl-C, Ctrl-D or a stop signal, or when the topic closes. It draws the screen's contents and cursor only, never the agent's input modes (mouse tracking, bracketed paste, keypad), and resets the terminal when it leaves, however it leaves. A host that has sent nothing for 5 s sends a heartbeat, so a viewer that hears nothing from the host for 30 s says it may have stopped and leaves. `mahi join <ticket> -- <agent>` then runs the user's own agent in the thread instead of watching (milestone 2): in a worktree at the thread's base commit, which the clone must have, under the user's own `<participant>.<agent>` refs, sandboxed and recorded as with `mahi run`, and hosted live on the thread's topic, joined through the owner's host, trusting the ticket's owner key. A second `join` continues the same agent in the same worktree; if that worktree is gone, it is rebuilt as `mahi resume` does. Agent options such as `--allow-host` are refused without an agent. `mahi join` also keeps where it reached the host, in the git directory, and `mahi resume` and `mahi end` then work for a joined thread as for the user's own: they check `meta` against the owner key remembered from the ticket when there is one, and otherwise against the user's own key, never both, and `resume` rejoins the thread's topic through the remembered host. From milestone 3 it also fetches `refs/threads/<id>/*`, renders history, and dedupes by sequence number. The teammate can then watch, queue prompts to others' agents, or `mahi agent add` to run their own agent in the thread.

Ending and restarting: `mahi end` waits for idle, commits final turns, compacts, pushes, and stops sandboxes. In milestone 1 it is local: `mahi end <thread-id>` ends a thread the user owns and that is not running (it takes the thread's lock and refuses otherwise), records the worktree in a last snapshot of the user's agent (`--agent <name>` picks one of several), then removes the worktree, the state directories of the thread's agents with the plaintext they hold (such as Claude Code's own transcripts and a `/login` credential) and the thread's lock file. The thread's refs stay: they are its history. It needs no passphrase, since snapshots are not encrypted. Files `.gitignore` excludes are not in snapshots and are removed with the worktree, like build output; files a snapshot cannot record (too large, unreadable) make `mahi end` refuse and list them, and `--force` removes them anyway. A worktree whose `.git` file no longer links back is left in place and the thread is not ended; a worktree deleted by hand only has its registration pruned. Nothing is removed before the last snapshot is recorded, and a stop signal while it is taken ends `mahi end` with nothing removed; once it is recorded, the removal runs to its end. `mahi resume <id>` fetches, decrypts, restores worktrees at their latest snapshots, restores agent config, and relaunches (native resume if the adapter supports it, otherwise a handoff bundle).

Local resume (milestone 1): `mahi threads` lists the threads in this repository from their refs: id, agents, and whether the worktree is still there; it reads no encrypted content, so it asks for no passphrase. `mahi resume <thread-id>` resumes a thread the user owns: it checks that `meta` is signed by the user's own signing key, asks for the passphrase to unwrap the thread key, reopens the registered worktree, or rebuilds it when its directory was deleted. A rebuilt worktree has a detached `HEAD` and an index at the thread's base, and the files of the agent's latest snapshot, so the recorded work shows as changes on top of the base. Commits the agent made are kept only as those files, and a file it had added although ignored is left out of later snapshots, since the snapshot does not record what was tracked. A worktree whose directory still exists but no longer links back is not rebuilt: it is reported for the user to repair. mahi then reopens the agent's state directory without following symbolic links and rewrites the profile's files by replacing them, then runs the agent as `mahi run` does, with the same options. Snapshots continue from the `snapshots` ref's head (no new snapshot zero) and turns from the transcript's tip. The agent is the program named after the thread's agent slot, looked up on `PATH`, plus the profile's resume arguments (`--continue` for Claude Code, which reopens its last conversation from the kept `CLAUDE_CONFIG_DIR`); `mahi resume <id> -- <agent> [args…]` runs another command, and `--agent <name>` picks one of several agents. Checks that need no key (the agent program, the sandbox, the network, the owner's signature on `meta`) run before the passphrase is asked. Only one mahi at a time runs a thread: `mahi run` and `mahi resume` hold an advisory `flock` on `locks/<thread-id>` in mahi's configuration directory for as long as they live, which the system releases however they exit; no sandbox sees that directory, so an agent cannot hold another thread's lock. `mahi end` removes a thread's lock file; a mahi that opened it just before holds the lock only if the path still names the file it locked, and tries again otherwise, so an ended thread never has two holders. The state directory is opened once without following symbolic links, checked through that open descriptor (a directory the user owns), reset to mode 700, and written relative to it.

Host migration: if an agent's host leaves, another peer restores from the latest snapshot and resumes the session (native or handoff).

## Participants and the live layer

Milestone 2 lets teammates watch a thread live, and run their own agent in it, before thread refs are pushed anywhere.

- Each user has an iroh node key: `node.key` in the config directory, an ed25519 secret held to the same file rules as `identity.age` (600 in a 700 directory, owned by the user, written once, never followed through a link). `mahi init` creates it, also on a setup made before it existed. Its public half, the node id, names the user's machine on the live layer. There is one per user, so it links their live sessions the way their SSH key links their `meta` entries.
- `mahi id` prints the user's participant card, one line holding only public keys: `mahi-participant <name> <mahi key> <node id> ssh-ed25519 <key>`. Fields are separated by spaces, anything after the SSH key is its comment and is dropped, and a card holding a control character (such as a second, pasted line) is refused. The teammate sends it any way they like; the owner must know it came from them, as with an SSH public key.
- `mahi invite <thread-id> <card>` is run by the owner. It asks for the passphrase, unwraps the thread key, adds the participant with the thread key wrapped to their mahi key, signs the next generation of `meta`, pins it and prints a ticket. It asks for the passphrase only when it must add someone: a card already listed exactly gets its ticket again, and one that shares a name or key with a listed participant is refused first. The thread may be running: its host rereads `meta` when an unknown node connects, and `invite` then takes the running host's address instead of binding a second endpoint with the same node key, since a relay keeps only the newest connection of a node. A running host publishes its address, and updates it when it changes (such as when its relay answers), in `live/<thread-id>` in the config directory, a private file it removes when it stops; `invite` reads it when the thread's lock says the thread is running, and otherwise binds its own endpoint while it holds the lock, so for those few seconds starting or resuming the thread says it is already running. The address is found before anything is changed, so an invitation that cannot get one adds no one. The ticket is `mahi1…`, bech32 over `postcard`: its version, the thread ID, the host's address (node id, relay URL and direct addresses, found by binding the endpoint), the owner's SSH key, the minimum `meta` generation and the invitee's node id. It holds no secret: the thread key only ever travels wrapped to the invitee's mahi key. A ticket is pasted from elsewhere, so it is parsed strictly (at most 1023 characters, bech32m, no trailing bytes), its relay must be a plain `https` URL on a domain name other than `localhost` (no user information, query or fragment), and it holds at most 8 direct addresses, none unspecified, multicast, broadcast, IPv6 link-local or on port 0, so a hostile ticket cannot point the joiner's machine at local services.
- The endpoint is iroh with the user's node key and `mahi-tls`, and uses n0's public relays, which only forward ciphertext. There is no discovery service: addresses come from the ticket. It listens on a UDP port chosen by the node id among the 16384 dynamic ports (a random one when that is taken), so the direct addresses a ticket holds still reach a host started later. The relay is the address that works across networks: a ticket is not printed without one, and a host reaches the same relay again as long as it runs from the same place. `node.key` is stored unencrypted, like an SSH key without a passphrase, so `mahi run` needs no passphrase: whoever reads it can speak as the user on the live layer, though they still cannot open a thread without the mahi key.
- `meta` is served over a direct connection (ALPN `mahi/meta/1`). The joiner sends the thread ID, and the host answers with the current signed document only when the connecting node id, which iroh's TLS authenticates, is a participant's node key in it; otherwise it closes the connection. A host rereads its `meta` ref for an unknown node at most once every 5 s, whoever asks, since fresh node keys cost nothing, and runs at most two reads at once; a request beyond that, a slow read or a failure on the host's side closes the connection as "unavailable", which a joiner retries, and only a node that is not a participant is told "refused". Answers are bounded like any `meta` read (256 KiB). The joiner checks the signature against the owner key in the ticket, never the one in the document, refuses a generation below the ticket's minimum, pins it and checks that it lists both its own node id and the host's.
- `mahi join` runs in a clone of the project, since resuming needs the base commit: pins live in that clone's git directory as they do for the owner.
- Live messages travel on one gossip topic per thread. iroh-gossip admits anyone who knows a topic's ID, so the ID and the sealing key are derived from the thread key, which only participants hold: HKDF-SHA256 with the thread key's secret as input, the thread ID as salt, and `mahi-live-topic-v1` or `mahi-live-seal-v1` as info. Rotating the thread key when a participant is removed therefore moves the thread to a new topic and key, which is what shuts a removed participant out; peers follow the newest `meta` they have pinned. The host is the bootstrap peer. A node accepts gossip connections only from the nodes of its `meta`'s participants; connections gossip opens itself, to peers other members name, are not filtered, and iroh-gossip also learns those peers' addresses from them, so an admitted participant can make another participant's node dial an address of their choosing (it then only sends sealed frames there). A broadcast waits at most 2 s, so a peer that stops reading cannot stall the sender, and a receiver counts the frames it drops when it falls behind, so a viewer then asks for the screen again.
- A frame is `postcard` of the sender's node id, a signature, a 24-byte random nonce and the ciphertext, and is at most 64 KiB. The signature is the sender's node key's ed25519 signature over `mahi-live-v1`, the thread ID, the topic ID, the sender's node id, the nonce and the ciphertext, so it cannot be mistaken for anything else the node key signs, such as TLS handshakes. A receiver checks the size, that the sender is a participant's node in its `meta`, then the signature, and only then opens the ciphertext: XChaCha20-Poly1305 under the sealing key, with the thread ID and the sender's node id as associated data. The plaintext is the sender's epoch (16 random bytes drawn when its mahi starts), a sequence number and a body.
- Per sender, a receiver keeps the current epoch and the highest sequence number accepted in it, and drops anything not above it. A newcomer asks for the screen with a random challenge, and accepts the epoch of the first part of a screen that echoes it; after that, a new epoch from the same sender is accepted only through a fresh screen request, since one challenge anchors a sender only once. A receiver also remembers the last 256 challenges it was asked, and drops a request that repeats one. Replayed frames, even whole old runs re-sent by a participant, are dropped. Screens and resizes of zero rows or columns, or more than 1000 of either, are refused, so a viewer never allocates a huge screen. (The HKDF implementation does not wipe its internal state, which briefly holds a key derived from the thread key; the derived keys themselves are wiped.)
- Bodies: terminal output (the agent's output, in chunks) and resizes, heartbeats, a request for the screen (carrying its challenge), and the screen (the host's `vt100` virtual screen, as the escape sequences that redraw it, with its size, in chunks that each fit a frame). Output, resizes, heartbeats and screens name the agent slot they belong to, and are accepted only from the node of the participant who owns that slot: other participants cannot draw on a viewer's terminal. Even then the agent's output is untrusted, since the agent is sandboxed code: a viewer feeds it to its own `vt100` screen and redraws its terminal from that, so escape sequences such as clipboard writes (OSC 52), titles or hyperlinks never reach it. A host answers at most one screen request per second, and one per second per requester, coalescing the rest.
- Until milestone 3, a joiner receives `meta`, the current screen and the live stream; history comes with fetch. A viewer's terminal is read-only: keys are not sent, and prompts to others' agents come with milestone 4.

## Multi-engineer, multi-agent

- Every teammate runs their own agent, on their own machine, with their own worktree branch, sandbox and credentials.
- Agents never write into each other's worktrees. Work flows by merge ("merge Alice's agent's fix into my worktree"), and agents resolve conflicts. Forking = starting a new agent from another agent's snapshot.
- Remote prompts go into the host's queue; permission requests always route to the host, never the sender. Default: the host accepts each remote prompt with a keypress.
- In-session UI. While an agent runs, it keeps the whole terminal: mahi passes its output and the user's keys through untouched and draws nothing of its own, since a status row cannot hold what several teammates do and compositing the agent's screen would cost fidelity. mahi speaks up in two ways only.
  - Notifications. When a teammate's prompt arrives, mahi asks the terminal to raise a desktop notification (`OSC 9`, and `OSC 777;notify` and `OSC 99` for the terminals that use those; others ignore them) naming the teammate and the prompt's first words, then rings the bell once. It writes these only between the agent's escape sequences, tracking where the agent's output stands, so it never cuts into one. Watching needs no notification: the invite was the permission.
  - The palette. `Ctrl-Space` (which no common agent binds; pressed twice, one goes to the agent) opens mahi's palette. Some setups take that key before the terminal sees it (macOS switching input sources when more than one is enabled, VS Code's terminal, a tmux prefix), so `palette-key` in `~/.config/mahi/config.toml` changes it: `ctrl-space`, `ctrl-a` to `ctrl-z` (one the agent does not need; not `ctrl-g`, which ends terminals' answers to an agent's queries, nor `ctrl-h`, `ctrl-i`, `ctrl-j` or `ctrl-m`, which terminals also send for Backspace, Tab and Enter), `ctrl-]`, `ctrl-\`, `ctrl-^`, `ctrl-_`, or `f1` to `f12`. mahi recognises the key both as terminals send it by default (a control byte or an `F`-key sequence, including the Linux console's) and in the kitty keyboard protocol or xterm's `modifyOtherKeys` an agent may turn on (a release or repeat the kitty protocol reports goes nowhere), never inside a bracketed paste, even one whose start arrives split across two reads, and says which key it is when a run starts. The palette is a rounded box centred over the agent's screen, with a filter line on top. While it is open, the agent's output is held back, up to 1 MiB (past that the palette closes itself), and keys go to the palette. It lists the prompts waiting for the agent, oldest first, each with its sender and age (`Enter` accepts, `Ctrl-X` rejects, `Tab` accepts and always accepts that teammate's prompts for the rest of the run), and who is watching; later, actions such as inviting, pushing now or handing over. `Esc` closes it: mahi releases what it held back and makes the agent repaint by resizing its terminal one row smaller and back.
- Remote prompts. A teammate running `mahi join` opens the same palette in the viewer and writes a prompt for one of the thread's agents; it travels as a sealed, signed live frame, like every other, to the agent's host, which accepts it only from a participant `meta` lists and only for an agent it runs. A prompt names the host's run, which the viewer learned from the host's screen, and a random id, which the host's answers carry and the viewer matches with the agent; a host takes a prompt only for its current run and only once, so none can be replayed into a later run, and takes at most 1,024 prompts from one node in a run, so remembering their ids stays bounded. A prompt holds at most 8 KiB of text; control characters other than newlines and tabs, invisible characters and text-direction marks are left out when it is shown or given to the agent. An accepted prompt waits until the agent is idle (after the turn-end hook its profile reports, or else after 2 s without output or keys) and is then typed into it: as a bracketed paste when the agent turned that mode on, then `Enter`. The sender learns whether it was accepted, rejected or dropped when the run ended. Nothing a teammate sends reaches the agent without the host user's keypress, unless that user chose to always accept that teammate for the run.
- Advisory claims (file/task) live in the CRDT and are exposed via MCP so agents avoid overlap.
- Cross-agent handoff: a new agent, of any kind, takes over another agent's work with a briefing mahi writes from what it recorded, since mahi calls no model itself. `mahi handoff <thread> --from <participant>.<agent> -- <agent>` starts it: in a thread whose `meta` lists the user with their key, whose named participant `meta` also lists, and with no worktree for the thread in this clone (`mahi end` records and removes one), since the new agent's worktree is built from the other agent's latest snapshot on top of the thread's base, and the new agent's own snapshots start from it. The new agent is the user's own, under their name; one they already have in the thread is resumed instead. mahi fetches the thread first, like `mahi resume`, so a teammate's latest work is there. The briefing is written, readable by the user only, into the agent's private temporary directory, outside the worktree, so it is never recorded or committed; the agent gets its path in `MAHI_HANDOFF`, and an agent whose profile takes a first prompt, such as Claude Code, starts with one asking it to read the notes and continue, after `--` so that none of the user's own options takes it as its value. For any other agent, mahi prints that sentence for the user to give it. The previous agent's transcript is walked newest first through at most 10,000 turns; one that cannot be read back to its start, past that or past a commit that does not check out, gives what was read, and the briefing says its first prompt is only the earliest read. If the new agent cannot be started, its snapshots, state and worktree are removed again, so the handoff can be retried. The worktree holds a teammate's files, which may include settings their agent reads, such as `.claude/settings.json` or `.mcp.json`; the new agent runs in the same sandbox as any other, and its own trust prompts are left to it. The briefing is Markdown, at most 64 KiB, and quotes the thread's records, which other participants or agents may have written, as context, never in the voice of its own instructions: as block quotes, or code spans fenced longer than any backquotes they hold. It holds the thread's title and branch and which agent did the work; what the user asked, oldest first (the first prompt, which is the goal, and as many of the latest 30 as fit, each cut to 2000 characters and 60 lines), since the later prompts hold the user's corrections; the files the previous agent's latest snapshot changed from the base, as a list with `git status` and `git diff` named for the details, since the new agent works on those very files; its latest 20 tool calls; and, when its profile can read its session log and the recorded session is signed by the key `meta` lists for its participant, its latest 3 replies from the newest log (for Claude Code, the text parts of its own `assistant` entries, not a subagent's, an API error's or one Claude Code made up; a log that cannot be read gives no replies rather than an older log's), so what it found or decided is not lost at no extra cost. The log is read line by line, leaving out lines over 4 MiB. Each section has its own share of the size, filled from the newest record back, and says what it left out. Control characters other than newlines and tabs, invisible characters and text-direction marks are left out. Listing the changed files reads at most 64 levels, 65,536 trees and 32 MiB of trees, since a snapshot may come from another participant.

## Landing

- A thread results in **one remote branch**. The remote serializes it: only fast-forward pushes; a rejected push → fetch, merge, retry.
- The integrator (thread owner by default; needs push access) merges agent branches locally, curates them into clean commits, rebases onto main, and pushes.
- Commit trailers link back to the thread:

  ```
  Thread: 7f3a9c2e
  Agent: claude-code (alice)
  Session: 01J8...
  ```

- mahi generates the PR description from the thread: summary, key decisions and why, agents and people involved, link to the thread. The final look and approval happen in the forge.

## Compaction and cleanup

Compaction tiers:

- **Live**: every snapshot.
- **Rolling**: older turns collapse to one snapshot per turn.
- **Landed**: one encrypted transcript blob per agent, one or zero snapshots per turn (per policy).
- **Expired**: thread refs deleted; only the trailers remain.

Compaction is done by one peer (owner or integrator), only when agents are idle, pushed with `--force-with-lease`. A compaction marker in `meta` makes the rewrite authoritative.

Branch deletion triggers cleanup:

- Detected via `git fetch --prune` on any `mahi` command, and optionally by a CI job on the forge's branch-delete event.
- Merged (check with patch IDs or the forge API, since squash merges break ancestry): compact to the Landed tier or delete, per policy.
- Deleted unmerged: tombstone in `meta`, grace period (~2 weeks); restoring the branch cancels it; then delete.
- Purge: delete remote refs; locally remove worktrees, config dirs, sandbox state, refs **and reflogs**, prune objects, and destroy the thread keys (crypto-shredding covers forge caches). Peers clean up on their next fetch. Limit: purging can't be forced on a machine that never runs mahi again.

## Serverless caveats

- NAT traversal: hole punching works for most networks; symmetric NATs need a relay, which can be any peer with a public IP (it only forwards ciphertext).
- Discovery: invite tickets shared out of band, or DHT (pkarr / Mainline); mDNS on a LAN.
- Async work across time zones goes through the remote; realtime needs peers online together.
- The LLM itself is a hosted API unless a local model is used.

## Testing

- Unit and integration tests cover behaviour; property tests (`proptest`) cover invariants such as round trips and ordering, inside the unit tests.
- Fuzzing is used wherever it can be: every decoder and parser of input from a peer, a remote, an agent, a transcript or a file in a worktree has a fuzz target. The targets live in `fuzz/`, a crate outside the workspace built with `cargo-fuzz` (libFuzzer, on nightly, as `rustfmt` already is). It is a development tool only, never part of the mahi binary, so the pure-Rust rule for mahi's dependencies is unchanged. Each target checks that any input is accepted or refused without a panic, a hang or memory beyond the documented bounds, and, where there is an encoder, that decoding what was encoded gives it back.
- Targets, by crate: `mahi-core` (thread ref names, participant, agent and slot names); `mahi-crypto` (opening sealed content, unwrapping thread keys); `mahi-identity` (ssh-agent answers, identity and key files); `mahi-thread` (`meta` documents and their signatures, participant cards, transcript turns, session manifests and pieces, fetched-ref acceptance, handoff briefings); `mahi-store` (send-pack advertisements and reports, tree listings and changed paths, snapshot names); `mahi-ssh` (`known_hosts`, remote URLs, exec output); `mahi-live` (tickets, live frames, meta requests); `mahi-proxy` (`CONNECT` requests and host names); `mahi-tls` (records, handshake messages, certificates and their verification); `mahi-agent` (hook messages, Claude Code's hook payloads, session logs and session directories).
- The fuzz crate reaches only the library crates' public items, so each library that decodes something behind a check the fuzzer cannot pass (a signature, a seal), or behind a socket or a transport, exposes that decoder to it in a `fuzzing` module, compiled only with `--cfg fuzzing`, which `cargo-fuzz` sets: `meta` bodies past their signature, transcript turns and session manifests past their seal, live frames past theirs. The first round covers `mahi-core`'s names, `mahi-crypto`'s opening and unwrapping (with a seal and open round trip), `mahi-thread`'s `meta`, cards, keys, turns and manifests (each with a round trip), session paths and briefings, `mahi-live`'s tickets (past their bech32m checksum, with a round trip) and frames, `mahi-ssh`'s `known_hosts` and URLs, `mahi-http`'s URLs and proxy settings, `mahi-proxy`'s host names and `CONNECT` requests, `mahi-agent`'s hook messages (with a round trip) and Claude Code's session directories, log lines and hook payloads (with their size bounds), `mahi-identity`'s ssh-agent answers to signing and listing, and `mahi-store`'s send-pack advertisements and reports. A live `meta` request is a fixed 16-byte thread id read to that bound, so it needs no target. Each input may run 10 s before it counts as a hang. The rest of the list above is still to come, notably `mahi-store`'s tree listings, session pieces, fetched-ref acceptance, `mahi-ssh`'s exec output and `mahi-tls`, which move into reach as their parsers do.
- `just fuzz <target> [seconds]` runs one target. `just fuzz-all [seconds]` runs each in turn. CI runs every target for 20 s on each push to `main` and for 5 minutes on a nightly schedule, with the corpora cached between runs and a crashing input kept as an artifact. A crash becomes a regression test, with its input, in the unit tests of the crate it was found in.

## Milestones

1. `mahi run -- <agent>`: sandbox, snapshots, encrypted transcript refs, local `mahi resume`, local `mahi end`.
2. P2P live layer: iroh gossip, invite tickets, live terminal view for teammates; resuming your own agent in a thread someone else owns, trusting the owner's key from the invite ticket.
3. Remote backing store: push/fetch thread refs, cross-machine resume, handoff bundles; rebuilding a missing worktree from the agent's latest snapshot (useful locally too, after a worktree was deleted); binding a participant's agents to the signed `meta`, since once peers push refs, the names under `refs/threads/<id>/agents/` are theirs to choose.
4. Multi-agent threads: the in-session palette and notifications, remote prompts and their queue, `mahi agent add` (one worktree per agent), `mahi merge` (gix's three-way merge of another agent's latest snapshot into the user's worktree), MCP coordination tools (`mahi mcp`), claims held by the thread's host (a CRDT later, if offline multi-writer state proves needed).
5. Landing: integration, curated commits with trailers, PR description generation.
6. Compaction and branch-deletion cleanup; caps on how much snapshots and transcripts add to the repository.

Fuzzing (see Testing) comes as its own step after milestone 3, covering every parser written so far, and then grows with each new one.
