# mahi — design

> *mahi* (te reo Māori): work.

mahi is a single Rust binary that lets multiple engineers collaborate in real time with **any** terminal coding agent (Claude Code, Codex, Gemini CLI, …), peer-to-peer, with the full history of the work stored encrypted in the project's own git remote.

## Thesis

Review shouldn't be a gate at the end. When every teammate's agent works on everyone's latest work, and teammates watch it happen, design problems are caught at turn 3 instead of in a finished PR. By the time a branch lands, the discussion has already happened; the PR on GitHub/GitLab becomes a quick skim of changes people already saw being made.

## Principles

- **Agent-agnostic.** Wrap the agent's own terminal UI; never require a specific agent or editor.
- **Peer-to-peer.** No mahi server. Realtime traffic goes directly between peers.
- **Git-native.** All durable state lives in git refs on the project's existing remote. The result of a thread is one ordinary remote branch.
- **Private by default.** Rich history (transcripts, agent state) is end-to-end encrypted before it becomes a git object.
- **Sandboxed.** Every agent runs inside an OS-level sandbox, so a teammate's work merged into it acts only within the sandbox's bounds.
- **Fuzzed.** Everything that reads untrusted input is fuzzed as well as unit-tested (see Testing).
- **Use the forge for what it's good at.** Final diff viewing and approval happen in GitHub/GitLab. mahi does not rebuild review tooling.

## Non-goals (decided)

- Signed review attestations / `allowed_signers` trust roots: overhead with little value when repo access already defines the team. May return later as an optional compliance layer built on forge identities.
- Implicit review-coverage tracking: dropped; the forge's PR diff covers the final look.
- Multiple agents editing the same worktree simultaneously.
- Several agents for one person in a thread, and prompts from one person to another's agent (see One agent each, kept in sync).

## Architecture

### Core (agent-independent)

- **PTY wrapper**: launches the agent in a pseudo-terminal, passes it through to the user's terminal, and maintains a virtual screen (`vt100`) for late joiners and crude text snapshots. The pseudo-terminal is opened with `rustix` and the agent is spawned by `mahi-sandbox` itself, not by `portable-pty`, because the sandbox must act between fork and exec on the same spawn. The agent starts with an empty environment plus what mahi passes on, in its own session and process group, and killing it kills the whole group.
- **Sandbox**: the whole agent process runs inside an OS sandbox: namespaces, Landlock and seccomp on Linux (and WSL 2), Seatbelt through `sandbox_init` on macOS. Same pattern as Anthropic's sandbox-runtime (`srt`), implemented natively in Rust with no helper program such as `bwrap`. All `unsafe` code in mahi lives in this one crate. On Linux the agent starts in new user, mount, PID and network namespaces, mapped to the user's own effective uid and gid, with an empty read-only root: the host's programs and libraries (`/usr`, `/etc`, `/bin`, `/sbin`, `/lib*` and `/opt`, where distribution packages install programs, all read-only), and otherwise only the paths its policy binds (read-only, recursively, or read-write), a private `/tmp`, its own `/proc`, and a minimal `/dev` (null, zero, full, random, urandom, tty, `console` as its own terminal, `fd`, a private `devpts` and `/dev/shm`). Each bound path is opened with `openat2` and `RESOLVE_NO_SYMLINKS` after the namespaces exist, so a planted symbolic link cannot redirect a bind, and is cloned with `open_tree` and made read-only with `mount_setattr`, which also covers mounts below it. Mount points are created and reached component by component with `openat2`, so a symbolic link placed in a writable path cannot move a mount elsewhere. Before exec the child locks the securebits (`NOROOT`, `NO_SETUID_FIXUP`), empties the capability bounding and ambient sets, sets `no_new_privs` and marks every inherited descriptor close-on-exec, so the agent holds no capability even when mahi runs as root, and cannot reopen the host through a leaked descriptor. Two small processes watch the agent: one outside the PID namespace, which `mahi` waits on and which passes the agent's exit status up (a signal death arrives as exit code 128 plus the signal), and the namespace's init, which reaps orphans. Both are marked non-dumpable, since they are copies of mahi's memory, and init keeps its capabilities, so the agent can neither trace them nor read their `/proc` entries. The agent leads its own session with the terminal, so terminal keys and a hangup reach it alone, and `kill(0)` cannot reach its watchers. The outer watcher also sees the hangup: if the agent is still running three seconds later, it kills init, so a sandbox does not outlive mahi's terminal by more than that grace period. When the agent exits, init exits and the kernel ends everything left in the namespace, including processes that started their own session; init also dies with the outer watcher. Its network namespace has no route and only loopback up, which init brings up, so the agent reaches nothing outside (DNS fails at once with connection refused) and cannot see the host's sockets in `/proc/net`; outside access goes through mahi's network proxy, whose listening socket is created on this loopback and handed to mahi (see Network proxy). A Unix socket inside any bound path can be connected to, even through a read-only bind, so policies never bind a directory that holds agent sockets (`$XDG_RUNTIME_DIR`, `~/.gnupg`, `/run`): policy is the only guard for sockets at file paths, since neither Landlock nor seccomp can filter `connect` by path. Abstract sockets are already cut off by the network namespace. Init sets `user.max_user_namespaces` to 0 in the sandbox, so the agent cannot create nested user namespaces and gain capabilities over new network or mount namespaces, a common path to kernel exploits. As in OCI runtimes, `/proc/sys`, `/proc/sysrq-trigger`, `/proc/irq`, `/proc/bus`, `/proc/fs` and `/proc/dynamic_debug` are read-only and `kcore`, `keys`, `timer_list`, `vmallocinfo`, `slabinfo` and similar entries are masked, which matters when mahi runs as root. Because of the masks, the agent cannot mount a fresh `/proc` of its own, so nested sandboxes such as `bwrap` or `unshare --mount-proc` do not work inside mahi, and tools that sandbox themselves with a user namespace (Chromium, Electron, Playwright browsers) need their `--no-sandbox` option. `/proc/1/cmdline` shows mahi's arguments, which therefore never carry a secret. On top of the mounts, the agent restricts itself with Landlock before exec, through raw system calls since the rules are built between fork and exec: everything is readable and executable; only the read-write binds, `/tmp` and `/dev/shm` are writable, and no real device node can be created anywhere; files in `/proc` can be written where the kernel allows it (`/proc/sys` stays read-only), since browsers write `oom_score_adj`; and devices under `/dev` and its own terminal can be used, including their `ioctl`s. Rights come from the kernel's highest Landlock ABI, and on ABI 6 abstract Unix sockets and signals are scoped to the sandbox. The sandbox needs ABI 2 (Linux 5.19), because on ABI 1 Landlock forbids moving files between directories; a kernel without it refuses to start the sandbox, with an error that says why, rather than run it weaker. This is defence in depth: a mistake in the mount setup, or a writable mount the policy did not mean outside the read-write binds, still cannot be written through. A read-only bind nested in a read-write one is protected by its mount alone. Last before exec, the agent installs a seccomp filter, written as classic BPF by mahi and built before the fork: it kills the process on a foreign architecture, refuses x32 system calls, and returns `EPERM` for calls a coding agent never needs and that widen the kernel's attack surface (module loading, `kexec`, `bpf`, `perf_event_open`, `userfaultfd`, keyrings, every mount call, `setns`, `clone` and `unshare` with namespace flags, `modify_ldt`, clock and swap changes, `ioperm` and `iopl`, the `TIOCSTI` and `TIOCLINUX` terminal injections, and `AF_VSOCK` sockets, which network namespaces do not confine (vsock namespace modes default to global, and only the host's root can change them) and which reach the hypervisor, its guests or local vsock services, such as Windows under WSL 2). `io_uring` and `clone3` return `ENOSYS`, so runtimes fall back to plain system calls and to `clone`, whose flags the filter can check. Arguments are compared on their low 32 bits, as the kernel truncates them. The Linux sandbox supports little-endian x86_64 and aarch64, and 32-bit programs (i386 or AArch32) are killed. The agent's terminal comes from the host's `devpts` and is bound at `/dev/console`, as containers do, so glibc's `ttyname` finds it there. On Ubuntu, unprivileged user namespaces must be allowed (`kernel.apparmor_restrict_unprivileged_userns=0`). On macOS the agent's process applies a Seatbelt profile with `sandbox_init` just before exec. The profile is written by mahi before the fork, with every path quoted, and bind paths must be canonical (no symbolic link anywhere) since Seatbelt matches resolved paths. It denies by default and allows reading the bound paths and the system (`/usr`, `/bin`, `/sbin`, `/opt` for Homebrew on Apple Silicon and MacPorts, but not their `var` directories, where local databases and service data live, `/System/Library`, the cryptexes, `/private/etc`, the dyld cache, and the developer directory `xcode-select` chose, through its link `/private/var/db/xcode_select_link`, or else the Command Line Tools, since `/usr/bin/git` and the other tools there only start `xcrun`, which loads them from it; for an Xcode app, all of its `Contents` and `/Library/Preferences/com.apple.dt.Xcode.plist`, since `xcrun` then runs the app's `xcodebuild`, which loads the app's frameworks, to check its first launch and license), writing the read-write binds, the usual devices, `ioctl`s on its own terminal (which it inherits open, and cannot reopen), and user lookups through opendirectoryd. A read-only bind inside a read-write one gets explicit write denials, and the directories between them cannot be renamed, since macOS has no mounts to protect it. There is no network access except to the one loopback port of mahi's proxy, and to Unix sockets mahi names (the hook socket): other localhost ports stay closed, since host services such as browser debuggers could run code outside the sandbox, so tests that listen on loopback fail on macOS while they pass on Linux; Unix socket pairs still work. Only an allowlist of system settings can be read through `sysctl` (hardware, OS version, process records by pid, which hold no arguments or environment), and signals reach only the sandbox. One gap remains that no Seatbelt rule closes: the kernel serves `KERN_PROCARGS2` outside Seatbelt's sysctl rules and only checks that the caller runs as the same user (or root), so the agent can read the arguments and the environment every process of the user was started with, mahi's and the user's shells included. Secrets must therefore never be passed in the arguments or environment of any of the user's processes while a macOS agent runs: a token exported in the shell is readable from mahi's own entry and from the shell's. The agent's own credential is exposed only to what it could read anyway, but on macOS it should come from a file that mahi reads (the credential store) rather than from mahi's environment: that keeps it out of mahi's and the shell's environment, though the user's other processes can still read it from the agent's own through the same gap. Closing the gap fully would need the agent to run as its own user. Metadata of every file stays readable, since path lookups need it, so names are visible but contents are not. macOS has no private `/tmp` or process namespace: the caller binds a private temporary directory and sets `TMPDIR`, and a process that leaves the agent's process group survives it, keeping its sandbox. `sandbox_init` compiles the profile, so, unlike on Linux, the child allocates between fork and exec; libSystem's fork resets malloc and dyld in the child and the parent never touches libsandbox, the same pattern as Nix's macOS builder.
- **User namespaces off or restricted**: the Linux sandbox needs unprivileged user namespaces. On Ubuntu 23.10 and later, AppArmor gives a process it does not confine no capabilities in a user namespace it creates (`kernel.apparmor_restrict_unprivileged_userns=1`), so the sandbox fails as it writes its uid map. Before it starts the sandbox, mahi checks for this, from the sysctl and its own AppArmor label being `unconfined`, and refuses with the fix: `mahi apparmor | sudo tee /etc/apparmor.d/usr.bin.mahi && sudo apparmor_parser -r /etc/apparmor.d/usr.bin.mahi` installs a profile for mahi's own path that only allows it to create user namespaces (`userns`) and confines nothing else (`flags=(unconfined)`). The profile and its file are named after that path, as Ubuntu names profiles (`usr.bin.mahi` for `/usr/bin/mahi`, `home.a..cargo.bin.mahi` for a `cargo install`), so two installs never replace each other's, and the message names the file for the mahi that refused; a path with a space or a character AppArmor reads as a pattern gets no profile. The `.deb`, built with `cargo-deb`, installs the same profile for `/usr/bin/mahi` as a conffile in `/etc/apparmor.d/usr.bin.mahi`, loads it when installed and unloads it when removed, and breaks AppArmor before 4.0 (Ubuntu 22.04, Debian 12), whose parser knows neither the `abi/4.0` file nor `userns` and which has no restriction to lift; CI installs it on Ubuntu 24.04 with the restriction on and runs a thread from `/usr/bin/mahi`, and checks that an unprofiled copy is refused with the message. Turning the restriction off for every program (`sysctl kernel.apparmor_restrict_unprivileged_userns=0`) also works, and the message says so as the wider choice. A process labelled `unprivileged_userns`, which AppArmor gives one already inside a restricted namespace, counts as unconfined. The same check refuses, naming the setting, when user namespaces are off altogether (`kernel.unprivileged_userns_clone=0` on Debian kernels, or `user.max_user_namespaces=0`). It refuses WSL 1 first, which it knows by a kernel release ending in `-Microsoft` and which has no user namespaces, asking for the distribution to be converted with `wsl --set-version <distribution> 2`. On WSL 2 (`microsoft` in the release), a kernel without Landlock or with an ABI below 2 is reported with `wsl --update` and the removal of any custom kernel in `.wslconfig` as the fix, since WSL's own kernels from 6.1 on have Landlock with ABI 2 or later (its 5.15 kernel has only ABI 1). Root, or any process with `CAP_SYS_ADMIN`, is exempt from the AppArmor restriction and from `unprivileged_userns_clone`, so the check lets it through; `max_user_namespaces=0` stops it too. There is no weaker fallback without namespaces: Landlock and seccomp alone could give no empty root, private `/proc` or `/tmp`, or network namespace for the proxy to enforce, so mahi refuses rather than run the agent in a sandbox that looks the same and is not.
- **Windows**: mahi runs on Windows through WSL 2 only, as the Linux binary inside a WSL 2 distribution, whose kernel has the namespaces, Landlock and seccomp the sandbox needs. Native Windows is not planned: it has nothing that gives an unprivileged process an empty root, private `/proc` and `/tmp` and a network namespace as the Linux sandbox does. WSL 2 lets Linux programs start Windows programs through interop: a `binfmt_misc` handler for Windows executables runs `/init`, which asks an interop server for the process over a Unix socket under `/run/WSL` (named by `WSL_INTEROP`, or found by its own and its parents' process ids). The sandbox blocks this at two levels. Current WSL registers the handler with the `P` flag only, so the kernel looks `/init` up in the sandbox's root, which has none, and running a Windows executable fails as not found; this is what CI sees. WSL's source also registers it with the `F` flag, which opens `/init` when the handler is registered so that it runs even without one; then no policy binds `/run`, so `/init` finds no server even when the agent names one in `WSL_INTEROP`, and vsock sockets, the Hyper-V channel to Windows, are refused (see Sandbox). Windows drives under `/mnt` are not mounted unless bound. Repositories are best kept in the distribution's own file system rather than under `/mnt/c`, which WSL serves over a slower network file system. CI runs the whole test suite, the git tests and a WSL-only test inside an Ubuntu 24.04 WSL 2 distribution on a Windows runner, in the distribution's own file system: the WSL-only test runs a copy of `cmd.exe` from a shell in a terminal, with `WSL_INTEROP` set and its own input and output piped (interop gives a Windows program attached to a terminal no output there), which must work outside the sandbox and must fail inside it, where the test first checks that the copy is there. Only the `P`-only registration is tested, since that is what the runner has. A read-write bind under `/mnt/c` would still let an agent leave files that Windows programs later run, which is one more reason to keep repositories out of it. Telling WSL 1 from WSL 2 by the kernel release is unit-tested; WSL 1 itself is not run in CI.
- **Network proxy**: the agent reaches the network only through mahi's allowlist proxy, an HTTP `CONNECT` proxy for port 443 that mahi runs on the host. The allowlist is a list of host names and is empty by default: an agent with no profile and no `--allow-host` has no network. mahi never looks inside TLS, so it never sees a credential or a prompt, and it can allow or refuse hosts, not paths. mahi resolves the names itself (the agent has no DNS), connects to the addresses it resolved without a second lookup, and refuses loopback, private, shared, link-local, multicast, reserved and documentation addresses, cloud metadata, IPv6 forms that embed such an IPv4 address (mapped, translated, compatible, NAT64, 6to4), and Teredo and the local-use NAT64 prefix, so an allowed name that resolves into the user's network, or a rebinding trick, reaches nothing. A network whose own NAT64 prefix is not one of these cannot be told apart. Host names are exact DNS names, never IP addresses in any form (dotted, hexadecimal or octal). It refuses plain HTTP, IP literals and other ports, answers `503` past 64 concurrent connections, gives the `CONNECT` request 10 s and all the addresses of a name 10 s together, and closes a tunnel after 5 minutes without traffic either way. The agent gets `HTTPS_PROXY` and `https_proxy`; a program that ignores them has no route at all. On Linux the proxy's listening socket is created inside the agent's network namespace, by the namespace's init right after it brings loopback up, and handed back to mahi over a socket pair made before the fork (`SCM_RIGHTS`): a socket keeps the namespace it was created in, so mahi accepts the agent's loopback connections from the host and no relay process runs in the sandbox. On macOS the proxy listens on the host's loopback, on both `127.0.0.1` and `::1` since Seatbelt's `localhost` covers both and another process must not take the other one, the Seatbelt profile allows connecting to that one port and nothing else on localhost, and the proxy URL carries a random per-run password (`http://mahi:<token>@127.0.0.1:<port>`) that the proxy checks in constant time, since other users' processes can reach the port too. The user's own processes can read the password through the `KERN_PROCARGS2` gap below, as they can read the agent's environment, so it does not keep them out; they can also hold the proxy's connections to deny the agent the network, which only hurts that user.
- **Credentials**: mahi is agent- and LLM-neutral: it knows no provider's authentication and never injects a credential into the agent's traffic. The agent starts with an empty environment plus a fixed list of harmless variables, so nothing from the user's shell reaches it implicitly: an API key exported for other tools never switches an agent from a subscription to per-token billing by accident. Whatever the agent authenticates with reaches it only when named: `mahi run --pass-env NAME` passes one environment variable through unchanged, a profile can declare the same (`pass_env`) or keep a login file in the agent's per-thread state, and the credential store hands the agent a token the user saved, without mahi ever interpreting it. `mahi credential add <name>` reads a token once, hidden from the terminal or piped (`claude setup-token | mahi credential add claude`), and keeps it in `credentials/<name>` in mahi's config directory under the same rules as `identity.pub` (600, a 700 directory owned by the user, written once, opened without following symbolic links); `mahi credential list` shows names only and `mahi credential remove <name>` deletes one. `mahi run --credential <name>=<VARIABLE>` hands a stored token to any agent as that variable, only in the agent's environment, never in mahi's own; a profile can name one too (Claude Code's is `claude`, as `CLAUDE_CODE_OAUTH_TOKEN`), which is used when stored and then wins over the same variable in the user's shell. A named credential that is not stored is an error before any thread exists, and a variable given more than one way (`--credential`, `--pass-env` or the profile) is refused. Injecting a key at the proxy was rejected: it needs each provider's header and TLS interception.
- **Snapshot scheduler**: snapshots of the agent's worktree into hidden refs, taken when the agent's hooks report that a tool ran or a turn ended, and otherwise on a timer that runs every second while the worktree keeps changing and backs off to 30 s while it does not. There is no file-system watcher: a worktree belongs to an agent, and a watcher can be made to follow a swapped-in symbolic link out of the tree, exhaust the user's watch limit, or queue events without bound, all of which were demonstrated against `notify`. The timer is the safety net for changes no hook reports (a background process, a person editing the worktree, an agent without hooks): they show up at the next tick, within a second while the worktree is busy and within 30 s after a long idle spell. Pokes never bring snapshots closer together than one second, except a turn end, which is taken at once at most once a second. With the snapshot cache a tick costs about 10 ms on 5,000 files and 170 ms on 100,000, in a release build.
- **Git storage**: `gix` for objects, refs and worktrees, and for fetch. mahi never runs the `git` program. Push is not in `gix` yet, so mahi implements send-pack itself, over mahi's own SSH client (`mahi-ssh`) and, after the handoff, HTTPS. HTTPS is for networks where only HTTPS gets out, often through a company proxy that SSH, even on port 443, cannot pass, so it goes through the proxy `HTTPS_PROXY` names (HTTP `CONNECT`) from the start; its token comes from the credential store, for the host it was stored for only. A machine with a token but no SSH key is not a case for it: mahi signs every agent commit through ssh-agent.
- **SSH transport** (`mahi-ssh`): SSH remotes come first, since most developers already have one and a key in ssh-agent, so there is nothing to set up. mahi has its own SSH client. The Rust SSH libraries either bind C (`ssh2`, `thrussh`'s libsodium, `ring` and `aws-lc-rs` under `russh`'s ciphers) or are no longer maintained, and `russh` would not take a pure-Rust cipher backend, so `russh` is not used, and mahi needs no `[patch]`. `age` stays at 0.11 until an `age` release moves to `ml-kem` 0.3, the version mahi's key exchange uses, since `age` 0.12's `ml-kem` 0.2 cannot share the `kem` crate with it. The client is small because mahi needs only a small part of SSH: a client, one connection per remote, public-key login through ssh-agent and `exec` channels. The protocol is written without I/O (bytes in, bytes and events out) so that tests, property tests and fuzz targets drive it directly, and a thin tokio driver connects it to the socket. The primitives come from RustCrypto and dalek (`x25519-dalek`, `ml-kem`, `ed25519-dalek`, `p256`, `p384`, `sha2`, `chacha20`, `poly1305`, `aes-gcm`); mahi writes no primitive itself.
  - **Algorithms.** Only modern algorithms, with no fallback to old ones. Key exchange: `mlkem768x25519-sha256` (post-quantum hybrid, first) and `curve25519-sha256` (also as `curve25519-sha256@libssh.org`). Host keys: `ssh-ed25519`, `ecdsa-sha2-nistp256` and `ecdsa-sha2-nistp384`; no RSA, no DSA and no certificates. Ciphers: `chacha20-poly1305@openssh.com`, `aes256-gcm@openssh.com` and `aes128-gcm@openssh.com`, all AEAD, so there is no separate MAC: as in OpenSSH, MACs are not negotiated when the chosen cipher is AEAD, and the MAC list names `hmac-sha2-256-etm@openssh.com` only because the protocol needs a non-empty list. No compression. GitHub, GitLab and Bitbucket all offer `curve25519-sha256`, `ssh-ed25519`, `chacha20-poly1305@openssh.com` and strict key exchange (checked 2026-10-01); GitLab and Bitbucket also offer `mlkem768x25519-sha256`, while GitHub's post-quantum exchange is `sntrup761x25519-sha512`, which mahi does not implement. OpenSSH has offered all of them since 9.9.
  - **Strict key exchange is required** (`kex-strict-c-v00@openssh.com`, the fix for the Terrapin attack, CVE-2023-48795): a server that does not offer `kex-strict-s-v00@openssh.com` is refused with an error that names it. Only the markers in the first `KEXINIT` of each side count; later ones are ignored. The server's `KEXINIT` must be the first packet mahi receives, during the first key exchange any message other than the key exchange's own ends the connection, and the sequence numbers start again from 0 after each `NEWKEYS`.
  - **Bounds.** The server's identification line is at most 255 bytes, and at most 32 other lines (8 KiB) may come before it. A packet is at most 256 KiB, as in OpenSSH, and mahi reads nothing more while 1 MiB of its own output waits to be written, and its length must be a whole number of cipher blocks; the length is checked before anything is allocated for it. Padding is 4 to 255 bytes; mahi sends zeros, as the padding is encrypted and authenticated under a nonce used once, so random bytes would hide nothing more. A name list is at most 64 KiB and a name 64 bytes. A banner from the server during login is discarded, never shown. The connection is rekeyed after 1 GiB in either direction, after 2^28 packets or after an hour, and accepts a rekey the server starts at any time. mahi starts no rekey before it has logged in, since OpenSSH refuses one then; a sequence number that would wrap before a rekey ends the connection.
  - **Key exchange checks.** The server's X25519 key must be 32 bytes and the shared secret must not be all zeros; the ML-KEM ciphertext must be 1088 bytes. The exchange hash covers both `KEXINIT` payloads as they were sent and received. It is signed by a host key of the negotiated type, whose encoding must be canonical, and the signature is checked, and the key accepted from `known_hosts`, before `NEWKEYS` is sent; a rekey must present the same host key. A server that sets `first_kex_packet_follows` is refused, since in these exchanges the client speaks first and a guess has no use. Ephemeral secrets, the shared secret and the session keys are zeroized when they are no longer needed, and appear in no `Debug` output or error.
  - **Login.** mahi asks the server whether it accepts each key before it asks ssh-agent to sign, so the agent signs (and, for a key added with confirmation, asks the user) only for a key the server accepts. It tries at most 6 plain keys, in the agent's order, since OpenSSH's server stops after 6 tries; certificates and RSA keys are skipped, and a key the agent will not sign with is passed over. The signature is checked against the key before it is sent.
  - **Channels.** Only channels mahi opens exist: a channel the server tries to open is refused, and a global request that wants an answer gets a failure. mahi offers a 2 MiB window and 32 KiB packets and tops the window up when half of it is used; it never sends more than the server's window or packet size allows, and data beyond the window it offered, data for a channel that is closed or unknown, or a second `CLOSE` ends the connection. Several channels may run at once on one connection.
  - **Driver.** Reading, writing and the timers run on one tokio task per connection. Keepalives are `keepalive@openssh.com` global requests, 15 s apart, and four unanswered ones close the connection.
  - **Remotes, host keys and commands.** mahi reads the remote URL itself (`ssh://[user@]host[:port]/path` and git's `[user@]host:path`), refuses a host, user or path that starts with `-`, a host that is not a DNS name or an IPv6 address, a user with a space, a colon (a password), a control character or an invisible one (`mahi_core::is_invisible`) and a path with a control or invisible character (so a path with a zero-width joiner, as in some emoji and scripts, is refused), and quotes the path for the remote shell as git does. Unlike git it does not percent-decode `ssh://` URLs. It does not read `~/.ssh/config`, so a host alias defined there is not resolved. The host key is checked against the user's `~/.ssh/known_hosts` and the system's `ssh_known_hosts` with mahi's own reader: plain, bracketed `[host]:port`, hashed and wildcard names, negated patterns and `@revoked` keys (a revoked key is refused even when another line lists it). `@cert-authority` lines are skipped and host certificates refused. Only key types `known_hosts` lists for the host are offered, so a server cannot switch to a type the user never saw; with no entry for the host every type is offered and the key is then refused as unknown. RSA host keys are not supported, since verifying them would bring back the `rsa` crate, and a host `known_hosts` lists only with RSA keys is reported as such (GitHub, GitLab and Bitbucket all have ed25519 keys). An unknown, changed or revoked key stops the connection before logging in, with its SHA-256 fingerprint; mahi never adds keys to `known_hosts`. Connecting and logging in must finish within 20 s, and so must starting a command; what the host sends before saying it runs the command is kept, up to 64 KiB. Fetching runs `git-upload-pack` on the session as gix's transport, and mahi's own send-pack will run `git-receive-pack` the same way; both ask for protocol version 2 through `GIT_PROTOCOL` (a host that does not take the variable answers with version 1). A command fails when it exits with another status than 0, is ended by a signal, or the connection ends before it closes its channel. What it writes to its error stream is kept, up to 4 KiB, and shown when it fails, each line marked `remote:`, with control and invisible formatting characters (such as bidirectional overrides) replaced so it can neither drive the terminal nor disguise itself. Reading or writing that makes no progress for 5 minutes ends the transfer. gix's network client is built for its protocol code only: it can also run `ssh` and credential helpers, so mahi never lets gix open a connection itself and always hands it this transport. The tests that run the real `git upload-pack` and `git receive-pack` through OpenSSH's `sshd` run with `just test-git`.
- **HTTPS transport** (`mahi-http`): for networks where only HTTPS gets out. gix speaks git's smart HTTP protocol through its `Http` trait, over `ureq` (blocking HTTP/1.1) with rustls and `mahi-tls` as the crypto provider, and the Web PKI's roots; no curl, no reqwest. Requests go through the proxy `HTTPS_PROXY` names (an `http://` proxy, with HTTP `CONNECT`; `NO_PROXY` lists hosts, and their subdomains, reached directly, or `*` for all). Only `https://` remotes are used, and never with a password in the URL. No redirect is followed, so a token only ever reaches the remote's own host; a remote that moved says so. The token is sent with Basic authentication, as `user:token` when stored that way, else with the URL's user or `x-access-token`; a user in the URL, where some write a token, is kept out of the URL gix sees and reports. A refused request (401, 403) names `mahi credential add`. Connecting, through the proxy and TLS, waits at most 20 s, a response's headers at most 60 s after the request was sent, and any single wait to send or receive at most 5 minutes, so a server or proxy that stops making progress fails the transfer. `NO_PROXY` takes host names and IP addresses, IPv6 ones bare or in brackets, not address ranges. Server certificates are checked against the Web PKI only, so a company proxy that intercepts TLS with its own authority is not supported yet.
- **Live layer**: iroh (QUIC, hole punching, relay fallback) + iroh-gossip, one topic per thread. iroh's TLS runs on `mahi-tls`, a rustls crypto provider built on the RustCrypto implementations (TLS 1.3 only: AES-GCM, ChaCha20-Poly1305, X25519, QUIC packet and header protection, and ECDSA, RSA and Ed25519 signature checks for relay certificates; RSA is only ever used to verify, which keeps it clear of the Marvin timing attack on private keys), because the providers iroh offers, `ring` and `aws-lc-rs`, build C code. It is checked against the RFC 9001 test vectors.
- **Shared state**: a CRDT (Automerge or Loro) for multi-writer data: human chat, claims, comments.
- **MCP server**: exposes the thread to every agent (list agents, read others' transcripts/diffs, merge a branch, claim a file/task).

### Adapters (agent-specific)

mahi is agent-agnostic: any terminal agent runs in it, and how fully mahi supports one depends on what it knows about it. That knowledge is the agent's adapter: how to launch it (program, arguments, variables, credential), what its sandbox must allow (hosts) and where its per-thread state lives, how its hooks report prompts, tool calls, turn ends and its own questions to mahi (`mahi hook prompt|tool|turn-end|asks`), how to read what it did, and how to resume it. mahi starts no program but the agent, so an adapter is never a program of its own: it is a profile, which is data (built in, or written by the user in TOML), and, for reading the agent's own sessions, a reader, which is code built into mahi.

Support is a gradient:

1. **No profile** (`mahi run --no-profile`, or an agent mahi has no profile for): the sandbox, the live terminal view and the snapshots, taken on a timer. Nothing reports the agent's turns, unless its own configuration runs `mahi hook` (every agent gets `MAHI_BIN` and the hook socket), so none are recorded, and the agent counts as idle after 2 s of quiet.
2. **A profile**: the agent's hosts, variables, credential, state directory and resume arguments, and the files that wire its hooks and `mahi mcp`. mahi ships two profiles built in, chosen by the agent program's file name: `claude-code` for `claude` and `codex` for `codex`; users write their own as TOML files (format below), and one for the same program replaces the built-in one. A profile adds its hosts to `--allow-host`, passes its variables only when they are set (a missing one is not an error, since the agent may sign in another way), sets its quiet settings, and prepares the agent's state directory, `<common git dir>/mahi/state/<thread-id>/<participant>.<agent>`: private to the user, bound read-write, kept after the run for `mahi resume`, and removed with a thread discarded before its agent ran. The state directory holds what the agent keeps in plaintext, such as Claude Code's own transcripts and a `/login` credential, until `mahi end` removes it. Resume must reopen it without following symbolic links, since on macOS the agent can replace the directory itself with a link, and must replace the files it writes there by writing a new file and renaming it, never by following an existing one. With hooks, mahi snapshots after each tool call and turn, records each turn as the events its hooks sent, and knows when a turn ends. mahi reads hook payloads in the shape Claude Code's share, which Codex documents too (a prompt's `prompt`, a tool call's `tool_name` and `tool_input`), for any agent: a payload that is not JSON is shown as text, and a prompt without one as a note; whatever is shown leaves out control and invisible characters.
3. **A profile and a reader**: mahi also reads the agent's own sessions, so a handoff briefing and a pull request draft can quote its replies, and a thread resumed on another machine restores its session. A reader is code in `mahi-agent`, fuzzed like every parser of untrusted input, chosen by the profile's `reader`. mahi has one for Claude Code (`claude-code`) and one for Codex (`codex`). Readers are added for the agents people use, rather than through a plugin interface, since each agent keeps its sessions in its own form.

Notes for Codex: its built-in profile gives each thread its own `CODEX_HOME`, where mahi writes `hooks.json` before each launch, and passes the rest as `-c` overrides on its command line, which win over the top level of the `config.toml` there: Codex's own sandbox off (`sandbox_mode = "danger-full-access"`, the mode Codex documents for an agent already isolated, since its bubblewrap or Seatbelt sandbox cannot nest inside mahi's), its sign-in kept in a file in `CODEX_HOME` (never the system keyring, which the sandbox does not reach), no update check or analytics, and, when mahi serves tools, `mahi mcp` as an MCP server whose tools need no approval. It may reach `api.openai.com`, `chatgpt.com` and `auth.openai.com`. Codex's terminal app reads no API key from the environment, so the profile hands it no credential: the user signs in from Codex's own screen once per thread, with a ChatGPT device code (its browser sign-in waits on localhost, which the sandbox keeps apart; ChatGPT allows device codes for Codex only once the user turns them on in its security settings) or an API key. Codex runs a hook only once the user has approved it, and records each approval in its `config.toml` as a hash of the hook under a key naming the `hooks.json` it is in. So the user approves mahi's three hooks once: when a Codex run ends, mahi keeps the hashes Codex recorded for them in `codex-hooks.toml` in its configuration directory, and before each launch adds them, under the new thread's key, to the thread's `config.toml`, leaving any record already there as it is. A hash only trusts the exact hook it was made for, so a planted one gains nothing, and when a Codex release hashes hooks differently it asks once more and mahi keeps the new approval. mahi never passes `--dangerously-bypass-hook-trust`, which would also skip the review of a repository's own hooks. Tested end to end with Codex 0.160.1 and a ChatGPT login: model requests through mahi's proxy, the hook review, recorded turns and snapshots, `mahi mcp`'s tools, and resume all work. `mahi resume` runs `codex resume --last --all`, `--all` because Codex otherwise keeps to sessions started in the same directory, and the thread's `CODEX_HOME` holds only its own. The user's own `--sandbox`, `--full-auto` or `--profile` (or a profile the agent selects in its `config.toml`) still win over the override and turn Codex's sandbox back on, which fails inside mahi's. Codex runs hook commands with the user's login shell (`$SHELL -lc`), so `"$MAHI_BIN" hook …` needs a shell that expands it, such as sh, bash, zsh or fish, and a login script that prints nothing; `mahi hook` itself writes nothing to standard output. A Codex installed under `/usr` or `/opt` (a system package, or Homebrew) runs as is; one installed with npm under the user's home starts a native binary from elsewhere in its package, which the sandbox does not mount (not yet tested).

Turns are recorded as the agents' hooks send them, and read when they are shown, so a newer reader also reads older turns. Today they are read into text: what was asked, which tools ran on what, and, through a reader, what was replied. The planned model for a structured shape is the ACP (Agent Client Protocol) session-update schema, once a second reader shows what agents have in common.

mahi merges teammates' work into the agent (see Sync) only when the agent is idle: no turn is open (a `prompt` hook opens one, and its `turn-end` hook, or the user's Ctrl-C or Escape, ends it); the user's own input line is empty; mahi's palette is closed; and nothing was written or typed for 2 s.

A user-written profile is a TOML file in `profiles/` in mahi's configuration directory, parsed in `mahi-agent`, which checks everything before mahi uses it. mahi reads them only for the commands that run an agent or read its sessions (`run`, `resume`, `handoff`, `agent add`, `join` with an agent, and `land`), and never from a repository, so a project cannot widen what its agent reaches: the directory and each file must be the user's own and writable by no one else, and are read without following links; files not ending in `.toml`, and hidden ones such as an editor's lock files, are ignored; an invalid profile stops the command and names its file; two profiles for the same program, or with the same name, are refused; a variable mahi reserves or already passes on (such as `PATH` or the proxy variables) cannot be set or passed by one; and a profile for a program a built-in profile covers replaces that profile whole, so it must restate what the built-in one gives the agent. mahi says at start which profile it uses, and from which file:

```toml
name = "my-agent"                     # the profile's name: a-z, 0-9 and -, at most 32
program = "my-agent"                  # the file name of the agent program it applies to
hosts = ["api.example.com"]           # added to --allow-host
pass-env = ["EXAMPLE_API_KEY"]        # passed on only when set
env = { MY_AGENT_NO_UPDATE = "1" }    # set for the agent
state-env = "MY_AGENT_HOME"           # given the agent's state directory
resume-args = ["--continue"]          # what `mahi resume` runs the program with
args = ["--no-telemetry"]             # added after the user's arguments, before any `--`
credential = { name = "example", variable = "EXAMPLE_TOKEN", hint = "make a token at example.com/settings" }
first-prompt-arg = false              # a handoff's first prompt goes last, after `--`

[tools]                               # added after `args` when mahi serves tools
args = ["--mcp-config", "{state_dir}/mcp.json"]

[[file]]                              # written into the state directory
path = "mcp.json"
when = "tools"                        # "always" (default) or only when tools are served
write = "replace"                     # "replace" (default) or "create" when missing
content = '''{"mcpServers": {"mahi": {"command": "{mahi_bin}", "args": ["mcp"],
  "env": {"MAHI_MCP_SOCKET": "{mcp_socket}"}}}}'''
```

Only `name` and `program` are required, and unknown fields are refused. `resume-args` replace the arguments after the program when `mahi resume` is given no command, with no session id: they ask the agent to continue its latest session, which lives in the thread's own state directory. `reader` names one of mahi's built-in readers, `claude-code` or `codex`, for where the agent keeps its sessions, which of its files are session logs and how their lines read, so a profile that replaces the built-in one for `claude` or `codex` keeps its sessions. `args` and then tool arguments go after the user's arguments and before the user's `--`, and a first prompt after all of them. Files, `{state_dir}` and a `reader` need a `state-env`. A file's path is relative to the state directory, at most 8 components of at most 200 bytes, each made of ASCII letters, digits and `._-+@`, never `.` or `..`, nor of the form `.<name>.mahi`, which mahi's writer uses for its temporary files; no two paths may be the same once ASCII case is folded, nor one a directory of another. A template holds text and `{state_dir}`, `{mahi_bin}` or `{mcp_socket}`, the last two only where tools are served, and `{{` and `}}` for braces; values are inserted as they are, so mahi refuses to write a file or an argument when a value holds a quote, a backslash or a control character, which could change what the agent reads: a file it cannot write stops the agent's start, and tool arguments it cannot fill in are left out, with the agent's tools off. Limits: a file of at most 64 KiB, 32 hosts, variables, resume arguments and arguments, 16 tool arguments and 16 files, values of at most 4 KiB. A variable may be named only once across `pass-env`, `env`, `state-env` and the credential.

Notes for Claude Code: a per-thread `CLAUDE_CONFIG_DIR` lets mahi inject hooks without touching the user's global config, and tells it exactly where transcripts land. Before each run mahi empties `sessions/` in that directory, for any profile that reads Claude Code's logs: Claude Code lists its running sessions there by process id, and those of an earlier run ended with its sandbox's PID namespace, where Claude Code cannot see that they ended, so `--continue` would take their conversation for one still running elsewhere and find none to continue; the agent's lock means no other run uses that directory meanwhile. When it cannot empty it, mahi says so and runs the agent anyway. Its credential decides who pays: `ANTHROPIC_API_KEY` bills per token to a Console account, `ANTHROPIC_AUTH_TOKEN` is a bearer token for a gateway, and both win over a subscription (only cloud-provider settings rank higher), while `CLAUDE_CODE_OAUTH_TOKEN`, the one-year token `claude setup-token` prints, uses the user's Pro, Max, Team or Enterprise plan and can only make model requests. The profile therefore passes only `CLAUDE_CODE_OAUTH_TOKEN`, from the stored `claude` credential when there is one (`claude setup-token | mahi credential add claude`), otherwise from mahi's environment, where on macOS the user's other processes can read it. A login from `/login` lives in `.credentials.json` under `CLAUDE_CONFIG_DIR` (on macOS in a Keychain entry keyed to that directory, which Seatbelt blocks), so a per-thread config dir would need a login per thread; the token avoids that. The built-in profile allows only `api.anthropic.com`, which model requests with the token need, and sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (telemetry, error reports, auto-update), `DISABLE_AUTOUPDATER=1` and `ENABLE_CLAUDEAI_MCP_SERVERS=false`, so Claude Code does not reach its other hosts. Signing in with `/login` inside the sandbox also needs `platform.claude.com` (and `claude.ai`), which `--allow-host` adds. Its `settings.json` in `CLAUDE_CONFIG_DIR` sends `UserPromptSubmit`, `PostToolUse` and `Stop` to `$MAHI_BIN hook prompt`, `tool` and `turn-end`, and `Notification`, matched to `permission_prompt|elicitation_dialog`, to `$MAHI_BIN hook asks`; mahi also reads the payload's `notification_type` and takes only those two, so its reminder that it waits for input (`idle_prompt`) never counts as a question. A question is not kept in the transcript. A fresh config directory would start Claude Code's onboarding (theme picker and a connectivity check against `platform.claude.com`) in every thread, and each thread's new worktree would ask whether to trust its folder, so the profile writes `.claude.json` with `hasCompletedOnboarding`, and the thread's worktree marked trusted (`projects.<worktree>.hasTrustDialogAccepted`; the sandbox already confines the agent to it, and the user's own `~/.claude.json` is never touched), once, when it is missing, and never overwrites what Claude Code keeps there (checked with Claude Code 2.1.281). Trusting the worktree lets the repository's own `.claude` settings and hooks run without a question, inside the sandbox and behind the proxy, as accepting the question did (declining it ended Claude Code, so it was never a real choice); the project's MCP servers in `.mcp.json` still ask. A teammate's snapshot taken by a handoff or merged into a landing worktree can bring `.claude/settings.json` along, which could turn off mahi's hooks for that agent; it stays inside the sandbox all the same. Tested end to end with a real subscription token: `/status` shows `CLAUDE_CODE_OAUTH_TOKEN` as the credential and mahi's proxy, and model requests, hooks, snapshots and transcript turns all work. Claude Code refuses to edit files under a `.git` directory without asking, even with `acceptEdits` or explicitly allowed tools, so a worktree inside the git directory does not work with it. Hooks run inside the sandbox, so the hook handler (`mahi hook`) talks to the host binary over a bind-mounted Unix socket. Hook handlers must never block or fail the agent: log and exit 0.

## Storage layout

```
refs/threads/<id>/meta                              # title, base, participants, wrapped keys, landing branch
refs/threads/<id>/state                             # CRDT blob (encrypted)
refs/threads/<id>/agents/<participant>.<agent>/snapshots   # one commit per edit (worktree trees)
refs/threads/<id>/agents/<participant>.<agent>/transcript  # one commit per agent turn (encrypted)
refs/threads/<id>/agents/<participant>.<agent>/session     # native agent session files (encrypted)
```

- Each author only writes their own refs, so the layout is append-only and conflict-free.
- Agents live under `agents/`, named `<participant>.<agent>`, so an agent can never be called `meta` or `state`, and two people can run the same agent in one thread.
- Thread refs are pushed to the project's remote (the durable backing store) after every turn. They are not in the default refspec, so normal clones never see them.
- Fetching a thread brings its remote refs into a local waiting area, `refs/mahi/fetched/<id>/…`, which mirrors the remote (what an earlier fetch left there is removed first); thread refs are never written by the fetch itself. They are then accepted, `meta` first: the fetched document must be the thread's and signed by the owner key the reader trusts. A newer generation than the local one, or the same document, becomes the local `meta`, moved under the pin's lock with the pin written only once the ref moved; the pin refuses another document of a generation already seen, and an older fetched document leaves the local one in place. The check rests on the signed documents, not on commit ancestry, since a joiner's `meta` (recorded from the host) never shares commits with the owner's; only the tip document is read. If the document is refused, the fetch is refused and reported and no ref moves, so a remote cannot swap `meta`. Then each ref under `agents/` moves only forward (behind moves to the fetched commit, ahead stays, a history that went apart stays and is reported), and only for a participant the resulting `meta` lists, other than the reader: the reader's own agent refs are never moved by a fetch, so no one with push access can put files or transcript turns into them (continuing one's own agent from another machine takes them explicitly, see `mahi resume --take-remote` below), and refs of names `meta` does not list are skipped. `state` is skipped until its writers are settled. A ref that fails its checks (not a commit, a merge, a broken history) is refused on its own and the others go on. A fetch with more than 4096 refs is refused, and all the history walks of one acceptance go through at most 2^20 commits together; past that the remaining refs are refused. Someone with push access can so keep a thread from syncing, as they can by pushing a broken `meta`, but cannot move a ref. How much a fetch reads from the remote is bounded by `fetch-limit` (see Compaction and cleanup).
- Nothing is pushed until the user chooses a remote for the clone: `mahi remote <name> --private` or `--public` keeps the choice in the git directory (`mahi/sync/remote`, a private file), `mahi remote` shows it and `mahi remote --off` stops pushing. The remote must exist in the repository's git configuration with an SSH or `https://` push URL (its `pushurl`, or else its `url`, after git's `insteadOf` and `pushInsteadOf` rewriting); an HTTPS remote's token is the credential named `https-` and its host in lowercase with each `-` doubled and each `.` turned into `-`, then `---` and the port unless it is 443 (`mahi credential add https-github-com`; `mahi remote` names it), so no two hosts share a token and none is an agent's; a remote with no such credential, or whose host is not a plain DNS name or IPv4 address, is reached without one (`HTTPS_PROXY` and `NO_PROXY`, or their lowercase forms, which come first, name the proxy); remote names are ASCII letters, digits, `-`, `.` and `_`. An error about a remote names it, never its URL, which may hold a token. On a remote marked public, the agents' snapshots, which are not encrypted, stay local until encrypted snapshot bundles exist; `meta` and the encrypted transcripts are pushed. Fetching needs no choice: `mahi resume`, and `mahi join -- <agent>` once the host's `meta` is recorded, fetch the thread from the chosen remote, at the URL it pushes to since that is where the threads go, or else from `origin` when it fetches over SSH or HTTPS (quietly skipped otherwise; fetching from `origin` cannot be turned off, and it only ever reads), and accept what checks out (see above) as the participant `meta` lists with the user's key, or node for a joiner, never as the name `USER` gives, so the user's own refs are never moved by it, unless they ask: `mahi resume --take-remote` takes the thread's lock, checks ssh-agent, and fetches before it looks for the user's agent, taking the user's own agents' refs too, forward only and only commits their key signed, as another machine of theirs pushed them. It resumes a thread on a clone that does not have it yet, for a thread the user owns; a joined thread needs its owner remembered, which only its ticket gives. It is refused while the clone has a worktree for the thread, whose files would otherwise be recorded over what was taken; `mahi end` records and removes it first. Each ref is taken on its own, so a snapshot history and a transcript that went apart differently can be resumed together, and nothing stops the same agent from running on two machines at once, whose histories then go apart for good. Since signatures do not name the thread, whoever can push to the remote can also put the user's own signed snapshots of another thread into a clone that has none of the thread's. They then use the `meta` the fetch may have brought. A remote without the thread changes nothing; a fetch says so before it connects, and one that fails is reported, with what the remote said escaped and cut short, and the command goes on with what the clone has. A stop signal during the fetch stops it within about 100 ms over SSH, connecting or transferring alike (a host name still being resolved is left behind rather than waited for), and over HTTPS once the request in flight answers or its wait runs out, and ends the command; nothing is accepted unless accepting had already begun, which then finishes. A second signal ends mahi at once; since each ref move and pin write is atomic, at worst a stale lock file is left behind. If stop signals cannot be listened to, the fetch runs without them. Watching with `mahi join` fetches nothing, since history is not shown yet. Once a remote is chosen, `mahi run`, `mahi resume` and `mahi join -- <agent>` push in the background after each turn the agent ends, a burst of turns being one push, and once more after the agent stops and its last snapshot is taken: the agent's transcript and session refs, its snapshots on a private remote, and `meta` when the user owns the thread (a joiner's `meta` is the owner's to push). A push never holds up the agent. A remote that cannot be used (no ssh-agent for an SSH remote, a plain `http://` one, an unusable proxy) is reported when the run starts and nothing is pushed; what the last push did is told when the run ends, including refs another clone moved on the remote, which are not pushed over. A stop signal while the last push runs stops it within about 100 ms over SSH, even while connecting to or waiting on a remote that has stopped answering; over HTTPS it stops once the request in flight answers or its wait runs out (20 s to connect, 60 s for a response's headers, 5 minutes without progress), so the run may take that long to end unless a second signal ends mahi at once. A push stopped before its pack is fully sent moves no remote ref; one stopped while the remote applies it may still have moved them. A second signal ends mahi at once. The remote and its visibility are read when the run starts; choosing another with `mahi remote` takes effect at the next run.
- Pushing is mahi's own send-pack, since gix has none. It runs `git-receive-pack` (protocol version 0, since version 2 has no push), reads the refs the remote advertises, and sends each ref only as a fast-forward of what the remote has: a ref the remote moved to a commit the local one does not descend from, or that is not here, is left alone and reported, to be fetched first. The updates ask for `report-status`, and for `atomic` when the remote offers it, so either every ref sent moves or none does. The pack holds the new commits and the objects of their trees that are not in the trees of the remote's `HEAD` and of the thread's refs the remote advertised, when this repository has those commits; compressed objects and deltas are copied from local packs, never thin, so the remote must offer `ofs-delta`, as git does. Of the advertisement, mahi keeps only those tips (at most 65536 lines are read), and of the report only the lines for refs it sent, with the remote's reasons escaped and cut to 200 characters. What the remote refuses is reported per ref, a ref whose local history cannot be checked is reported on its own, and a pack the remote cannot unpack fails the push. An interrupted push sends nothing, or a pack cut short, so no remote ref moves. How much a push sends is bounded by `push-limit`: it sends the refs that fit, and the rest wait (see Compaction and cleanup). The landing branch is pushed the same way, to the branch of the same name, but its history may hold merges: it moves when its tip reaches the remote's through any parent, found by walking newest commit first no lower than a day before the remote's tip was committed (a history dated more out of order than that is reported as behind and not pushed), and the pack holds the commits it reaches that the remote's branches, tags and `HEAD` do not, walked newest first only while one of them is left and down to a day below the oldest, so the shared history is not walked to its root, and the objects of their trees not in the trees of the parents just below them. Each walk stops at a million commits and on a stop signal.
- Thread IDs are random, and thread commits use a generic committer identity, to limit metadata leakage.
- Agent commits (snapshots, transcript turns and session state) are signed by their participant's SSH key through ssh-agent, the way git signs commits with SSH: a `gpgsig` header holding an SSHSIG signature in the `git` namespace, SHA-512, over the commit without that header, so `git verify-commit` with an allowed-signers file checks them too. A fetched agent ref only moves when every commit it adds is signed by the key the signed `meta` lists for its participant, which binds a participant's agents to them; a ref that adds a commit anyone else signed, or no one did, is refused on its own and reported. A signature names the participant, not the thread or the ref, so whoever can push to the remote can still point a participant's ref at other commits that participant signed, such as another thread's snapshots; and since a participant's key cannot change yet, a new key would make their earlier commits unacceptable to a clone that has none of them. So `mahi run`, `mahi resume`, `mahi join -- <agent>` and `mahi end` need ssh-agent holding the signing key, and check that it lists the key before they fetch, ask for the passphrase or start the agent; `mahi resume` and `mahi join -- <agent>` also refuse when `meta` does not list the user with that key (under the name `USER` gives, for `resume`), since what they signed would then be refused by everyone else. If ssh-agent stops signing during a run, the first snapshot and the first turn that fail are reported when the run ends, with the count of agent events the lost turns held. A signature ssh-agent is still making is waited for, up to its 60-second timeout, before a stop signal takes effect; a key that asks for confirmation (`ssh-add -c`) would ask at every snapshot and turn, so it is not suited to mahi. `meta` needs no commit signature, since its document is signed.

## Encryption

- Encrypt at write time, before content becomes a git object: serialize → LZ4 → encrypt → write blob. The encrypted payload is the plaintext length (`u32`, little-endian) followed by one LZ4 block, so a reader checks the length against its limit before allocating, and a hostile blob cannot expand without bound. (zstd was the first choice; the only pure-Rust decoder, `ruzstd`, does not bound how much one block expands to.)
- Each participant has two keys. Their SSH ed25519 key ties them to their forge identity and signs (the owner signs `meta` with it, through ssh-agent, so no prompt). Their mahi key, an age X25519 identity, is what thread keys are wrapped to: ssh-agent can sign but not decrypt, so decrypting with the SSH key would need its passphrase every time, and a separate key also keeps a stolen SSH key from opening every thread.
- The mahi key lives in `identity.age` in the user's config directory (`~/Library/Application Support/mahi` on macOS, `$XDG_CONFIG_HOME/mahi` or `~/.config/mahi` elsewhere), encrypted with a passphrase (age scrypt, work factor 18; files asking for more than 19 are refused, which caps scrypt at 512 MiB). It is written to a temporary file and hard-linked into place, so it is either complete or absent and never overwritten. The file (600) and its directory (700) must be owned by the user, and a file others can read, or a directory others can write, is refused. The one exception is the config directory itself: release installers create it for their receipt with the user's umask, which leaves it writable by the user's group on Ubuntu, so each mahi command first opens it without following links and, when it is the user's own and its group or others may write to it, resets it to 700 through that descriptor and says so. Each file in it is still checked on its own, so a file someone else put there is refused. It works the same on Linux and macOS, with or without a desktop keyring.
- `mahi init` creates the mahi key, then writes two public files beside `identity.age`: `identity.pub` (the mahi key's age recipient) and `signing-key.pub` (the ed25519 SSH key that signs `meta`, chosen from the keys ssh-agent lists, without its comment). `mahi run` reads only these, so starting a thread never asks for the passphrase; it is asked when a thread key must be unwrapped, as on resume, which also checks that `identity.pub` belongs to `identity.age`; until then a replaced `identity.pub` would only show there, which is why its file rules matter. `mahi init` refuses an `identity.pub` left without `identity.age`, which would wrap thread keys to a key nobody holds. Both files are written once, never overwritten, and held to the same rules as `identity.age` (600, in a 700 directory, owned by the user, opened without following symbolic links): their content is public, but whoever could replace them could make new threads trust their key.
- SSH keys other than ed25519 are refused, `ssh-rsa` included. Since thread keys are wrapped to mahi keys, not SSH keys, mahi does not build `age`'s SSH support at all, and with it the `rsa` crate and its unfixed timing advisory (RUSTSEC-2023-0071) are gone.
- `age` (Rust `age` crate): each thread has its own age X25519 identity, the thread key. Content is encrypted to the thread key's recipient. The thread key's secret is itself encrypted to each participant's mahi key and stored in `meta`. Adding a participant wraps the existing thread key once more; nothing else is re-encrypted.
- Always encrypted: transcripts, native session files, screen captures.
- Code snapshots: plaintext, which keeps dedup and diffs, so they are pushed only to a remote the user declared private (`mahi remote <name> --private`); on a remote declared public they stay in the local repository, and only the encrypted records are pushed. Visibility is never guessed: nothing is pushed until the user chooses a remote and says which it is.
- Authorship comes from signatures, not encryption: anyone who has a thread's public recipient can seal content to it, but every agent commit (snapshots, transcript turns, sessions) is signed with its participant's SSH key, and a fetch accepts only commits signed by the key `meta` lists for that participant, so no one can write in another's name.
- Removing a participant rotates the thread key for future content: a new thread identity, wrapped for the remaining participants. Content written before the removal stays readable to the removed participant.
- Optional team recovery recipient (an offline key).

### The `meta` document

- Encoded with `postcard`, in a versioned envelope: `{ version, body, signature }`.
- The body holds, in plain text: the thread ID, the base commit, the owner's name, the thread recipient, and each participant's name, SSH ed25519 public key, mahi key (age X25519 recipient), iroh node key and the thread key wrapped to that mahi key. The title and the landing branch are sealed to the thread key.
- The owner signs the body with their SSH key (SSHSIG, namespace `mahi-meta`, SHA-512).
- A reader verifies the signature against an owner key it already trusts: its own key when it created the thread, or the key in the invite ticket when it joins. Never against the key the document names. This is what stops someone who can push to the remote from replacing `meta` with a thread key they control.
- After unwrapping, a participant checks that their thread key matches the recipient in the body, so the owner cannot give different participants different keys.
- The body names its thread and carries a generation: 0 for a new thread, one higher for each later version. A reader refuses a document whose thread is not the ref's. It also keeps, per thread and outside git, the highest generation it has accepted and that document's body hash. It refuses a lower generation (a rolled-back `meta` that still lists a removed participant or an old key), and a different body with the same generation. Checking that the ref only fast-forwards is not enough, since a force-push can rewrite it. An invite ticket carries the generation the joiner must accept at least. Pins live in each clone's git directory (`mahi/pins/`), so a fresh clone starts without one, and that minimum is what protects its first load.
- A tombstone is the last `meta` of a purged thread: a body of its own kind, in a new envelope version, holding only the thread ID, its generation (one higher than the last live one) and the owner's name, signed like any other. A reader checks its signature, thread and generation as for any `meta` and accepts it as the thread's end: there is no recipient, participant or thread key to check, and nothing is unwrapped. A live body without participants is still refused.
- A `meta` document is identified by the hash of its body, not by its git blob id: the envelope around a signed body can be re-encoded without breaking the signature.
- Keys that are points of small order are refused: an SSH ed25519 key of small order lets anyone forge its signatures, and a mahi key of small order gives an all-zero shared secret (age panics on it).
- Reading is bounded: 256 KiB per document, 256 participants, and a 256-byte title.

### Transcripts

- Each agent turn is one commit on `refs/threads/<id>/agents/<participant>.<agent>/transcript`, whose tree holds a single file, `turn`: the turn sealed to the thread key.
- A turn is `postcard` in a versioned record: its number, counted from 0, and its events, each a host-assigned sequence number and an opaque payload (the hook's name, a newline and its details, as the agent's hook sent them).
- Each sealed turn also stores the running last sequence number of the whole transcript, so an empty turn carries it forward.
- Turn numbers go up by one from commit to commit, and sequence numbers strictly increase within and across turns. Appending checks the new turn against the transcript's tip (its newest commit, turn number and running last sequence number), which the host keeps in memory or recovers by opening only the newest commit; it never opens earlier turns. Reading walks newest first, holds one turn at a time, and checks every commit it walks, which also has to have at most one parent.
- Reading is bounded: 1 MiB per event, 100,000 events and 64 MiB per encoded turn (plus the sealing overhead for the stored blob), and the caller chooses how many turns to read back.

### Native session files

- An agent's own session files (for Claude Code, the conversation it resumes with `--continue`) are recorded on `refs/threads/<id>/agents/<participant>.<agent>/session`, one commit per change, signed like the agent's other commits.
- Each file is cut into 64 KiB pieces, each sealed to the thread key on its own and named in the commit's tree by its tag: a BLAKE3 keyed hash under a key derived from the thread key, so names reveal nothing without it. A piece the previous commit holds is reused rather than sealed again, once that commit is found signed by the user's own key, so a session file that only grew, as a conversation log does, costs the pieces it gained. A sealed `manifest` in the same tree lists each file's path, size and piece tags, in a versioned `postcard` record; paths are relative, `/`-separated, with no empty, `.` or `..` component. A commit whose files are exactly the previous commit's is not written.
- Recording and reading are bounded: 4096 files, 8192 distinct pieces and 512 MiB of file contents per commit, 1024-byte paths 16 components deep. Reading checks the manifest (valid paths in strictly ascending order, none a directory of another or equal to another but for ASCII case, sizes that match their piece counts, every piece present, at most 4096 files as it decodes) before anything is written, then each piece's size and tag as it is copied out.
- The profile names the directory the agent keeps its sessions in, inside its state directory; for Claude Code, `projects/` and the worktree's path with every character but an ASCII letter or digit replaced by `-`, one per UTF-16 unit, as Claude Code names it (a path it would shorten, past 200 characters, is not recorded). Nothing else of the state directory is recorded, so its credentials never are. The directory is recorded after each turn the agent ends and once more when it stops, on a thread of its own so that hook messages keep flowing, a burst of turns being one record. It reads only regular files and directories, never through a symbolic link and skipping what it cannot open; it first walks the directory to count at most 8192 entries and add up the files' sizes, so a session past the limits is refused before anything is sealed.
- Before the agent starts, when its state directory has no session directory for the worktree, as on another machine or after `mahi end`, the latest recorded session, once found signed by the user's own key, is written there: into a new private directory beside it, under a random name, that then takes its name, so an interrupted restore leaves no half session, and under the name the worktree's path gives on this machine, so `claude --continue` finds it. A session directory already there is kept as it is. A session that cannot be recorded or restored is reported and the agent runs all the same.
- What the pieces show without the key: how many there are, which ones repeat from commit to commit (so that a file grew, and its size to 64 KiB), and the compressed size of each, like every sealed blob; a conversation's last piece is sealed again at each change, so its compressed size is seen as it grows.

## Getting started

Starting to work with mahi takes one command: `mahi run claude`, or `mahi` alone for the home screen. Every step that needs the user's answer is asked once, on the terminal, the first time it matters, and remembered; nothing the user must decide is guessed, such as a passphrase or whether a remote is public. Each step can still be done ahead with its own command. mahi asks only when its standard input is a terminal, and asks on the terminal itself, so standard output stays clean (`mahi id | pbcopy`). Without a terminal nothing is asked and mahi behaves as it did before these steps existed: a missing setup fails with the error that names `mahi init`, a missing credential leaves the agent to sign in its own way, and a clone with no remote chosen pushes nothing.

- **First-run setup.** `mahi run`, `mahi join`, `mahi id` and `mahi invite` set mahi up when it is not: before anything else, when `identity.pub`, `signing-key.pub` or `node.key` is missing, they say `mahi is not set up yet; setting it up` and run `mahi init`'s steps, then carry on. `mahi init` asks for a new passphrase twice when it creates the mahi key, or for the existing one once when `identity.age` is there without `identity.pub`, and chooses the signing key without a question when ssh-agent holds exactly one ed25519 key. A setup that fails or is stopped stops the command before it does anything else; the steps already done are kept, and the next command goes on from there. The home screen sets mahi up the same way before it unlocks the mahi key for an agent it starts. While the home screen shows, a setup keeps the key it made or unlocked, as an action's unlocked key is kept, so the passphrase is not asked a second time.
- **Credentials on first use.** Before the agent starts, after the checks that need no answer, `mahi run`, `mahi resume`, `mahi handoff`, `mahi agent add` and `mahi join -- <agent>` (not the agent `mahi land --with` drafts with) ask for the credential the agent's profile names (Claude Code's `claude`) when the variable it becomes would otherwise get no value: the credential is not stored, no `--credential` binds that variable, no `--pass-env` names it, and it is not set in mahi's environment as a variable the profile passes on (Claude Code's `CLAUDE_CODE_OAUTH_TOKEN`). mahi says how to make one, from the profile's `hint` (Claude Code's: run `claude setup-token` in another terminal), and asks for it with echo off. In a dialog, text between a pair of backticks in what mahi says, such as a command, is drawn highlighted and without its backticks; on plain lines the backticks stay. A pasted token is checked as `mahi credential add` checks it, never against its provider, stored, and handed to the agent. An empty answer runs the agent without it, so it can sign in its own way, and is remembered as an empty file named after the credential in `declined/` in the config directory, under the identity files' rules (600, in a 700 directory, owned by the user, not followed through a link), so it is not asked again; `mahi credential add` removes that file. A user profile may give a `hint` of 1 to 200 characters, not all spaces, with no control character and no invisible one (`mahi_core::is_invisible`: zero-width characters, text-direction marks and the like).
- **The remote, offered once.** When the clone has chosen no remote and has never been asked, and `origin`'s push URL is one `mahi remote origin` would accept, `mahi run` asks whether to push its threads to `origin`, and whether `origin` is private (with the agents' snapshots) or public (without them), or not to push at all: `[p]rivate`, `p[u]blic` or `[n]o`, Enter alone being `[n]o`, so visibility is never guessed. An HTTPS `origin` with no stored token is named with the credential it needs, as `mahi remote` names it. The answer is kept as `mahi remote` keeps it. `[n]o`, and `mahi remote --off`, which creates the sync directory if needed, write the line `off` to `mahi/sync/remote`, so the question is not asked again in that clone; `mahi remote` then says `threads of this clone are not pushed (turned off)`, and `mahi remote <name> --private` or `--public` still chooses one later. A clone turned off before this existed has no file and is asked once. mahi 0.1.0-rc.1 reads `off` as a corrupt setting, which a preview allows.
- **The home screen.** `mahi` with no arguments, in a git repository and on a terminal, opens a full-screen view drawn with `ratatui` (`ratatui-core` and `ratatui-widgets`, without default features, so no `crossterm`) on the alternate screen, which it does not leave until the user quits. Its colours are Royal Plum (#832161) behind the selection and mahi's badge, with white text, and a lighter plum (#D864AF) for titles, borders and keys, which reads on a dark terminal; they are drawn in 24-bit colour when `COLORTERM` says the terminal draws it (`truecolor` or `24bit`), and otherwise as the nearest of the 256-colour palette (89 and 169). One top row, on the terminal's own background, holds mahi's badge, the workspace's tabs when one is open (see Workspace), a blank cell between each, and on its right the repository, the remote threads are pushed to and the user's name; a remote not chosen reads as a warning, followed by `(m)` where that key chooses it, and a row too narrow for all of it leaves out the repository, then the whole right side, never a tab; a menu (threads, new thread, join with a code, remote, credentials, your card, help, quit) sits beside the thread list, which shows each thread as `mahi threads` does (id, agents, whether the worktree is there, and whether the user owns it), and an activity pane, whose last rows, the status line, tell the outcome of the last action below what mahi's commands printed; the keys of the focused part close the screen, the selected thread's own keys among them while the thread list has focus; on a terminal too narrow for them all, the last are left out, but never help and quit. A list too narrow for its whole ids shows their first 8 characters, as the tabs do, so the agents show on an 80-column terminal. It reads no encrypted content (not the title, not the landing branch, both sealed in `meta`) and asks for no passphrase until an action needs one. The mahi key an action unlocks is then kept in memory, in a copy that is zeroed when dropped, for the actions that follow, so the passphrase is asked once: it is forgotten when the home screen ends, before mahi dies of a signal that stops it (also from inside a dialog or an action), or when no action has used it for 15 minutes, a wrong passphrase keeps nothing, and a command run outside the home screen never keeps it. While it is kept, mahi's soft core file size limit (`RLIMIT_CORE`) is 0, its hard limit unchanged, so a crash writes no core file holding it (systemd-coredump, which the kernel streams a crash to whatever the limit, also stores none then), and a key that cannot have that limit is not kept; the agents mahi starts meanwhile inherit the limit. mahi is not made non-dumpable instead, since the sandbox's child, forked from it, writes its own `uid_map`. Tab moves between the menu and the threads, arrows or `j` and `k` move (also in a dialog's list), Enter opens what is selected (a thread opens a menu of what can be done with it: resume when the user owns it, add an agent, hand off, land, push the landed commits as `mahi land --push` does, optionally with an agent to rewrite the pull request draft, end, invite, purge), and keys reach the same actions at once: `n` new thread, `r` resume, `a` add an agent, `h` hand off (each asks in dialogs what its command needs: which agent to start, among the programs mahi has a profile for on `PATH`, and whose work it starts from or takes), `l` land, `e` end, `p` purge, `i` invite, `c` join with a code, `m` remote, `s` credentials (add one, its token asked masked as `mahi credential add` asks it, or remove a stored one after a confirmation; names only are shown), `u` your card (as `mahi id` prints it), `?` help (a table of the keys, scrolled with the arrows or `j` and `k` when it is taller than the screen), `q` or Escape quit. When the list has no thread, a thread's key says how to start one instead of doing nothing. The remote dialog lists each git remote as private or public, and also adds a git remote to the repository (a name, `origin` when left empty, and an SSH or `https://` URL, refused when mahi could not push to it), written to the repository's `config` under its lock with git's default fetch refspec, as `git remote add` does, then asks whether it is private. Landing and ending ask first, and purging asks as `mahi purge` does; when the thread's agents run in the workspace's tabs, ending and purging first ask whether to stop them, as quitting does, stop them on yes and go on, and keep them running otherwise; purge asks its own question after that stop, so an agent stopped for a purge that is then declined keeps its work in its last snapshot, to be resumed, and an agent that does not stop within 30 s keeps running and the thread is neither ended nor purged; Escape closes a dialog, and the keys read after it, in the same read or the next, still act. When a read ends in an escape byte alone, outside a paste, the next read, when it comes within half a second and starts as the rest of an escape sequence (`[` or `O`), is joined back to that byte, so the rest of a paste split after its escape byte is read as a paste and cannot answer anything.
  - Everything an action asks is a dialog on the same screen, drawn over the home screen's last frame, which is drawn again without its own dialog once an action is chosen there, so a question the action asks never shows over the menu that started it: every prompt mahi's commands use (the setup's passphrase, a credential, the remote offered once, a confirmation, a pairing code, the choice of an agent or a key) becomes, while the home screen owns the terminal, a dialog that lists choices, asks yes or no, or takes a line, masked for secrets; a pairing code shows as it is typed, since the owner read it out or sent it anyway and a dialog on the alternate screen leaves nothing in the scrollback, while `mahi join` on lines still reads it without echo. A spinner turns in the title of every notice but a pairing code's, such as the one that says mahi is working after a question is answered, until the next question or the next frame of the home screen; a command that shows nothing within 150 ms gets a notice that says it is working. An invite says it is getting a pairing code ready on the remote, by name, and shows the code in a still dialog of its own titled Invite a teammate, with the code on a line of its own after a key and in the colour of something to type, the text in paragraphs below it and Ctrl-C as its key; once the wait ends, a notice says mahi removes the pairing code from the remote. Nothing is drawn while a question shows, and nothing after mahi leaves its screen. What a command prints to standard output, such as a card, a ticket or a list of credentials, is shown in a dialog that closes on Enter; when it is one line, mahi also puts it on the clipboard through the terminal (OSC 52), since copying a long line off the screen would take the dialog's border and line breaks with it. What the commands print to standard error goes to the activity pane instead of over the screen, through a pipe put in place of standard error while the home screen lives and taken away when it ends.
  - A new thread, a resume, an added agent and a handoff run their agent as a child mahi process in the tab of its thread, which opens for it (see Workspace), and a resume of a thread whose tab already runs an agent shows that agent instead of starting another, which would find its agent already running: its keys reach the agent, and the palette key opens the workspace's palette (see Workspace), whose entries and keys move between the thread list and the tabs (`0` to `9`, `←`, `→`), choose the agent of the tab shown, hide or show the list of its agents with `b` (the agents' terminals then take the room it leaves, and the workspace, before it draws, waits for the shown agent, while it runs, to redraw at its new size: until the agent has written and then stayed quiet for 15 ms, and at most 250 ms after the first resize it waits for, so its pane does not show blank in between and resizing without pause cannot hold drawing longer), and show with `Space` the next agent, in any tab, that is done, asks the user or failed; the palette key pressed twice sends it to the agent. Each child reports its thread and its agent's state to the workspace, as the Workspace section's Reports describe. While a tab is open the terminal reports the mouse (modes 1002 and 1006, turned off when the last tab closes, when mahi leaves its screen and while a dialog shows, so the dialog's text, such as a pairing code, can be selected), as the Workspace section describes: a click on a tab shows it, on `+` starts a new thread, on an agent in the list shows that agent, elsewhere on the top row or in the list does nothing, and the rest of the mouse goes to the agent shown, at its own cell and in the mode and encoding it asked for, only when it asked for the mouse; a report cut between two reads is kept for the next one, so it never reaches the agent or the thread list as keys. A command that succeeds is drawn once more, then leaves its tab, with its outcome in the status line, and a tab with no agent left closes, unless it only watches a thread the user joined; one that fails stays, marked failed in the list, with its last screen, until a key in its pane closes it. Quitting while an agent runs in a tab first asks whether to stop them (`1 agent is running: stop it and quit?`, Enter alone being no); yes leaves mahi's screen, says `stopping N agent(s)`, and sends each child `SIGTERM` (not `SIGHUP`, which a mahi started under `nohup` would pass on ignored), so it ends its agent as a stop signal does, with its last snapshot unless it was already taking it when the signal came; mahi waits up to 30 s for them, which a push to the remote can take, reading what they write meanwhile, then kills what is left and says how many lost their last snapshot. The end of mahi's input stops them the same way, without asking. Another action that runs an agent, such as the pull request draft's writer, runs it in a pane of mahi's own screen, never on a screen of the agent's: a header names what runs (the agent and its thread, or the pull request draft's writer), the agent's screen sits in a bordered pane, and a line below gives mahi's keys (the palette key, and that exiting the agent goes back to the threads). The agent's terminal is the pane's size, and follows it when the terminal is resized: mahi's own screen takes the new size before the agent's terminal does, so what the agent draws for it is read at that size. mahi reads the agent's output, as much as is waiting at once (up to 64 KiB), into its own `vt100` screen (`mahi-term`'s `AgentScreen`, at least two rows and columns, since `vt100` cannot draw in less; an OSC the agent begins, the only string `vt100` keeps, is cut off past 128 KiB so it cannot grow without end; a screen that gets narrower starts blank with the agent's modes and the agent redraws, since `vt100` 0.16 panics on a wide character a narrower row cuts in two) and draws that screen into the pane, one frame per batch inside a synchronized update, so nothing the agent writes reaches the user's terminal as it is. mahi answers the agent's cursor position and status reports itself, since only it knows where the cursor is in the pane; the rest of what the agent asks of the terminal itself is passed on with control characters, C1 included, taken out: the bell, the window title, the clipboard as base64 (up to 128 KiB), plain-text OSC 9, OSC 99 and OSC 777 `notify` notifications, the terminal's identity and colour queries (whose answers come back on the keyboard; an OSC that would set a colour is not passed on), the kitty keyboard modes it pushes and pops and xterm's `modifyOtherKeys`, and the key modes it switches (application cursor keys, the application keypad and bracketed paste), written before the rest, so a query of a mode the agent just set is answered for the new mode. mahi puts the key modes back, and pops what the agent pushed, when the agent exits, and draws nothing the agent writes after that. mahi's own notices skip the agent's screen and reach the terminal as they are. Mouse reporting is not passed on, since the terminal would report positions on the whole screen. The palette, titled "Held turns" and named so on the line of keys, opens as a layer over the pane, drawn into a screen of its own whose written cells cover the agent's: the agent keeps drawing beneath it, and closing it needs no redraw, so the agent's terminal is never resized for it as it is outside the home screen. When the agent exits the home screen redraws itself, with the action's outcome in the status line. Outside a repository, or without a terminal, `mahi` prints its help as before. Keys come through `mahi-term`'s parser and drawing goes through a small `ratatui` backend over the same terminal, so mahi has one input path; the view redraws on a key, a resize, new activity, or a change in the thread list, which it reads again every 2 s.
- **Pairing codes.** `mahi invite <thread>` without a card, or `i` on the home screen, pairs the owner with a teammate through a short code, instead of a card sent one way and a ticket sent back. When the clone pushes its threads to no remote, inviting from the home screen (`i`, the thread menu or the palette) first opens the remote dialog, saying that pairing needs a remote to meet through, and invites only once one is chosen. Cards and tickets keep working as before.
  - The code is a slot number from 1 to 999 and two words, the first from the PGP word list's even list and the second from its odd list, such as `412-merit-intention`, read without regard to case, with a slot written without leading zeros and dashes that chat apps substitute (such as an en dash) read as hyphens. The slot is not secret; the words are 16 bits of secret, and every pairing draws fresh ones. The owner's mahi shows the code once, to be said or sent to the teammate, who runs `mahi join` with no ticket (or `c` on the home screen) in a clone of the project and types the code when asked. On the home screen the joined thread then opens in a tab of its own, which watches the owner's agents as a thread's teammates are watched, with the user's mahi key unlocked to host it, instead of the full-screen view; that tab, which holds no agent of the user's, stays until the palette's Leave this tab closes it. Until it lists one of the owner's agents, its pane shows `waiting for the thread's host` in its middle, after a spinner that turns every 100 ms. The code is never taken as an argument, since arguments are readable by other local users and, on macOS, by a sandboxed agent (see Sandbox), and it is never logged or written anywhere.
  - Rendezvous goes through the project's remote, not a server. For each pairing the owner's mahi makes a fresh iroh key, so pairing neither moves the user's own node off its relay while one of their threads runs, nor publishes their long-term node id; the owner's real host address comes later, in the ticket. Pairing needs a chosen remote (`mahi remote`). The owner picks a slot at random among those with no ref on that remote and pushes `refs/mahi/pair/<slot>` only if it is absent: one commit, with the generic committer identity thread commits use and no parent, whose tree holds one blob, `where`, with the pairing key's node id and its relay URL (its direct addresses instead when `MAHI_LIVE` is `local`, which has no relay, so local mode shows the owner's network addresses to whoever reads the remote). Another slot is tried if the push loses a race. The ref is deleted when pairing ends, succeeded or not, only by the owner and only while it still points at the owner's commit (a push that loses the race to create it is refused by the remote, and another slot is tried). Pairing commits carry no time, like thread commits, so the owner's mahi records a pending pairing's slot and commit in `mahi/pairing` in the git directory; a pairing that crashed leaves its ref and that record, and the owner's next pairing in that clone deletes the ref, again only while it still points there. The joiner fetches the ref from its own chosen remote, else from `origin`, into memory, without writing a local ref.
  - The fetched ref is untrusted input: anyone with push access, or a hostile `origin`, writes it. The joiner fetches it with a read budget of 64 KiB, so a ref pointing at a large history fails rather than filling the repository, refuses a commit with a parent or over 2 KiB, a tree that holds anything but `where` or over 128 bytes, and a blob over 1 KiB, each from its header, checks that the place has the shape above (a relay and no direct address, or in local mode the reverse), and holds the relay URL to a ticket's rules (`https`, a domain name that is not `localhost`, no user information, query or fragment). Pairing-ref reading and the pairing messages each get a fuzz target.
  - The joiner connects with its own node key (ALPN `mahi/pair/1`). The two run SPAKE2 (the `spake2` crate, Ed25519 group), the owner as side A with the identity `mahi-pair-v1 owner <slot>` and the joiner as side B with `mahi-pair-v1 joiner <slot>`, and the whole code, lowercased, as the password. HKDF-SHA256 over the SPAKE2 key, salted with `mahi-pair-v1 <slot>`, gives four keys, with the info strings `confirm joiner`, `confirm owner`, `seal joiner` and `seal owner`. The joiner sends its SPAKE2 message first, since a QUIC stream reaches the other side only with data, and the owner answers with its own. The joiner then sends HMAC-SHA256, under its confirm key, of the SHA-256 of both SPAKE2 messages (each with its length, the owner's first); the owner checks it, then sends its own. The `spake2` crate keeps copies of the password and its secret scalar that it frees without wiping, so a memory disclosure afterwards could show a code already used, whose words are 16 bits. Nothing else is sent until both check.
  - A code allows exactly one SPAKE2 exchange: the first connection that opens a stream uses it up, any other connection that opens one is closed at once, a connection that opens none within 15 s is closed without using it up, and a failed confirmation ends the pairing, telling the owner, who can draw a new code. A guesser therefore has one chance in 65536. The joiner, too, stops after one failure and never tries the same code again, since a forged ref can point it at someone else.
  - Messages carry at most 4 KiB each, framed as a two-byte big-endian length and the sealed message (at most 4 KiB plus its 24-byte nonce and 16-byte tag), sealed with XChaCha20-Poly1305 under the sender's seal key, with a random nonce and the sender's role and a message counter as associated data, so none can be replayed, reflected or reordered; any failure ends the channel. The joiner sends its participant card, whose node id must be the node its connection is authenticated as. The owner's mahi shows its name and SSH key fingerprint and asks `Add <name> (<fingerprint>) to thread <thread-id>? [y/N]`, then adds them as `mahi invite <thread> <card>` does (asking for the passphrase) and sends the ticket back; the joiner checks that the ticket is for its node, then joins with it as `mahi join <ticket>` does.
  - Each step after connecting must finish within 15 s, the human answers excepted, and the whole pairing within 10 minutes. Whoever can read the ref (anyone, on a public remote) can spoil a pairing by connecting first with a wrong guess, and whoever can push can replace or delete the ref; either way the pairing fails and says so, and nothing is added. Like the other serverless caveats, this costs a retry, not a secret. If the owner adds the teammate but the ticket cannot be sent, mahi says so and prints the ticket for the owner to pass on, since the teammate is already in `meta`; the owner's mahi closes the connection on any failure, so the joiner learns at once that the pairing ended.

## Session lifecycle

`mahi run -- claude` (or any agent):

1. Find the repository that holds the current directory, as git does (a repository owned by another user is refused, as git refuses it), and create the thread: ID, thread key, `meta` ref (base commit, creator key, participants, landing branch). `HEAD` must be on a local branch, which becomes the landing branch. The creator's participant name comes from `USER`, lowercased, and the agent's name from the file name of the agent program. Optionally snapshot uncommitted changes as the real starting point.
2. Add a linked worktree at the base with a detached `HEAD`, at `$XDG_DATA_HOME/mahi/worktrees/<repository>-<hash>/<thread-id>.<agent>`, one for each of the user's agents in the thread (`~/.local/share/…` when it is unset, on macOS too, since `~/Library` is kept from agents), where `<repository>` is the repository's name made safe (at most 64 bytes) and `<hash>` the first 4 bytes of the SHA-256 of its common git directory's path, in hex. Before the thread is created, mahi refuses a worktree root inside a private directory and opens the repository's directory without following links, as a directory the user owns, reset to mode 700; an empty one is removed when a start fails. The worktree is outside the git directory because agents protect files under a `.git` directory (Claude Code asks before every edit there, whatever its permission mode), and, with the default location, outside the user's checkout so it does not show in `git status`. It is still registered in the repository's `worktrees/` as git does, so no branch appears in the user's branch list; the agent's work is recorded in its `snapshots` ref. mahi writes git's linked-worktree layout itself and checks files out with gix. `.gitattributes` conversions (`text`, `eol`, `ident`, `working-tree-encoding`) apply as in git, so `git status` stays clean, but no filter driver is configured, so no filter program (such as git-lfs) runs: filtered files are checked out as stored. Inside the sandbox the agent sees only the parts of the repository's git directory that git needs in its worktree, all read-only: the worktree's `.git` file, its own record in `worktrees/` (refused when it holds a `config.worktree`, which mahi never writes), and `objects`, `refs`, `packed-refs`, `info`, `shallow` and `reftable` (the two files as they were when the agent started, since a file replaced by renaming does not reach the sandbox; mahi's own refs are files in `refs/`, which does). The configuration (remote URLs that may carry a token, `http.extraHeader`, credential helpers, includes and the programs config can run), `remotes/`, `branches/`, `modules/`, the hooks, the other worktrees' records and mahi's own directory, with the other threads' worktrees and whatever ignored files they hold, are not there. In their place git reads a configuration mahi writes for the run in its scratch directory, which keeps from the repository's only the `core` settings that describe its files and its `extensions`, each only when its value is a plain word: on Linux it is shown at the configuration's own path, outside every bound path, so nothing done to the real file reaches the agent; on macOS, where Seatbelt cannot show one file in place of another, the real configuration is unreadable and `GIT_COMMON_DIR` points git to a directory in the scratch directory holding the cleaned configuration and links to the parts above, so git run in another repository inside the sandbox on macOS uses this one's objects and refs. A directory on `PATH`, or the agent's program, that holds the git directory or lies inside it is not given to the agent; a working directory whose `.git` is not a file pointing to a record in the repository's `worktrees/` is refused; and so is a repository whose git directory lies under a system directory the sandbox shows the agent (such as `/opt`), where the agent would see all of it.
3. Start the network proxy and the snapshot scheduler. On macOS the proxy listens before the agent starts; on Linux its listening socket only exists once the sandbox is set up in step 5, and the proxy starts on it then. Snapshot zero, the checked-out base, is committed to the agent's `snapshots` ref as soon as the thread exists; after that a commit is added only when the worktree's tree changed, and a last snapshot is taken when the agent exits. Snapshot errors do not stop the agent: the first one is reported when mahi ends, and so is the number of paths the last snapshot left out. A stop signal during snapshot zero or the last snapshot stops the walk between two files, so no ref update is cut short and no lock is left behind; mahi then ends with that signal, and a second signal ends it at once, which can still cut short a ref update in progress and leave its lock. When a stop signal ended the agent, further signals already queued are dropped, so a terminal that sends `SIGHUP` twice does not lose the last snapshot; a stop signal that arrives as the agent exits on its own counts as the first one. What snapshots add to the repository is bounded per snapshot and per transfer, and removed with `mahi purge` (see Growth caps); a thread's history is never rewritten, so its total size is not capped.
4. Create the per-thread agent config dir and install capture hooks. The agent sees `MAHI_BIN` (the mahi binary, bound read-only) and `MAHI_HOOK_SOCKET` (a Unix socket in its private scratch directory, the only one it may connect to). A hook runs `mahi hook prompt|tool|turn-end|asks` with the event's details on standard input; for a known event it exits 0 even when mahi cannot be reached, so it never breaks the agent, but it waits for its standard input to close and for mahi to accept the connection. It sends the event's name, a newline, the details' length (four bytes, big-endian) and the details, so a message cut short is refused. mahi reads one connection at a time, with a 2 s deadline, a closed set of event names and at most 1 MiB per event, and drops what does not fit its queue of 16 messages; the number dropped is reported when mahi ends. When the agent has exited, mahi still reads the connections already waiting, for about 5 s at most (under 10 s even when a slow connection is being read), before it seals the last turn. A failed accept counts as a dropped event and does not stop the server. `tool` and `turn-end` ask for a snapshot. Every event but `asks` is recorded, as its name, a newline and its raw details, which mahi reads when the turn is shown (see Adapters); `turn-end` seals the events since the last turn into one encrypted transcript commit of at most 64 MiB, and the rest are sealed when the agent exits. Each turn is bounded (see Growth caps); the number of turns is not, as for snapshots.
5. Launch the agent in the sandbox → PTY → the user's terminal. mahi keeps its own copy of the agent's terminal open while the agent runs and closes it, on a thread of its own, once the agent has exited: macOS drops what a program wrote and no one read yet when its exit closes the terminal's last copy, so an agent that prints and exits at once, before mahi first reads, would otherwise lose its output; while mahi's copy stays open, what the agent wrote waits until mahi has read it. Everything that can fail without the thread is checked before step 1, including that the agent is a native program or a `#!` script: libc's `execvp`, which `std::process::Command` uses, would run any other file with `/bin/sh`, so a start that failed would look like an agent that ran and exited. Files run through a `binfmt_misc` handler are refused for the same reason. If the agent still cannot start, the thread's `meta` ref, its pin and its worktree are removed, so a failed start leaves nothing to push. A stop signal (`SIGINT`, `SIGTERM`, `SIGHUP`, `SIGQUIT`) during steps 1 and 2 interrupts the checkout, removes what was made, and then ends mahi with that signal. Signing `meta` through ssh-agent cannot be interrupted, since the agent may be waiting for a confirmation or a key touch, so a second stop signal ends mahi at once and may leave the new worktree behind.
6. Start the live layer (milestone 2, see Participants and the live layer), before the agent starts so its whole screen is known: bind the iroh endpoint with the user's node key, serve `meta` to the thread's participants, join the thread's gossip topic and broadcast the agent's terminal. The output goes to the user's terminal first; a copy feeds the host's `vt100` screen, which numbers each chunk it takes, and a queue of chunks for one broadcaster thread, which sends output, resizes and screens in order. A screen says through which chunk it goes, and the broadcaster skips the queued chunks it holds, so a viewer never applies output twice. When the network falls behind, chunks are dropped rather than slowing the agent, and the broadcaster then sends the whole screen, which viewers already following accept. A send that fails counts as a drop too, and a screen skips queued chunks only once it can be sent. Screen requests are answered at most once a second per requester, several at once from one snapshot; a viewer asks again until a screen anchors it. When the agent ends, output still queued is dropped. A live layer that cannot start is reported and the agent runs without it. `MAHI_LIVE=off` turns it off, `MAHI_LIVE=local` runs it without relays, reachable only on the local network, and any value other than those and `public` is refused rather than guessed. Teammates are invited with `mahi invite`, which prints their ticket.
7. Each turn: events get host sequence numbers, are broadcast live, and are flushed as an encrypted turn commit at turn end, then pushed to the remote.

Joining: `mahi join <ticket>` runs in a clone of the project, checks that the ticket was made for this machine's node, fetches `meta` from the host (retrying for about 30 s while the host rereads it), checks it against the owner key and minimum generation in the ticket and that it lists both this node and the host, refuses a thread this repository started (one with a `meta` ref but no remembered owner), records the document as the thread's `meta` ref and pins it, only after checking it against any `meta` ref already there (when milestone 3 fetches the owner's refs, a fetched `meta` that does not verify under the remembered owner key is refused and reported, never silently put in place: a ticket naming a thread the user started in another clone must not take it over), then remembers the ticket's owner key for the thread (in the git directory, write-once: another key for the same thread is refused) (until milestone 3 fetches the owner's refs, which then replace this local copy), asks for the passphrase to unwrap the thread key, shows the host's current screen and then follows the live terminal. The viewer draws on the terminal's alternate screen from its own `vt100` copy, follows one agent of the host's participant, asks for the screen again whenever frames were dropped or a sender restarted, and leaves on `q`, Ctrl-C, Ctrl-D or a stop signal, or when the topic closes. It draws the screen's contents and cursor only, never the agent's input modes (mouse tracking, bracketed paste, keypad), and resets the terminal when it leaves, however it leaves. A host that has sent nothing for 5 s sends a heartbeat, so a viewer that hears nothing from the host for 30 s says it may have stopped and leaves. `mahi join <ticket> -- <agent>` then runs the user's own agent in the thread instead of watching (milestone 2): in a worktree at the thread's base commit, which the clone must have, under the user's own `<participant>.<agent>` refs, sandboxed and recorded as with `mahi run`, and hosted live on the thread's topic, joined through the owner's host, trusting the ticket's owner key. A second `join` continues the same agent in the same worktree; if that worktree is gone, it is rebuilt as `mahi resume` does. Agent options such as `--allow-host` are refused without an agent. `mahi join` also keeps where it reached the host, in the git directory, and `mahi resume` and `mahi end` then work for a joined thread as for the user's own: they check `meta` against the owner key remembered from the ticket when there is one, and otherwise against the user's own key, never both, and `resume` rejoins the thread's topic through the remembered host. From milestone 3 it also fetches `refs/threads/<id>/*`, renders history, and dedupes by sequence number. The teammate can then watch, or `mahi agent add` to run their own agent in the thread.

Ending and restarting: `mahi end` waits for idle, commits final turns, pushes, and stops sandboxes. In milestone 1 it is local: `mahi end <thread-id>` ends a thread the user owns and none of whose agents is running (it takes the thread's lock alone and refuses otherwise), records each of the user's agents' worktrees in a last snapshot of that agent, then removes the worktrees, the state directories of the thread's agents with the plaintext they hold (such as Claude Code's own transcripts and a `/login` credential) and the thread's lock files. The thread's refs stay: they are its history. It needs no passphrase, since snapshots are not encrypted. Files `.gitignore` excludes are not in snapshots and are removed with the worktree, like build output; files a snapshot cannot record (too large, unreadable, or named as git refuses, such as `.GIT`, `git~1` or a symbolic link called `.gitmodules`, which git's fsck rejects) make `mahi end` refuse and list them, and `--force` removes them anyway. A worktree whose `.git` file no longer links back is left in place and the thread is not ended; a worktree deleted by hand only has its registration pruned. Nothing is removed before the last snapshot is recorded, and a stop signal while it is taken ends `mahi end` with nothing removed; once it is recorded, the removal runs to its end. `mahi resume <id>` fetches, decrypts, restores worktrees at their latest snapshots, restores agent config, and relaunches (native resume if the adapter supports it, otherwise a handoff bundle).

Local resume (milestone 1): `mahi threads` lists the threads in this repository from their refs: id, agents, and whether the worktree is still there; it reads no encrypted content, so it asks for no passphrase. `mahi resume <thread-id>` resumes a thread the user owns: it checks that `meta` is signed by the user's own signing key, asks for the passphrase to unwrap the thread key, reopens the registered worktree, or rebuilds it when its directory was deleted. A rebuilt worktree has a detached `HEAD` and an index at the thread's base, and the files of the agent's latest snapshot, so the recorded work shows as changes on top of the base. A snapshot may be a teammate's, so it and the base are counted before anything is written, each distinct tree read once: one that would check out more than 2,000,000 files (gitlinks included), 262,144 directories or 64 GiB (a subtree's files and directories counted each time it is named, so a small tree naming the same subtrees or blobs over and over, even empty ones, cannot stand for millions of entries or a full disk), holds a file over 256 MiB or a tree over 1 MiB, nests directories deeper than a snapshot records them (256), or holds more than 262,144 distinct trees or 256 MiB of them is refused. A snapshot never records a tree over 1 MiB: a directory with that many entries (about 20,000 with ordinary names) is left out and reported like a file too large, and a worktree root directory that large fails the snapshot, and with it `mahi end`, even with `--force`. A worktree past the other limits can still be snapshotted, so a thread that large cannot be rebuilt. Commits the agent made are kept only as those files, and a file it had added although ignored is left out of later snapshots, since the snapshot does not record what was tracked. A worktree whose directory still exists but no longer links back is not rebuilt: it is reported for the user to repair. mahi then reopens the agent's state directory without following symbolic links and rewrites the profile's files by replacing them, then runs the agent as `mahi run` does, with the same options. Snapshots continue from the `snapshots` ref's head (no new snapshot zero) and turns from the transcript's tip. The agent is the program named after the thread's agent slot, looked up on `PATH`, plus the profile's resume arguments (`--continue` for Claude Code, which reopens its last conversation from the kept `CLAUDE_CONFIG_DIR`), unless the agent's state holds no session log of its for the worktree (an earlier run that ended before its first prompt keeps none), when the agent starts a new conversation instead, as mahi says, rather than fail on a conversation it cannot find; mahi looks only as deep as the agent keeps its logs (at the top of Claude Code's project directory, three dated directories down Codex's), at no more than 10,000 entries, following no symbolic link inside the session directory, and when it cannot tell (no reader for the agent, a session directory it cannot name, or one it cannot read) the agent is resumed with its arguments as before; `mahi resume <id> -- <agent> [args…]` runs another command, and `--agent <name>` picks one of several agents. Checks that need no key (the agent program, the sandbox, the network, the owner's signature on `meta`) run before the passphrase is asked. Only one mahi at a time runs an agent, and nothing ends a thread while one runs: every mahi that runs an agent holds an advisory `flock` on `locks/<thread-id>` shared and one on `locks/<thread-id>.<agent>` alone, for as long as it lives, and the system releases them however it exits; `mahi end` and `mahi invite`, which must know that no agent runs, take `locks/<thread-id>` alone. While its agent runs, the mahi also holds `locks/<thread-id>.<agent>@running` alone, taking it with a wait rather than failing: the user's other mahis tell that the agent runs on this machine, for `list_agents`, by trying to take it shared without waiting and letting it go at once, so looking never makes a starting mahi fail. No sandbox sees that directory, so an agent cannot hold another thread's lock. `mahi end` removes a thread's lock files; a mahi that opened it just before holds the lock only if the path still names the file it locked, and tries again otherwise, so an ended thread never has two holders. The state directory is opened once without following symbolic links, checked through that open descriptor (a directory the user owns), reset to mode 700, and written relative to it.

Host migration: if an agent's host leaves, another peer restores from the latest snapshot and resumes the session (native or handoff).

## Participants and the live layer

Milestone 2 lets teammates watch a thread live, and run their own agent in it, before thread refs are pushed anywhere.

- Each user has an iroh node key: `node.key` in the config directory, an ed25519 secret held to the same file rules as `identity.age` (600 in a 700 directory, owned by the user, written once, never followed through a link). `mahi init` creates it, also on a setup made before it existed. Its public half, the node id, names the user's machine on the live layer. There is one per user, so it links their live sessions the way their SSH key links their `meta` entries.
- `mahi id` prints the user's participant card, one line holding only public keys: `mahi-participant <name> <mahi key> <node id> ssh-ed25519 <key>`. Fields are separated by spaces, anything after the SSH key is its comment and is dropped, and a card holding a control character (such as a second, pasted line) is refused. The teammate sends it any way they like; the owner must know it came from them, as with an SSH public key.
- `mahi invite <thread-id> <card>` is run by the owner. It asks for the passphrase, unwraps the thread key, adds the participant with the thread key wrapped to their mahi key, signs the next generation of `meta`, pins it and prints a ticket. It asks for the passphrase only when it must add someone: a card already listed exactly gets its ticket again, and one that shares a name or key with a listed participant is refused first. The thread may be running: its host rereads `meta` when an unknown node connects, and `invite` then takes the running host's address instead of binding a second endpoint with the same node key, since a relay keeps only the newest connection of a node. A running host publishes its address, and updates it when it changes (such as when its relay answers), in `live/<thread-id>` in the config directory, a private file it removes when it stops; `invite` reads it when the thread's lock says the thread is running, and otherwise binds its own endpoint while it holds the lock, so for those few seconds starting or resuming the thread says it is already running. The address is found before anything is changed, so an invitation that cannot get one adds no one. The ticket is `mahi1…`, bech32 over `postcard`: its version, the thread ID, the host's address (node id, relay URL and direct addresses, found by binding the endpoint), the owner's SSH key, the minimum `meta` generation and the invitee's node id. It holds no secret: the thread key only ever travels wrapped to the invitee's mahi key. A ticket is pasted from elsewhere, so it is parsed strictly (at most 1023 characters, bech32m, no trailing bytes), its relay must be a plain `https` URL on a domain name other than `localhost` (no user information, query or fragment), and it holds at most 8 direct addresses, none unspecified, multicast, broadcast, IPv6 link-local or on port 0, so a hostile ticket cannot point the joiner's machine at local services.
- The endpoint is iroh with the user's node key and `mahi-tls`, and uses n0's public relays, which only forward ciphertext. It listens on a UDP port chosen by the node id among the 16384 dynamic ports (a random one when that is taken), so the direct addresses a ticket holds still reach a host started later. The relay is the address that works across networks: a ticket is not printed without one, and a host reaches the same relay again as long as it runs from the same place. `node.key` is stored unencrypted, like an SSH key without a passphrase, so `mahi run` needs no passphrase: whoever reads it can speak as the user on the live layer, though they still cannot open a thread without the mahi key.
- Finding a participant's machine. A node id, which `meta` lists for every participant, says who a peer is but not where. mahi joins a thread's topic through the addresses it remembers for the thread, in private files in the git directory: the host address of the ticket a thread was joined with (`mahi/hosts/<thread-id>`), and the last address at which each participant's node was reached while mahi hosted the thread, checked every 2 s and written when it changes (`mahi/peers/<thread-id>/<node id>`, its relay and direct addresses under a ticket's rules, read only under the node it names), at most 32 per thread, the one written longest ago going first; a host joins the topic only through those of the participants its `meta` lists now, and keeps a direct address only when it is in use, never one a peer merely named; `mahi purge` forgets them all. Alongside them, iroh looks the node up through its pkarr address lookup, over HTTPS from n0's server (`https://dns.iroh.link/pkarr`), which keeps the lookups away from the network's DNS resolver; every endpoint that joins a live topic does so with the public relays: a host, that is a mahi whose live layer serves an agent (a run, a resume, an added agent, a handoff, `mahi join -- <agent>`, the workspace), publishes while it hosts, and again every 5 minutes, a record signed with its node key, which iroh checks, holding only its relay's URL, never an IP address, so a peer meets it at the relay first and iroh then moves the connection to a direct path when one works. A workspace closes its node, and so stops publishing, once it hosts no thread. A viewer (`mahi join` without an agent), pairing and `mahi invite` publish nothing, and nothing is published when `MAHI_LIVE` is `off` or `local`, which has no relay. A relay URL from a record is taken only under the rules for a ticket's relay (a plain `https` URL on a domain name other than `localhost`), and a record's direct addresses are ignored. What publishing reveals must be said plainly: anyone who knows a node id, and every participant's is in a thread's `meta`, which a public remote shows to everyone, can see which relay it uses, roughly its region, though not its address, and, since a record is not withdrawn when the host stops but only replaced every 5 minutes while it runs, someone who keeps asking can tell when that node was hosting; the network itself sees only one DNS query for `dns.iroh.link`. mahi uses no other discovery (no DHT, no mDNS on the local network).
- `meta` is served over a direct connection (ALPN `mahi/meta/1`). The joiner sends the thread ID, and the host answers with the current signed document only when the connecting node id, which iroh's TLS authenticates, is a participant's node key in it; otherwise it closes the connection. A host rereads its `meta` ref for an unknown node at most once every 5 s, whoever asks, since fresh node keys cost nothing, and runs at most two reads at once; a request beyond that, a slow read or a failure on the host's side closes the connection as "unavailable", which a joiner retries, and only a node that is not a participant is told "refused". Answers are bounded like any `meta` read (256 KiB). The joiner checks the signature against the owner key in the ticket, never the one in the document, refuses a generation below the ticket's minimum, pins it and checks that it lists both its own node id and the host's.
- `mahi join` runs in a clone of the project, since resuming needs the base commit: pins live in that clone's git directory as they do for the owner.
- Live messages travel on one gossip topic per thread. iroh-gossip admits anyone who knows a topic's ID, so the ID and the sealing key are derived from the thread key, which only participants hold: HKDF-SHA256 with the thread key's secret as input, the thread ID as salt, and `mahi-live-topic-v2` or `mahi-live-seal-v2` as info. Version 2 left out the prompt frames of version 1, so a mahi of one version never meets one of the other. Rotating the thread key when a participant is removed therefore moves the thread to a new topic and key, which is what shuts a removed participant out; peers follow the newest `meta` they have pinned. The host is the bootstrap peer. A node accepts gossip connections only from the nodes of its `meta`'s participants, and a node that hosts several threads, as the workspace's does, from the participants of any of them, since each topic's frames are still checked against its own thread's `meta` and each thread's `meta` is served only to its own participants; connections gossip opens itself, to peers other members name, are not filtered, and iroh-gossip also learns those peers' addresses from them, so an admitted participant can make another participant's node dial an address of their choosing (it then only sends sealed frames there). A broadcast waits at most 2 s, so a peer that stops reading cannot stall the sender, and a receiver counts the frames it drops when it falls behind, so a viewer then asks for the screen again.
- A frame is `postcard` of the sender's node id, a signature, a 24-byte random nonce and the ciphertext, and is at most 64 KiB. The signature is the sender's node key's ed25519 signature over `mahi-live-v2`, the thread ID, the topic ID, the sender's node id, the nonce and the ciphertext, so it cannot be mistaken for anything else the node key signs, such as TLS handshakes. A receiver checks the size, that the sender is a participant's node in its `meta`, then the signature, and only then opens the ciphertext: XChaCha20-Poly1305 under the sealing key, with the thread ID and the sender's node id as associated data. The plaintext is the sender's epoch (16 random bytes drawn when its mahi starts), a sequence number and a body.
- Per sender, a receiver keeps the current epoch and the highest sequence number accepted in it, and drops anything not above it. A newcomer asks for the screen with a random challenge, and accepts the epoch of the first part of a screen that echoes it; after that, a new epoch from the same sender is accepted only through a fresh screen request, since one challenge anchors a sender only once. A receiver also remembers the last 256 challenges it was asked, and drops a request that repeats one. Replayed frames, even whole old runs re-sent by a participant, are dropped. Screens and resizes of fewer than two rows or columns, or more than 1000 of either, are refused, so a viewer never allocates a huge screen, and `vt100` 0.16, which panics on a wide character wider than its screen or on a line that wraps on a screen one row high, can always draw them; for the same reason mahi reads a terminal one row high or one column wide as two, and every `vt100` screen mahi keeps, its own and a viewer's, is at least two rows and columns and starts blank when it gets narrower, as `AgentScreen`'s does. (The HKDF implementation does not wipe its internal state, which briefly holds a key derived from the thread key; the derived keys themselves are wiped.)
- Bodies: terminal output (the agent's output, in chunks) and resizes, heartbeats, a request for the screen (carrying its challenge), and the screen (the host's `vt100` virtual screen, as the escape sequences that redraw it, with its size, in chunks that each fit a frame). Output, resizes, heartbeats and screens name the agent slot they belong to, and are accepted only from the node of the participant who owns that slot: other participants cannot draw on a viewer's terminal. Even then the agent's output is untrusted, since the agent is sandboxed code: a viewer feeds it to its own `vt100` screen and redraws its terminal from that, so escape sequences such as clipboard writes (OSC 52), titles or hyperlinks never reach it. A host answers at most one screen request per second, and one per second per requester, coalescing the rest.
- A joiner receives `meta`, the current screen and the live stream from the host; history comes with fetch from the thread's remote. A viewer's terminal is read-only: its keys are never sent to the agent, and no one sends another's agent a prompt.

## Multi-engineer, multi-agent

Milestone 9 replaces several agents per person, remote prompts and handoff, and removes `mahi merge` (see One agent each, kept in sync).

- Every teammate runs their own agent, on their own machine, with their own worktree branch, sandbox and credentials.
- Agents never write into each other's worktrees. Work flows by merge ("merge Alice's agent's fix into my worktree"), and agents resolve conflicts. Forking = starting a new agent from another agent's snapshot.
- Permission requests always route to the host, whose agent asks them, never to a teammate.
- In-session UI. While an agent runs, it keeps the whole terminal: mahi passes its output and the user's keys through untouched and draws nothing of its own, since a status row cannot hold what several teammates do and compositing the agent's screen would cost fidelity. mahi speaks up in two ways only.
  - Notifications. When an agent in a workspace tab not shown asks the user something (see Workspace), mahi asks the terminal to raise a desktop notification (`OSC 9`, and `OSC 777;notify` and `OSC 99` for the terminals that use those; others ignore them) naming the tab and the agent, then rings the bell once. It picks the one sequence the terminal reads, from `TERM`, `TERM_PROGRAM`, `KITTY_WINDOW_ID` and `VTE_VERSION`, which tmux passes on (`OSC 99` for kitty, `OSC 777` for foot, rxvt and VTE terminals such as GNOME Terminal, the bell alone for macOS Terminal, `OSC 9` for the rest), wraps it for tmux when `TMUX` is set (tmux 3.3 and later forward it only with `allow-passthrough` on; otherwise the bell alone arrives), and leaves control and invisible characters out of the text and turns `;` into `,`, so nothing in it can end the sequence. Watching needs no notification: the invite was the permission.
  - The palette. `Ctrl-Space` (which no common agent binds; pressed twice, one goes to the agent) opens mahi's palette. Some setups take that key before the terminal sees it (macOS switching input sources when more than one is enabled, VS Code's terminal, a tmux prefix), so `palette-key` in `config.toml`, in mahi's configuration directory (`~/.config/mahi`, or `~/Library/Application Support/mahi` on macOS), changes it; that file is at most 64 KiB and an unknown setting in it is refused, so a typo is not silently ignored: `ctrl-space`, `ctrl-a` to `ctrl-z` (one the agent does not need; not `ctrl-g`, which ends terminals' answers to an agent's queries, nor `ctrl-h`, `ctrl-i`, `ctrl-j` or `ctrl-m`, which terminals also send for Backspace, Tab and Enter), `ctrl-]`, `ctrl-\`, `ctrl-^`, `ctrl-_`, or `f1` to `f12`. mahi recognises the key both as terminals send it by default (a control byte or an `F`-key sequence, including the Linux console's) and in the kitty keyboard protocol or xterm's `modifyOtherKeys` an agent may turn on (a release or repeat the kitty protocol reports goes nowhere), never inside a bracketed paste, even one whose start arrives split across two reads, and says which key it is when a run starts. The palette is a rounded box centred over the agent's screen, with a filter line on top. mahi draws it only between the agent's escape sequences, control strings and characters, and not while the agent keeps a saved cursor, since mahi saves its own in the terminal's one place while it draws; when the agent leaves one unfinished for 200 ms, mahi draws anyway. While it is open, the agent's output is held back, up to 1 MiB (past that the palette closes itself), and keys go to the palette; a resize clears the screen and redraws it. It lists the teammates' turns held for the user because they change agent settings (see Sync), each with its teammate and age, and below them the whole text of the selected one, which `Page Up` and `Page Down` scroll; a held turn can be taken only once its whole text was shown, so nothing hidden past the first screen reaches the agent (`Enter` takes it and closes the palette, `Ctrl-X` skips it and keeps the palette open for the next); with none, it says `No teammate's turn waits for you`, or, in a run that takes in no teammates' work (see Sync), `This run takes in no teammates' work`; a filter that hides every held turn says `No held turn matches the filter`. It also lists who is watching; later, actions such as inviting, pushing now or handing over. `Esc` or `Ctrl-C` closes it: mahi releases what it held back and makes the agent repaint by resizing its terminal one row smaller and, 100 ms later, back, since some agents wait for resizes to settle. The palette is on only when both the keys and the output are a terminal, so a run whose output goes to a file gets none of it.
- The viewer's palette. A teammate running `mahi join` opens a palette in the viewer, with the same key, that lists the followed participant's agents: `↑`, `↓` and Enter switch to one, `Esc` or `Ctrl-C` closes it, and `q` leaves only while it is closed. No one sends another's agent a prompt: each collaborator prompts their own agent, which takes the others' work between its turns (see One agent each, kept in sync).
- More agents: `mahi agent add <thread-id> [--from <participant>.<agent>] -- <agent> [args…]` starts another of the user's agents in a thread, in the terminal it runs in, next to the ones already running. Its slot is `<user>.<agent>`, named after the program as for `mahi run`, and one the user has already is refused (`mahi resume --agent` resumes it). Its worktree, `<thread-id>.<agent>`, starts at the thread's base, or with `--from` from that agent's latest snapshot, as a handoff does but without the briefing; its snapshots, turns and session are its own. Each agent has its own mahi process and terminal, so each keeps the whole screen. Teammates see all of the user's agents: the user's first mahi in the thread hosts the live layer, and each later one hands it its agent's output, resizes and claims over a Unix socket in mahi's runtime directory, readable by the user only; when the first one ends, the next one to notice takes over the hosting. The mahi that hosts holds `locks/<thread-id>@live` alone, beside the thread's other locks (an agent's name cannot hold `@`), and `mahi end` removes it with them. A later mahi finds that lock taken and connects to `mahi-<uid>/<thread-id>.sock` in the user's runtime directory (`XDG_RUNTIME_DIR`, or the temporary directory when it is not set, which keeps the path within the 103 bytes a socket path may have), a directory only the user can open and no sandbox sees; a path that is still too long is reported and the agent runs without the live layer; it sends its agent's slot and screen, then its output, resizes and its agent's claims, as length-prefixed messages of at most 4 MiB. The host serves only the user's own slots, each once, and broadcasts each agent's output, screens and heartbeats under its own slot, and sends each later mahi every claim it knows whenever they change. Every mahi keeps a copy of its agent's screen, so when the output it hands over falls behind it sends the whole screen instead of what it dropped, and it can take over: a mahi whose host goes away tries each second to take the lock and host, starting from that copy, or else reaches the mahi that did; a failure other than the lock being taken waits 30 s before the next try. The viewer's palette lists the agents it sees.
- Merging: sync (see One agent each, kept in sync) brings a teammate's work into the worktree of the user's agent, and `mahi land` brings each agent's work into the landing worktree. Each takes the source's snapshot, which must be signed by the key `meta` lists for its participant. The merge is three-way, with gix's tree merge, between the agent's current files (a snapshot taken first), that snapshot and their base: the source's snapshot this agent last merged, which the agent's snapshots record in a `Mahi-Merged: <participant>.<agent> <commit>` trailer, signed with them, so it is found on any machine; with none, a snapshot of another agent that the source's own trailers say it merged and that this agent holds, through its trailers or its own snapshots, as after a handoff, whose new agent's first snapshot records the snapshot it started from; with neither, the thread's base. Without that second step, work taken over by a handoff would conflict with the very lines it started from when merged back. A merge also records what its source had itself merged, and so do a handoff and `mahi agent add --from` for the agent they start from, so landing or merging in another order does not bring these conflicts back: each agent with snapshots in the thread whose snapshot there is the same as or newer than the one the target held, while the target's record holds fewer than 128 of its 256 sources, so a teammate's trailers can never fill it. Finding a shared snapshot walks the histories within one budget, passes over an agent whose snapshots cannot be read, and falls back to the thread's base when the budget runs out. A merge that leaves a path as it was (a name git refuses, too deep, too large, something in the way, unwritable) is not recorded, by sync or `mahi land`, and says so: the agent does not hold all of what it was given, so recording it would let a later merge of that agent elsewhere start from a base that treats the missing files as deleted; the next merge starts from the same base again. The trailers are trusted as git trusts a merge's parents: a participant whose signed snapshot claims another agent's snapshot without its changes makes a later merge of that agent report it already there, as an honest merge followed by a deletion would, and the claim stays in their signed history. It runs no program: merge drivers, filters and text conversions set in git's configuration or in `.gitattributes` are not used; text is merged by gix's built-in driver, and the lines both sides changed differently are left in the file between conflict markers; a binary file (or one over the snapshot size limit), a symbolic link or a path both sides changed in ways that cannot be combined (one changed it, the other deleted it) keeps the agent's side. Those paths are the merge's conflicts. Only renames that keep a file's content are followed, since finding similar files would diff every pair of a teammate's added and deleted files; a renamed and changed file is a deletion and an addition. Each side may change at most 65,536 paths from the base. The result is written into the worktree only where it differs from the agent's files, each file written under a temporary name and renamed into place in a directory opened without following symbolic links, so nothing outside the worktree is written even when something in the sandbox changes the tree meanwhile; a path git refuses to check out, nested deeper than snapshots go, or blocked by what the agent put there (a link or a file where a directory should be) is left as it is and listed, and so is a path the merge adds where the agent's last snapshot recorded nothing but a file is there (an ignored file, say), and everything past 4 GiB written in all. A path that cannot be read or whose object is not a file is listed too, and the others are still written. Files are replaced as the agent's last snapshot recorded them, without checking them again, which is why a running agent is merged into only while it is idle. A temporary file left by a merge that was killed is never recorded by snapshots. `HEAD` and the index stay at the base. A snapshot is taken at once, carrying the trailer unless the merge left a path as it was (see above).
- MCP tools: `mahi mcp` is a Model Context Protocol server (JSON-RPC 2.0, one message per line on standard input and output; protocol versions 2024-11-05 to 2025-11-25) that the agent's profile starts for it: for Claude Code, mahi writes `mcp.json` into the agent's state directory, naming the mahi binary, `mcp` and the tool socket, passes it with `--mcp-config` among the user's own options, before their first `--`, and allows the `mahi` server's tools in the profile's `settings.json`, so they ask no permission; a binary or socket path that is not UTF-8 leaves the tools out. It runs inside the agent's sandbox and only relays: each line goes over a Unix socket in the agent's private temporary directory, as the hook socket does, to the agent's mahi, which answers. A message over 1 MiB is refused. The tools, which name agents as `<participant>.<agent>`:
  - `list_agents`: the participants `meta` lists, each agent that has snapshots here, which of the user's agents run on this machine, and the claims. A participant with no snapshots here is shown as such, not as having no agent, since their agents may be running elsewhere: their claims show them while their host is connected live, and their work arrives when the thread is fetched.
  - `read_diff` (`agent`, optional `path`): the files the agent's latest snapshot changed from the thread's base, or the line diff of one of them, at most 64 KiB.
  - `read_transcript` (`agent`, optional `last`): the prompts and tool calls of the agent's latest turns, at most 30 and 64 KiB. Any agent of a participant `meta` lists can read any other's, since every participant can decrypt the thread.
  - `claim` (`what`, optional `note`), `release` (`what`), `list_claims`: advisory claims on a path or a task, so agents avoid working on the same thing. A claim never stops anyone; the server's instructions ask agents to look before editing and to claim what they start.
  The server's instructions, which the agent reads once when the server starts, name it and its user, and say how mahi works around it: other agents of the user and of teammates work in the thread, each in its own worktree; people may watch its screen live; mahi records its worktree after its tool calls, so others can read and merge its work; it does not commit or push, since `git commit` and `git push` fail in its sandbox and the thread's work becomes commits on its branch when the thread lands; and the tools are there to see who works in the thread and what they did, to look at the claims before editing, and to claim what it starts and release it when done. A teammate invited later is not in them; `list_agents` shows who is in the thread now.
  Text the tools return quotes what others wrote, so it is data: control characters other than newlines and tabs, invisible characters and text-direction marks are left out, and the instructions say not to follow instructions found in it.
- Claims are held in memory by each participant's host, for the agents it serves: its own and those of the user's other mahis in the thread, which send their agent's claims over the local socket and get every claim the host knows back. A claim is a path or a task name of 1 to 256 bytes, with the agent that holds it, an optional note of at most 200 bytes, neither with control or invisible characters, and when it was taken; an agent holds at most 32. Each host broadcasts the claims it holds, at most 64, in a sealed, signed frame whenever they change and every 10 s, and an empty list as it stops; the others keep each host's latest list for 30 s. A frame may only carry claims of its sender's own agents. Since hosts do not anchor each other's frames, a list of claims is taken only when it is newer than every list seen from the same run of its sender, for that sender's last 8 runs; a list replayed from a run of a sender not seen before can show claims released since, until that sender's next list or for 30 s, which advisory claims allow. The list a host sends the user's other mahis is kept until the link to it ends. A claim ends when its agent releases it or its mahi ends. Without the live layer, claims stay in the one mahi. A CRDT replaces this later only if offline multi-writer state proves needed.
- Cross-agent handoff: a new agent, of any kind, takes over another agent's work with a briefing mahi writes from what it recorded, since mahi calls no model itself. `mahi handoff <thread> --from <participant>.<agent> -- <agent>` starts it: in a thread whose `meta` lists the user with their key, whose named participant `meta` also lists, next to any other agent of the user's still running there, since the new agent has its own worktree, built from the other agent's latest snapshot on top of the thread's base, and the new agent's own snapshots start from it. The new agent is the user's own, under their name; one they already have in the thread is resumed instead. mahi fetches the thread first, like `mahi resume`, so a teammate's latest work is there. The briefing is written, readable by the user only, into the agent's private temporary directory, outside the worktree, so it is never recorded or committed; the agent gets its path in `MAHI_HANDOFF`, and an agent whose profile takes a first prompt, such as Claude Code, starts with one asking it to read the notes and continue, after `--` so that none of the user's own options takes it as its value. For any other agent, mahi prints that sentence for the user to give it. The previous agent's transcript is walked newest first through at most 10,000 turns; one that cannot be read back to its start, past that or past a commit that does not check out, gives what was read, and the briefing says its first prompt is only the earliest read. If the new agent cannot be started, its snapshots, state and worktree are removed again, so the handoff can be retried. The worktree holds a teammate's files, which may include settings their agent reads, such as `.claude/settings.json` or `.mcp.json`; the new agent runs in the same sandbox as any other, and its own trust prompts are left to it. The briefing is Markdown, at most 64 KiB, and quotes the thread's records, which other participants or agents may have written, as context, never in the voice of its own instructions: as block quotes, or code spans fenced longer than any backquotes they hold. It holds the thread's title and branch and which agent did the work; what the user asked, oldest first (the first prompt, which is the goal, and as many of the latest 30 as fit, each cut to 2000 characters and 60 lines), since the later prompts hold the user's corrections; the files the previous agent's latest snapshot changed from the base, as a list with `git status` and `git diff` named for the details, since the new agent works on those very files; its latest 20 tool calls; and, when its profile can read its session log and the recorded session is signed by the key `meta` lists for its participant, its latest 3 replies from the newest log (for Claude Code, the text parts of its own `assistant` entries in a log at the top of its project directory, not a subagent's, an API error's or one Claude Code made up; for Codex, the `output_text` parts of the assistant `message` response items in its dated `sessions/YYYY/MM/DD/rollout-*.jsonl` logs, a form older and newer Codex logs share, and not the `item_completed` events that repeat them; a log that cannot be read gives no replies rather than an older log's), so what it found or decided is not lost at no extra cost. The log is read line by line, leaving out lines over 4 MiB. Each section has its own share of the size, filled from the newest record back, and says what it left out. Control characters other than newlines and tabs, invisible characters and text-direction marks are left out. Listing the changed files reads at most 64 levels, 65,536 trees and 32 MiB of trees, since a snapshot may come from another participant.

## Landing

Milestone 9 replaces this section with the `land` tool (see One agent each, kept in sync); the trailers below stay.

- A thread results in **one branch**, `mahi/<thread-id>` unless `--branch` names another, built on top of the thread's landing branch and pushed to the remote as a fast-forward only; a rejected push means fetch, merge, retry.
- `mahi land <thread-id> [--from <participant>.<agent>]…` makes the landing worktree, `<thread-id>@land` beside the agents' worktrees, with `HEAD` on that branch, created at the landing branch's current tip. It merges into it, one after the other and as Merging describes (gix's three-way merge from the same base a merge would take, no program run, conflicts left between markers and listed), the latest signed snapshot of each agent named, or of every agent in the thread when none is; it fetches the thread first, like `mahi resume`. The worktree is not sandboxed: the integrator, the thread's owner by default, curates it into commits with plain git. The only agent mahi runs there is the one `--with` starts to rewrite the pull request draft, and that one only reads it (see below). Run again, `mahi land` merges only what each agent did since the snapshot it last took, which the landing worktree records in its own state as sync records in snapshots.
- `mahi land <thread-id> --push` adds trailers that link each commit made on the branch since the landing branch's tip back to the thread, rewriting those commits (they are not pushed yet), and pushes the branch to the thread's remote with mahi's own push, fast-forward only:

  ```
  Thread: 7f3a9c2e…
  Agent: alice.claude
  Agent: bob.codex
  ```

  A commit whose trailers already name this thread (`Thread:` with its ID, the key in any case) is left as it is, so an agent that wrote the trailers itself keeps them, and so is one a remote-tracking branch reaches, since it may be pushed already; a remote-tracking branch that cannot be read, or more than 65536 of them, stops the rewrite. The trailers join the commit's last paragraph when git would read it as a trailer block (every line a `Key: value` trailer, a folded continuation or a `(cherry picked from commit …)` line, or at least a quarter of them with one git wrote, `Signed-off-by` or cherry-picked), and start a paragraph of their own otherwise, with the message's own line endings; the rewritten commits keep their trees, authors, committers and dates, and the branch moves only if it still points where it did. Rewriting a commit drops its signature and mahi signs nothing for the integrator, so a signed commit, and every unpushed commit before it, which it names, is pushed as it is; those without the trailers are listed. At most 10 000 unpushed commits are rewritten. The `Agent:` lines name the agents the landing worktree merged. The branch goes to the remote chosen with `mahi remote`, whichever its visibility, since the branch is meant to be seen; without a chosen remote, or before `mahi land` made the landing worktree, `--push` is refused before anything is rewritten. Finding the landing branch's tip needs the thread key, so it asks for the passphrase. A remote branch that moved on is reported, with what was rewritten, and the command fails: fetch and merge it, then push again.
- mahi calls no model, so the pull request description starts as a draft written from the records: the thread's title, the first prompt of each agent (its goal), the agents and the people involved, the files changed from the landing branch's tip here (a forge may diff from the merge base instead), and the last reply of each agent whose profile can read it, signed by its participant. Once the branch is on the remote, `mahi land --push` writes it to `PR.md` in the landing worktree's state, outside the worktree, and prints it. The draft is meant for a forge, so the records in it are shown in code spans and fenced blocks, where the forge neither notifies the people they mention nor loads the images they link; control and invisible characters are left out, and each section has its share of at most 60 KiB, saying what it left out; `--push --with <agent>` then starts that agent, with the options and arguments a run takes, to rewrite it with the key decisions and why. It is sandboxed as any agent, but the landing worktree is bound read-only, so it changes no code after the push; the draft is copied into its private temporary directory (outside `.git`, where Claude Code would ask before each edit), and its notes say where, what to do, and give the record of each landed agent's work, quoted as the handoff briefing does, within 256 KiB. It records no snapshots or transcript and gets no tools; its hook events are taken and dropped, and its profile keeps its state in the landing worktree's state. When it exits with 0, the draft it left there, read through the directory mahi opened before it started (so a link it plants cannot point the read elsewhere), if it is a regular file of at most 256 KiB in UTF-8, replaces `PR.md` with control and invisible characters left out, and is printed; anything else it wrote goes with its temporary directory. An agent that exits otherwise leaves the earlier draft, and `mahi land` exits with 1. The agent's options are refused without `--with`. The pull request itself is opened in the forge, where its final look and approval happen.

## Compaction and cleanup

Thread histories are never rewritten. A fetch moves an agent's ref only forward and only over commits its participant signed, so a rewritten history would be refused by every teammate, and no one can re-sign another participant's commits. What a thread adds to the repository is bounded instead, and cleanup deletes whole refs.

Growth caps:

- Per item, fixed: a file in a snapshot is at most 256 MiB, a transcript turn at most 64 MiB sealed, an agent's session files at most 512 MiB (see above), and a snapshot adds at most 512 MiB of new content, counting, at its size once converted by `.gitattributes`, each file it reads whose content is neither its index entry's nor what the same path held in the run's previous snapshot; past that, a file is hashed without being written and left out, as files too large are, unless the repository already holds its content (a file left out is remembered while it is unchanged, and read again only when the budget has room for it), and the paths left out are counted when the run ends and refuse `mahi end` as other unrecordable files do. The first snapshot of a run reads every file, so content an earlier run stored counts again there.
- Per object: gix's allocation limit (`gitoxide.objects.allocLimit`) is set to 512 MiB for every repository mahi opens, so a small pack whose deltas or compressed objects claim a huge size cannot make mahi allocate it; an object of the user's own larger than that cannot be read by mahi either.
- Per transfer, configurable: `fetch-limit` and `push-limit` in `config.toml`, 1 GiB by default. A fetch over SSH or HTTPS counts every byte it reads from the remote (the ref listing, the pack, progress lines, keepalives and whatever follows the pack) and stops once it passes the limit, so no fetched ref moves (a pack read in full before that may stay, unreferenced, until git's garbage collection); the error names the setting to raise. Reads during a push are not counted against it: they are the remote's ref listing and report, each bounded in lines. A push, over one connection, sends its refs in the order `meta`, transcripts, sessions, snapshots, as long as their new objects fit within the limit together (each object counted at its full size plus a 1024th of it and 64 bytes, and 32 for the pack, more than zlib and the entry headers add even to data that does not compress). From the first ref that does not fit, the later ones wait too, so refs never reach the remote out of order, and mahi pushes again at once, so a push after a turn, and the last one of a run, send everything in as many packs as it takes. A ref whose new objects alone pass the limit is reported with the setting to raise and is not sent; it holds no other ref back. The landing-branch push is one ref under the same limit. History only grows, so a thread larger than the limits can be synced only once they are raised; that is the user's choice, not mahi's.

Cleanup is one command, `mahi purge <thread>`, never automatic:

- It needs no running agent and takes the thread's lock, as `mahi end` does, and asks before anything is deleted unless `--yes` is given. The owner's purge needs ssh-agent, since it signs the tombstone, and commits it here first, so a thread purged without a remote is ended here too. It deletes on the chosen remote first and only then here, so a purge that fails on the remote leaves the local copy; it fetches nothing for that, since the deletes take their old values from the push's own advertisement and the tombstone its generation from the local `meta`. With no remote chosen, or pushing turned off with `mahi remote --off`, it says so and asks before purging only the local copy; it never writes to `origin`.
- On the remote, the owner first fetches the thread, so the tombstone follows the newest `meta` there (a failed fetch stops the purge before anything changes, and a remote without the thread gets nothing), then pushes the tombstone (see The `meta` document) over `meta`; if another clone of the owner changed `meta` in between, the push is refused and the purge has to be run from that clone, since a clone that holds a tombstone never takes another `meta`. Once the tombstone is there, every clone that fetches treats the thread as ended, whatever happens next; then mahi's own push deletes every other ref under `refs/threads/<id>/`, each at the value the remote advertised (receive-pack checks it), so a ref someone moved since is reported and left, ignored by everyone, for the next purge. A participant who is not the owner deletes only their own agents' refs; the tombstone is the owner's.
- Here, it deletes the thread's refs and their reflogs, the fetched refs waiting for it, its worktrees, its agents' state and its lock files, and keeps the local thread branch, which is the user's git branch, naming it with the command that deletes it. The owner's tombstone `meta` stays; a participant purging a thread that is still live deletes their `meta` too. The pin stays in both cases, so an older `meta` pushed back later is refused as a rollback, and the thread cannot be restarted under the same ID.
- A clone that fetches the tombstone accepts it like any newer `meta`, so it accepts no agent ref of the thread any more (the tombstone lists no one), stops pushing it, and refuses `mahi resume`, `join`, `handoff`, `agent add`, `merge` and `land` for it; `mahi threads` and the home screen mark it as purged by its owner while this clone still holds any of it, and suggest purging the local copy; once only the tombstone is left (the owner's own purge leaves just that), the thread is no longer listed. Refs a clone pushes before it fetches are ignored by everyone, and the owner's next purge removes them.
- A purge deletes; it cannot make others forget. Forge caches and forks, other clones that do not purge, and anyone who kept an older `meta` and a participant's mahi key can still read what they hold, and snapshots on a private remote were never encrypted. Only the trailers on landed commits are meant to remain.

The thread branch (`mahi/<thread-id>`, or the name `--branch` gave) is what `mahi land --push` pushed; when a pull request is merged or closed, the forge usually deletes it. `mahi land --push` records, in the git directory (`mahi/branches/<thread>`), the remote and branch it pushed, its tip and the landing branch; after each fetch of that thread that got an answer from the same remote, mahi reads the remote's ref listing (as a push does, read to its end within its 65536-line limit, so it needs push access; without it nothing is noted) and notes whether the branch is still there. `mahi threads` then says the branch is gone, merged or closed, and suggests `mahi purge`. Since mahi asks no forge, and a squash merge leaves no ancestry, `mahi purge` says whether the thread branch's last pushed tip is in the landing branch here; when it is not, it warns that the thread may hold the only copy of the work and asks before deleting.

## Serverless caveats

- NAT traversal: hole punching works for most networks; symmetric NATs fall back to the relay (n0's public relays), which only forwards ciphertext.
- Discovery: invite tickets shared out of band, the addresses a clone remembers for a thread's host and participants, and relay-only pkarr records through n0's server (see Participants and the live layer); no DHT and no mDNS.
- Async work across time zones goes through the remote; realtime needs peers online together.
- The LLM itself is a hosted API unless a local model is used.

## Testing

- Unit and integration tests cover behaviour; property tests (`proptest`) cover invariants such as round trips and ordering, inside the unit tests.
- Fuzzing is used wherever it can be: every decoder and parser of input from a peer, a remote, an agent, a transcript or a file in a worktree has a fuzz target. The targets live in `fuzz/`, a crate outside the workspace built with `cargo-fuzz` (libFuzzer, on nightly, as `rustfmt` already is). It is a development tool only, never part of the mahi binary, so the pure-Rust rule for mahi's dependencies is unchanged. Each target checks that any input is accepted or refused without a panic, a hang or memory beyond the documented bounds, and, where there is an encoder, that decoding what was encoded gives it back.
- Targets, by crate: `mahi-core` (thread ref names, participant, agent and slot names); `mahi-crypto` (opening sealed content, unwrapping thread keys); `mahi-identity` (ssh-agent answers, identity and key files); `mahi-thread` (`meta` documents and their signatures, participant cards, transcript turns, session manifests and pieces, fetched-ref acceptance, handoff briefings); `mahi-store` (send-pack advertisements and reports, tree listings and changed paths, snapshot names); `mahi-ssh` (`known_hosts`, remote URLs, exec output); `mahi-live` (tickets, live frames, meta requests, pairing codes); `mahi-proxy` (`CONNECT` requests and host names); `mahi-tls` (records, QUIC packets, key exchange, signatures, certificates and their verification; rustls parses the handshake messages); `mahi-agent` (hook messages, the hook payloads mahi reads, Claude Code's session logs and session directories, user-written profiles and their templates); `mahi-term` (the user's keys, with and without the palette open, the agent's output as mahi follows it, and drawing the palette from any text).
- The fuzz crate reaches only the library crates' public items, so each library that decodes something behind a check the fuzzer cannot pass (a signature, a seal), or behind a socket or a transport, exposes that decoder to it in a `fuzzing` module, compiled only with `--cfg fuzzing`, which `cargo-fuzz` sets, or with the crate's `fuzzing` feature, which only `just clippy` turns on: `meta` bodies past their signature, transcript turns and session manifests past their seal, live frames past theirs. The first round covers `mahi-core`'s names, `mahi-crypto`'s opening and unwrapping (with a seal and open round trip), `mahi-thread`'s `meta`, cards, keys, turns and manifests (each with a round trip), session paths and briefings, `mahi-live`'s tickets (past their bech32m checksum, with a round trip) and frames, `mahi-ssh`'s `known_hosts` and URLs, `mahi-http`'s URLs and proxy settings, `mahi-proxy`'s host names and `CONNECT` requests, `mahi-agent`'s hook messages (with a round trip), Claude Code's session directories and log lines, Codex's session log names and log lines, and hook payloads (with their size bounds), `mahi-identity`'s ssh-agent answers to signing and listing, and `mahi-store`'s send-pack advertisements and reports. A live `meta` request is a fixed 16-byte thread id read to that bound, so it needs no target. Each input may run 10 s before it counts as a hang. `mahi-tls` is reached through rustls's own interfaces to its provider, so it needs no `fuzzing` module: one target opens any TLS 1.3 record with each suite and seals then opens one, removes QUIC header protection from and opens any packet, with a round trip for each, and finishes X25519 with any peer key; the other verifies any signature with any key under each algorithm, mutates the signed fixtures and the real relay chain from the crate's tests, which must still verify when left untouched, and verifies any certificate chain against the Web PKI roots through mahi's provider. `mahi-identity`'s key files are read from bytes as well as from disk: one target reads any bytes as the public identity, the signing key, the node key and a stored credential, each of which must read back the same once written again; the other opens any encrypted identity with a fixed passphrase, and mutates a real one encrypted with that passphrase at a low work factor, which must open when left untouched (the work factor cap still bounds scrypt). `mahi-store`'s name checks are fuzzed together: a name a snapshot records, a merge writes, a tree entry is given or a worktree is called must not be empty, `.`, `..`, `git~1` or `.git` in any case (also with the characters HFS+ ignores), nor hold `/` or a NUL byte, nor be `.gitmodules` as a symbolic link where the check knows the entry is one, and a branch name must stay the branch it names under `refs/heads/`. The fuzzer found that the snapshot and merge checks let a NUL byte through, which no directory entry or parsed tree entry can hold and gix refuses to write, and both now refuse it. `mahi-ssh`'s exec output reaches mahi through the connection target, and what a command writes to its error stream is shown through one more: control characters other than tab and newline, and every character `mahi-core` counts as invisible (zero-width, fillers, line separators, text direction, tags) are replaced, and every line after the first is marked `remote:`; the reasons a server gives when it disconnects and the comments ssh-agent gives its keys are cleaned with the same list. A teammate's tree is fuzzed whole: one target builds trees from any bytes, unsorted, with repeated names, any modes, gitlinks and links pointing out of the worktree (to a canary directory by absolute path and by enough `../` from any depth, and any other target, absolute ones placed deep inside the fuzz directory), keeps their objects in memory (gix's object overlay), and reads each every way mahi reads a teammate's work: the paths it changes from a base and the diff of each, one entry by name, a worktree restored from it (with a small checkout budget), and a merge of it applied to a worktree of a base whose own link points out. Each worktree is checked on its own, nested 17 directories deep so that a single link's target rarely leaves the fuzz directory: nothing else in that directory may change, modes included, and the worktree's registration must hold exactly what the store wrote. A write through links that lead out of the fuzz directory, such as a chain of them, would not be observed. Writing this target found that restoring a worktree had no bound. Reading a session piece parses nothing of its own: it opens sealed bytes, which the opening target covers, and compares their length and tag with the manifest's. A recorded session's file list is checked as a reader would accept it: any list it accepts holds only relative paths with no empty, `.` or `..` component, in strictly increasing order, none the same as another once ASCII case is folded nor a directory of another, within the file and byte limits. Fetched-ref acceptance is fuzzed against a model: a thread whose `meta` lists its owner and bob, agent histories for them and for eve, whom it does not list, local and fetched versions of each ref related in every way (the same, ahead, behind, apart, signed by anyone or no one), and a fetched `meta` that is the same, a newer one listing eve, one eve signed, or none; after accepting, no ref moved when it failed, the local participant's and unlisted participants' refs never moved, and a ref that moved went to the fetched commit, forward, through commits its participant signed. Besides `--cfg fuzzing`, each crate's `fuzzing` feature also builds its hooks, and `just clippy` lints with those features on, so the hooks are held to the same lints as everything else without a second build of the dependencies.
- The SSH client is tested in four ways, and a piece of it is not done until all four cover it. (1) Known-answer tests: RFC 7748's X25519 vectors, and vectors computed with another implementation (OpenSSL, through Python's `cryptography`) for OpenSSH's PROTOCOL.chacha20poly1305 construction and the GCM nonce counter of RFC 5647; the exchange hash and key derivation of RFC 4253 are checked against an independent implementation in Python, and end to end by the interoperability tests. (2) Property tests: sealing then opening a packet gives it back for every cipher, key, sequence number and length; any changed bit in the length, the payload or the tag, a packet cut short or a wrong sequence number is refused; encoding then decoding every message gives it back; negotiation always picks a name both sides list, in the client's order, and fails when there is none; and a model of the channel windows, driven by random sends, receives and adjustments, never lets mahi send beyond the server's window or accept beyond its own. (3) A scripted hostile server in the tests, built from the same codec, that breaks one rule at a time: a wrong or missing host-key signature, a host key of another type than negotiated, an X25519 key of the wrong length or an all-zero shared secret, a message out of order or an `IGNORE` during the first key exchange, no strict key exchange, a packet too long or not a whole number of blocks, too much before the identification line, data beyond the window, for an unknown channel or after `CLOSE`, a channel the server opens, and a stall at each step; each must end the connection with the right error and no panic. (4) Interoperability with the real OpenSSH `sshd` and `ssh-agent`, run unprivileged on a free port with their own configuration: every key exchange the installed OpenSSH offers (`mlkem768x25519-sha256` needs OpenSSH 9.9, which not every CI runner has yet; `curve25519-sha256` must be there), every host key type and cipher together, a rekey by the server and by mahi's own timer, a forced rekey in both directions (`RekeyLimit`), a transfer of more than the window in both directions, exit statuses, signals, the error stream, and `git-upload-pack` and `git-receive-pack` through the git tests. These tests need OpenSSH, so they run with `just test-git`, and fail when it is missing; `sshd` runs as the user, from a configuration of its own, with a forced command that records `GIT_PROTOCOL` and then runs the requested command. A command killed by a signal is not among them: `sshd` runs commands through the user's login shell, which may report the signal as an exit status, so the scripted server covers signals. The fuzz targets for `mahi-ssh` add the identification line, packet opening with fixed keys, every message decoder, and the whole client state machine after the key exchange fed any sequence of messages, with a round trip for each encoder. `cargo-mutants` is run on the protocol modules as each piece lands (`just mutants mahi-ssh`): a mutant that survives gets a test, or a line in the commit that says why it cannot be told apart.
- `just fuzz <target> [seconds]` runs one target. `just fuzz-all [seconds]` runs each in turn, and `just fuzz-shard <index> <count> [seconds]` runs one shard of them. CI splits the targets into 6 shards that run in parallel, a target's shard chosen by a hash of its name so that adding a target leaves the others' corpora where they are, and runs every target for 20 s on each push to `main` and for 5 minutes on a nightly schedule, with the corpora cached between runs and a crashing input kept as an artifact. A crash becomes a regression test, with its input, in the unit tests of the crate it was found in.

## Workspace (milestone 8)

The home screen grows into a workspace: one terminal that runs and shows every agent the user works with, theirs and their teammates', in every thread. Steps, at the end of this section, says which parts are built; what is still open is listed in Open questions. Runs outside the workspace keep the rules above unchanged, except for what milestone 9 adds to every run (sync, the note and the confirmations). Milestone 9 replaces the agents' list, the prompts typed to a teammate's agent and the actions it removes (see One agent each, kept in sync).

- **Tabs for threads.** The top row holds, after mahi's badge, a tab for the thread list (the home screen's list), one tab for each open thread, and `+` (new thread, join with a code). A thread's tab opens when the user starts, resumes or watches an agent in it, and closes once none of its agents runs or is watched, except a tab that only watches a thread the user joined, which stays until the palette's Leave this tab closes it, or until the thread ends or is purged. Such a tab learns of its owner's purge from the remote, not from the owner's mahi, which may not be online: when it opens, and then every 10 s while none of the teammates' agents is online, a thread of its own fetches the thread's `meta` alone from where the clone fetches threads (at most 4 MiB read), without writing a ref, and accepts that document as a fetched `meta` is accepted, leaving the fetched refs that wait for a command as they are. Once that `meta` is the tombstone, the tab closes and the thread list says the owner purged the thread. A check that fails says nothing, and the next one tries again. A new thread's tab is named `new` until its child reports the thread, then after the thread's first eight digits. A tab carries a marker while one of its agents asks the user something.
- **The agents of a thread, as a list.** A thread's tab shows one agent at full size, with the list of the thread's agents on its right, about 24 columns wide: the user's own first under `Yours`, then each teammate's under their name (`bob's`), a blank row between groups. Each row starts with its state's mark, then the agent's name, the shown one highlighted across the row, its mark white like its name so it reads on the highlight. The states are: working (a turn is open), done (its turn ended, ready for the next prompt, drawn in a calm colour), asks you (the agent waits on a question of its own, for a profile whose hooks report one: Claude Code's `Notification` hook for a permission request or a question, not for its reminder that it waits for input; Codex reports none, so its agents show only working and done), live (a teammate's agent whose host is connected: its frames carry its terminal but not its turns, so working and done are the user's own agents' states only), or offline (a teammate's agent whose host is not connected; selecting it shows its last turns and the files it changed, as `read_transcript` and `read_diff` read them, which needs the thread key). An agent starts as done, ready for its first prompt, and the list shows a failed command as failed. The user's own agent takes their keys; a teammate's is read-only, and no key reaches it: the workspace draws it from the live layer. Hiding or showing the list resizes the agent's terminal once; on a terminal narrower than 100 columns the list starts hidden, and shows over the pane instead of beside it, so the agent is not resized.
- **Keys.** The workspace takes for itself only the palette key, and the keys typed while a teammate's agent is shown, which reach no one; the palette key opens the workspace's palette over what is shown, as the home screen's thread menu is drawn: a menu, titled with the shown tab's thread or `threads`, of the thread list (`0`) and each tab (`1` to `9`), the shown one marked, the shown tab's other agents with their state, the next agent, in any tab, that asks the user, is done or failed (`Space`), hiding or showing the list (`b`), while the user's own agent runs and is shown, its own palette, of the turns held for it (`p`), and sending the palette key to it (the palette key itself), and quitting (`q`). `↑` and `↓` move in it, Enter runs the selected entry and Escape closes it; an entry's key, and `←` or `→` for the previous or next tab, acts at once and closes it. The palette key pressed twice sends one to the selected agent. A child the workspace started opens its own palette only when the workspace asks, so the key reaches its agent as it is, and closes that palette first when it is open; `p` asks the child, on a pipe of its own (see Reports), to open it. The line below a tab says only which key opens the palette, such as `Ctrl-Space palette`. Once the tab knows its thread, the palette also lists the actions on it, as Actions in the palette says. `palette-key` in `config.toml` changes the key, as it does today. The user's own prompts are typed into their agent directly, which queues what it is sent while it works.
- **Mouse.** The workspace turns on the terminal's mouse reporting (button events, mode 1002, in the SGR encoding, mode 1006), which takes the terminal's own selection and wheel scrolling away while it runs; most terminals keep selection with Shift held. A click on a tab or in the list is the workspace's. Any other mouse event goes to the selected agent only when it is the user's own agent and it turned mouse reporting on itself, moved into its pane's coordinates, clamped to the pane, sent only for the events the agent's mode asks for and in the encoding it chose; otherwise it is dropped, which replaces, inside the workspace, the rule that mouse reporting is not passed on. What the terminal reports is untrusted input: its parser gets a fuzz target, as the key parser has.
- **A multiplexer.** Each of the user's own agents in a tab runs as a child mahi process on a pseudo-terminal the workspace owns, as `mahi resume` or `mahi agent add` runs it, and the workspace keeps a `vt100` screen for each and draws the selected one in a pane of its own screen. Each such agent keeps its own sandbox, recording and palette, and a crash ends one agent, not the workspace. The workspace runs at most 16 children. The workspace gives each child it starts the mahi key it keeps unlocked, if it keeps one, on a pipe only that child inherits, whose number `MAHI_KEY_FD` names, never through the disk, an argument or the environment: the child takes it before it opens anything, checks that it is a pipe, closes it, and keeps the key for its whole run, with its core file size limit at 0, as the home screen keeps one, but without the 15 minutes; so the passphrase is asked once, by the workspace, and a key the child cannot read only makes it ask as it would anyway. A program that runs in a sandbox is never given a descriptor. What a child's pseudo-terminal carries is the agent's output, untrusted, passed to the outer terminal under the rules for an agent's control strings (title, clipboard, notifications), only while that agent is shown. A child tells the workspace its thread and its agent's state through a pipe of its own, never in the pseudo-terminal, where the agent could forge them (see Reports). When an agent in a tab not shown asks the user something, the workspace rings the terminal's bell and raises a notification.
- **Reports.** Each child reports on a pipe of its own, which `MAHI_REPORT_FD` names, passed as the key's is, and which the agent cannot write, unlike its terminal. It sends its thread once it knows it, which names a new thread's tab; its agent's state, each time it changes, from the agent's hooks: `working` when a prompt opens a turn, or when a tool runs or the user answers (text or `Enter`) after a question, `done` when the turn ends or the user interrupts it with `Ctrl-C` or `Escape`, and `asks` when the agent waits on a question of its own, which marks its tab, and during which mahi never runs a merge, however long the turn stays quiet, since `Enter` would answer the question. The child writes its reports without waiting and drops one the pipe has no room for, so reporting never holds a run up. The other way, the workspace asks a child to open its palette on a pipe of its own, which `MAHI_COMMAND_FD` names, passed as the reports' is: one byte, `p`, which the child reads on a thread of its own, ignoring any other; the workspace writes it without waiting and drops it when the pipe is full. A child given that pipe opens no palette on the key from its terminal, and drops the requests that came before its run could open one. A report is one line of at most 512 bytes with its newline, which a pipe writes whole on every system; the workspace ignores any other line.
- **One endpoint, held by the workspace.** The relay reaches only the latest connection made with a node id, so the workspace binds only one endpoint for all its tabs, when it first hosts a thread, and hosts the live layer of every thread it has a tab for, with no agent of its own: once a tab's child reports its thread, the workspace takes `locks/<thread-id>@live`, opens the thread key with the mahi key it keeps, and serves the thread's local socket; it stops hosting when the thread's last tab closes, and when it quits, after its children have stopped. A child the workspace started never hosts: it only hands its agent over the local socket, as a later mahi in the thread does (see More agents), trying again every second until a host answers, so the user's node key is bound by the workspace alone. So that the workspace can open every thread's key, it unlocks the mahi key before it starts any agent, a new thread's included, and before a join with a code, unless `MAHI_LIVE` is `off`. If another of the user's mahi processes already hosts the thread, the workspace leaves it to that process, whose socket its children reach instead (see the known limit in Open questions). Every 2 s it tries again to host each open thread it does not host, so it takes a thread over when that process ends, and retries one whose hosting failed, which the status line tells once; mahi's keys are read then, so a setup the workspace's first agent makes is used. Quitting stops the threads' hosts together, after the children.
- **Watching teammates' agents.** A teammate's agent is read-only: what is typed while it is shown reaches no one. The workspace watches a teammate's agent itself, from the thread's gossip topic, which it joins once for each tab with the endpoint it holds: it keeps a `vt100` screen for each slot whose frames it accepts, under the rules for a viewer (only from the node of the participant who owns the slot, through the viewer's own screen, never the agent's input modes), asks for a slot's screen when it starts watching it and whenever frames were dropped, and lists the slots that `meta` and the topic name. Until it hears of any agent, it also asks for the screens every 3 s for its first 30 s, so a slow answer still meets the challenge it echoes. Every host answers with the screens of all its agents, so a teammate who just joined sees the owner's agents without waiting for their next heartbeat. It reaches the thread's participants as Finding a participant's machine says. A teammate's agent whose host is not reached is listed as offline. Watching needs no command and no child process, so `mahi join` stays the way to watch from a ticket or a code outside the workspace, while a code typed on the home screen opens the joined thread in a tab that watches it.
- **Quitting.** `q` in the thread list, or after the palette key, quits; while agents run it first asks whether to stop them (`3 agents are running: stop them and quit?`), and stops each as a stop signal stops a run today (see Session lifecycle). There is no background server: no agent outlives the workspace.
- **Actions in the palette.** The palette lists the actions for what is shown: on the user's own agent, hand off, add an agent and end; on the thread, invite, land and push. Each runs as its command does, its questions asked in dialogs, landing and ending confirmed first as in the thread's menu; an action that starts no agent then shows the thread list, which tells its outcome and the activity, and so does an agent that cannot start, with the reason. An invite that succeeds instead shows the thread's tab when one is open, as the invited teammate's join does, and the tab's last line says for a few seconds that the invite is done. Declining one of a new agent's questions keeps the tab. The actions that belong to no thread (new thread, join with a code, remote, credentials, the user's card, help) stay in the thread list's tab, and the home screen's menu panel is removed.
- **No permission prompts inside the sandbox.** mahi starts an agent in its own no-approval mode by default: Claude Code with `--permission-mode bypassPermissions`, its one-time acceptance recorded in the thread's own Claude Code state as the folder's trust is, and Codex with `approval_policy = "never"` among the `-c` options mahi gives it, so the user's own options win. `agent-approvals = "ask"` in `config.toml` (`"never"`, the default, keeps mahi's choice), or a permission option of the user's own after `--` (Claude Code's `--permission-mode` or `--dangerously-skip-permissions`; Codex's `--ask-for-approval`, `--approve-for-me`, `--dangerously-bypass-approvals-and-sandbox` or `-c approval_policy`), keeps the agent's own choice, and so does a managed setting that forbids the mode. The sandbox, not the agent's question, is then the boundary, and what it holds must be said plainly: the agent writes only its worktree and its state, reads the repository's objects and refs read-only (every thread's snapshots and every branch, but not its configuration or the other worktrees; see Session lifecycle), the directories on `PATH` and the system's, holds no ssh-agent, and reaches only the hosts allowed, through which it can still send what it reads to a third party (with an attacker's key at its model's API, or a host the user allowed that stores what it is sent). An agent driven by text it reads acts within those bounds without asking: a web page, or a file in the worktree, including what a merge brought from a teammate (`CLAUDE.md`, `.claude/settings.json`, `.mcp.json`, `.codex/`). Snapshots follow tool calls at most one a second, only when the tree changed, and leave ignored files out; no command yet brings back a chosen earlier snapshot. The files in its state directory that hold mahi's hooks (Claude Code's `settings.json`, Codex's `hooks.json`) are bound read-only, so the agent cannot edit them during the run; it can still turn hooks off through settings it may write, such as its worktree's `.claude/settings.local.json` or Codex's `config.toml`. Claude Code refuses its no-approval mode as root unless it is told it runs in a sandbox, so its profile sets `IS_SANDBOX=1`, which is true under mahi.
- **Steps.** Each its own commit. Built: the tabs, the agents' list, the workspace's palette with its keys (tabs, agents, the list, `Space`, the palette key, quitting), the mouse, quitting from the thread list, the key passed to children, the children's reports (thread, working, done, asks), the one endpoint held by the workspace, relay-only pkarr records, remembered addresses for every participant, and watching teammates' agents in the threads the workspace hosts, listed live or offline, including the agents the thread's refs name whose hosts were not heard from, and the last turns and changed files shown for an offline agent, and the shown thread's actions in the palette (add an agent, hand off, land, push, end, invite), with the labels its menu uses; the bell and a notification, titled with the tab and saying which agent asks you, when an agent in a tab not shown starts to ask, at most once every 30 s for each agent, since its own hooks report that it asks; the list hidden when the first tab opens on a terminal narrower than 100 columns; the limit of 16 children, checked before a new agent's questions are asked; `p` in the workspace's palette. Built too: the no-approval mode. Milestone 9 replaces the other steps planned here (the merge actions in the palette and the trust kept across runs).

## One agent each, kept in sync (milestone 9)

Milestone 9 makes a thread simple to work in: each person has one agent, prompts it as usual, and sees only that agent. mahi keeps every agent's worktree in step with the teammates' work, and the owner's agent lands the thread. Parallel work inside one person's agent is the agent's job, through its own subagents, which run in the same process, sandbox and worktree.

- **What it replaces.** Everywhere in this document, these belong to milestones 1 to 8 and go, each with its design text, in the step that removes its code: several agents per person (`mahi agent add`, the palette's Add an agent), `mahi handoff` and its briefing, forking, remote prompts (the viewer's composer, the host's queue and its palette, `Tab`, the `Prompt for <agent>` dialog, the `[from <name>]` tag, the prompt notifications, the teammates' prompts in the list and the reports), the `mahi merge` command and the palette's merge actions, the agents' list in a thread's tab, `mahi land` with its landing worktree, its pull request draft and `--with`, and the palette's Land and Push. What stays: the merge itself, as Merging describes it (gix's three-way merge, the `Mahi-Merged` trailers, the paths left as they were), now run by sync; the local socket through which a later mahi, such as a workspace's child, hands its agent to the thread's host; the trailers Landing describes; and the rest of the live layer, threads, encryption, claims, snapshots, transcripts, fetching, pushing, ending and purging.
- **Threads made before it.** Roles change `meta`'s format, so its version is 4 (3 is the tombstone's). mahi refuses a thread whose `meta` has an older version, as it refuses any version it does not read (`meta document version 2 is not supported`), and `mahi purge` still removes such a thread here, since it finds the thread by its `meta` ref without reading the document; with no document it can read, it signs no tombstone, so on the remote it removes only the user's own agents' refs, as for a teammate's purge, and the thread's `meta` and the others' refs stay there. No migration is kept.
- **Roles.** The owner invites a teammate as a collaborator or a watcher. The role is a field of the participant's entry in `meta`, in a new body version, so the owner signs it and every participant's mahi reads the same one; the owner is a collaborator. A joiner reads its role from the `meta` it verified, never from the ticket, and the pairing confirmation shows it on both sides. On the home screen the invite asks which, in a dialog after the remote one (`✎ Collaborator: they run their own agent, kept in sync with yours`, then `🔒 Watcher: they watch your agents`); `mahi invite <thread> [card]` takes `--collaborator` or `--watcher`, one of them required; inviting someone already listed with another role gives them that role, in a new generation, and with the same role gives their ticket again. The owner's own card cannot make them a watcher, which is refused before the passphrase is asked. Inviting a collaborator is the owner's choice for the whole thread: the other collaborators' worktrees take that teammate's work from then on, without being asked.
  - A collaborator runs one agent in the thread. A watcher runs none: every participant refuses a watcher's agent frames, turn-end announcements and snapshots, on the live layer and in a fetched ref, and serves no snapshot to a watcher.
  - Changing a role is a new `meta` generation. The owner's host names its current generation in each claims frame, and a participant behind it fetches `meta` from the host, as a join does. A collaborator made a watcher stops their agent, and each other collaborator merges none of its snapshots that reach it after it accepted that generation. A watcher made a collaborator chooses an agent and starts it as a collaborator's join does. A role changed while the owner's host is offline reaches the others when it is back.
- **One agent per person.** A collaborator has one agent in a thread, in the slot `<participant>.<agent>`, with its own worktree, sandbox, credentials and recording, as `mahi run` gives it today. Sync needs to know when an agent's turns end, so in a thread with more than one collaborator, each collaborator's agent runs with a built-in profile whose hooks report its turn ends, Claude Code's or Codex's: inviting a collaborator is refused while the owner's agent runs without one, and a joining collaborator chooses among them. A thread its owner works in alone still takes any agent, with or without a profile.
- **Joining.** A collaborator who joins with a code chooses their agent in a dialog, `Join a thread` asking `Which agent should work in this thread?`, from those built-in profiles on `PATH` (none asked when there is one), the one chosen last selected first, and is asked for its credential as a run asks on first use. Their mahi then asks the host for the other collaborators' latest turn-end snapshots (see Sync), retrying for about 30 s as a join retries for `meta`, merges them into a worktree at the thread's base, except one that changes agent settings, which waits for the keypress as Agent settings says, and starts the agent there. When no host answers, the agent starts from the base, and the merges come once a host is reached. A watcher's join opens the tab that watches, as a code's join does today. On the command line, `mahi join <ticket> -- <agent>` joins a collaborator, and `mahi join <ticket>` alone joins a watcher; each is refused for the other role.
- **One view.** In the workspace, a thread's tab shows the user's own agent at full size, without the agents' list. Under the pane, a status line names each other collaborator's agent with its state and, after a merge, the files that merge brought, such as `bob.claude working · src/client.rs`; a turn waiting for the user's keypress (see Sync) and unresolved conflicts are shown there too. Each host sends its agent's state (working, done or asks) in a frame when it changes and in each claims frame, under the rules for a heartbeat. A watcher's tab shows the owner's agent, read-only, and the palette moves it to another collaborator's agent. A run outside the workspace still draws nothing over its agent but its palette: sync and the note work there too. The keypress that takes a held turn and the landing confirmation are the run's own palette, which opens on its own for them, in the workspace's child too, whose pane the workspace shows; so the run that holds the worktree and the `land` call also takes the answer. Every collaborator's mahi, in the workspace or not, anchors each teammate's run through a screen request, as a viewer does, before it takes that run's announcements and states; it keeps the screen it gets only to draw it, which only a watcher's tab does.
- **Sync.** Every collaborator's agent takes the other collaborators' work automatically, between its turns.
  - **Turn ends.** When an agent's turn ends, as its profile's turn-end hook reports it (an interrupt with `Esc` or `Ctrl-C` is not a turn end), its mahi takes a snapshot even when the tree did not change, with the signed trailer `Mahi-Turn-End: <participant>.<agent>`, naming the agent's slot. The snapshot is taken at once, without waiting for the snapshot interval (at most once per interval, so hooks cannot flood the history), and before any merge that waits, so it holds the agent's own work. A turn end adds no snapshot when the last one already ends a turn with the same tree. A turn end whose snapshot fails is dropped, after three attempts when files change while they are read, and the next turn end takes the next one. Only such a snapshot is announced and merged: snapshots taken after a tool call, on the timer or at exit travel with it as its history but are never merged, so half-done work stays where it is.
  - **Announcing.** The host names the agent's latest turn-end snapshot in a frame when the turn ends, and again in each claims frame, every 10 s, so a teammate who comes back learns of it. The host finds it in the agent's snapshots ref, which a workspace's child shares with the workspace's host through the repository: at most every 200 ms it reads the ref of each agent it serves and, when the ref moved, walks back at most 4,096 snapshots to the newest one whose `Mahi-Turn-End` trailer names that agent's slot, so a trailer naming another slot never counts. When the ref no longer descends from the snapshot the host saw last, as after it was moved back, the host takes the latest turn end of the new history without a turn-end frame, naming it only in claims frames, where the receiver's descent check sets it aside, and announces the turn ends after it; an agent whose ref is gone is no longer named. A claims frame names at most 64 turn ends, one per agent; claims frames are ordered within each run of their sender but not anchored, so the receiver's check that a commit descends from the last one it merged is what guards that copy. A receiver takes the frame only from the node of the participant who owns the slot, and only for a commit that descends from the last turn-end snapshot it merged from that slot, so a replayed or reordered frame cannot take a teammate's work back.
  - **Fetching.** A collaborator's mahi that lacks the named commit asks the host for it over a direct connection (ALPN `mahi/snapshots/1`), naming the slot and the last commit of that slot it holds. The host answers only a collaborator its current `meta` lists, and only for the slots it serves, with the commits from that one to the latest turn-end snapshot and the objects of their trees the asker lacks, at most 4,096 commits and `fetch-limit` bytes in all, and within 60 s, or else nothing, so the asker catches up at its next fetch; it serves one request at a time for each peer and at most one every 5 s for each slot. The asker checks every commit as a fetched agent ref is checked (signed by the key `meta` lists for the slot's participant, forward only), then moves its copy of that slot's ref. Its request and the host's answer are untrusted input, each with a fuzz target. In the workspace, the workspace's host does the fetching and the serving, and its child asks it over the local socket. A teammate whose host is not reached is caught up when it is reached again, or at the user's next join or resume, which fetch the thread; on a public remote, where snapshots are never pushed, only the live layer brings them.
  - **Merging.** Once the user's agent's turn has ended, through its turn-end hook only, or before its first turn, and 2 s passed without output or keys, with the user's line empty, its mahi merges into its worktree each teammate's latest turn-end snapshot it has not merged yet, one after the other, as Merging describes, a snapshot taken at once with the trailer. The quiet fallback that makes a hookless agent idle never starts a merge. A merge that is under way when the user types holds their keys until it ends.
  - **Agent settings.** A turn-end snapshot that changes a path an agent reads as its settings or instructions (`CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `AGENTS.override.md` at any depth, `.claude/`, `.mcp.json`, `.codex/`) waits, whole, for the user's keypress, with that teammate's later turns behind it: the status line says so, and the palette lists it with the paths it changes, to take or to skip. Skipping it merges the teammate's next turns with the skipped snapshot as their base, so the skipped change stays out. So text that takes over one agent cannot reach the next person's agent through its settings without that person.
  - **Conflicts.** The lines both sides changed differently are left between conflict markers whose labels name the merge (`mahi bob.claude`). mahi keeps the conflicting paths in the agent's state, so they survive a restart, and a path counts as resolved once it holds no line those labels begin, or is gone. Until every path is resolved, the agent's turn-end snapshots are not announced or pushed, so a conflict never spreads to a teammate, and no other merge starts, so markers never nest. A conflict without markers (a binary file, a symbolic link, or a path one side changed and the other deleted) keeps the agent's side, as Merging says; the note lists it, so the agent can read the teammate's side with `read_diff` and decide.
  - **The note.** The user's next prompt to their agent carries a note of what came in: the conflicts first, with the agent asked to resolve them before anything else, then the files each merge brought, such as `merged bob.claude: src/client.rs, src/lib.rs`. The note quotes a teammate's paths, so it is data: each path is in a code span fenced with more backquotes than it holds, as the handoff briefing quotes, cut to 200 bytes, without control or invisible characters, at most 20 of each kind. mahi keeps the note in the agent's state until an agent takes it. For Claude Code, the `UserPromptSubmit` hook asks mahi for it over the hook socket, waiting at most 1 s, and adds it as context; on a timeout it adds nothing, and the note waits for the next prompt. For an agent whose hooks cannot add context, the server's instructions ask it to call `list_agents` at the start of each turn, which returns the note and marks it taken. While conflicts stay unresolved, the status line says so, since an agent that is never prompted again never resolves them.
- **Tools.** The MCP tools keep `list_agents`, `read_diff`, `read_transcript` and the claims, and add `land`. The server's instructions say that the agent's worktree takes the other collaborators' work between its turns, that the note lists what came in and what conflicts, that conflicts are resolved first, and that it does not commit or push, as today.
- **Landing.** The owner lands the thread by asking their own agent, which calls the `land` tool. Only the owner's agent may call it; a collaborator's agent gets an answer that only the owner lands, naming them.
  - **What it lands.** The changed paths are those whose files in the owner's worktree, read as a snapshot reads them (ignored files left out, under the snapshot size limits, names git refuses left out), differ from the last landed tree, or from the thread's base before the first landing: added, changed, deleted, or with a new mode, as snapshots record them.
  - **The call.** `land` takes a list of commits, each a message and the paths it holds, and the pull request's title and description. Each changed path goes in exactly one commit. A call that leaves a changed path out, names one twice or names one that did not change is refused, with the paths listed, so the agent can call again.
  - **Before it asks.** mahi refuses while a merge's conflicts are unresolved. It builds the commits at once, from the worktree as it is: each commit's tree is the one before it with that commit's paths as the worktree has them, the first one starting from the last landed commit, or from the thread's base before the first landing. Each carries the trailers Landing describes, naming every collaborator's agent, and is signed with the owner's SSH key, as snapshots are. What is pushed is exactly what is built, whatever changes in the worktree meanwhile.
  - **The confirmation.** The run's palette shows it over the agent's screen: each commit's first line and its paths, the pull request's title, and each collaborator whose latest turn-end snapshot is not merged yet, with when it ended, so the owner can land without them and land their work next time. Enter pushes, and Escape cancels. The keys typed before it showed are dropped, and it takes none for its first 500 ms, so an Enter meant for the agent does not push. The keypress is the safeguard: text that drives the agent cannot publish anything without the owner. Its wording is to be decided (see Open questions). The tool answers at once that it waits for the owner, and the outcome, pushed or cancelled, comes in the agent's next note, so no tool call waits on a person.
  - **The branch.** The commits go on the branch `mahi/<thread-id>`, pushed to the remote chosen with `mahi remote`, with mahi's own push, fast-forward only, and `mahi/branches/<thread-id>` records it, as Compaction and cleanup needs. They never go on the landing branch: the pull request brings them there, in the forge. A later landing puts its commits on top of the branch. When the forge deleted the branch after merging it, the next landing starts a new one from the landing branch's tip on the remote instead of the last landed commit: each commit's paths are merged into it three way, with the last landed tree as the base, so what changed upstream since stays, and a path that conflicts refuses the landing, listed.
  - **The pull request.** mahi does not call a forge's API. After the push, the confirmation shows the link the forge sent back for a new pull request, when it sent one: as plain text, cleaned as the remote's messages are, cut to 200 bytes, never opened by mahi. mahi writes the description to `PR.md` in the thread's state and, when it holds at most 64 KiB, copies it to the clipboard with `OSC 52`, for a terminal that takes it, without control characters other than newlines and tabs, or invisible characters.
  - **When the agent cannot run.** The owner's worktree holds the merged work as plain files. Outside the sandbox, the owner can commit and push it with plain git, as from any checkout.

## Milestones

1. `mahi run -- <agent>`: sandbox, snapshots, encrypted transcript refs, local `mahi resume`, local `mahi end`.
2. P2P live layer: iroh gossip, invite tickets, live terminal view for teammates; resuming your own agent in a thread someone else owns, trusting the owner's key from the invite ticket.
3. Remote backing store: push/fetch thread refs, cross-machine resume, handoff bundles; rebuilding a missing worktree from the agent's latest snapshot (useful locally too, after a worktree was deleted); binding a participant's agents to the signed `meta`, since once peers push refs, the names under `refs/threads/<id>/agents/` are theirs to choose.
4. Multi-agent threads: the in-session palette and notifications, remote prompts and their queue, `mahi agent add` (one worktree per agent, each in its own terminal, all hosted by the user's first mahi in the thread), `mahi merge` (gix's three-way merge of another agent's latest snapshot into the user's worktree), MCP coordination tools (`mahi mcp`), claims held by the thread's host (a CRDT later, if offline multi-writer state proves needed).
5. Landing: integration, curated commits with trailers, PR description generation.
6. Growth caps (per item, per object, and configurable per transfer); `mahi purge`, here and on the remote, with a tombstone `meta` the owner signs; noticing a thread branch that is gone. Thread histories are never rewritten.
7. Getting started: first-run setup, credentials on first use, the remote offered once, the home screen, pairing codes (see Getting started).
8. The workspace: tabs for threads, the agents of a thread in a list, a multiplexer of child mahi processes, one endpoint held by the workspace, finding participants' machines, watching teammates' agents, actions in the palette, no permission prompts inside the sandbox (see Workspace).
9. One agent each, kept in sync: roles in `meta`, an agent started on a collaborator's join, one view, automatic merges of turn-end snapshots with a note to the agent, the `land` tool (see One agent each, kept in sync).

Fuzzing (see Testing) comes as its own step after milestone 3, covering every parser written so far, and then grows with each new one.

## Open questions

- Name: mahi, at mahi.social, a domain the project owns, used wherever mahi needs a domain or a URL of its own. The `mahi` crate is reserved on crates.io with a 0.0.0 placeholder (Oct 2026), since mahi ships as a binary from GitHub releases; confirm other registries. Be thoughtful about using a te reo Māori word if this becomes commercial.
- To be decided: Nerd Font icons. The list's state marks (`✓ ● ! ◉ ○ ✗`) are plain Unicode, which every terminal font draws. A setting in `config.toml`, off by default as lazygit's `nerdFontsVersion` is, could draw Nerd Font glyphs instead, one column wide as the marks are. mahi cannot ask the terminal which font it uses, so the user turns it on. The setting's name and the glyphs are to be chosen.
- To be decided: cache what is derived from commits. A commit never changes, so what mahi reads from one (a thread's row in `mahi threads` and the home screen, which the home screen reads again every 2 s; the turns `walk_turns` finds by walking a transcript's commits) could be kept under the commit's id and never invalidated, each value computed from its parents' as Scion's derived data is (anthropic.com/engineering/redesigning-source-control). Only with a measurement that shows the reads are slow, and with what is kept from encrypted content under the same rules as that content.
- Known limit: two of the user's processes with a live layer at once outside the workspace, such as runs of two threads in two terminals, or a run and `mahi join`, each bind the user's node key, so the relay reaches only the one started last and the others keep only direct paths. The workspace avoids it by holding the one endpoint; a run outside it could hand its hosting to a running workspace, as a later mahi in a thread does, which is to be decided.
- To be decided, milestone 9: a snapshot names its slot but not its thread, so a host could answer with a participant's genuine snapshots from another thread they work in under the same key; the asker takes answers only from the slot owner's node, and whether snapshots should carry a signed thread trailer is open.
- To be decided, milestone 9: the wording of the role on the joiner's side of the pairing, the status line's wording when several teammates do not fit on one line, and the landing confirmation's wording.
- To be decided, milestone 9, once the settings keypress is built: one state per teammate for sync. What sync holds for a teammate's snapshots is spread over the run's set of snapshots tried, the `held` and `skipped` records, the `conflicts` record and the agent's turn flags, so nothing stops a teammate being both held and skipped. One enum per teammate, kept in one record, would make such states impossible to write.
- To be decided, milestone 9: whether Codex's hooks can add the merge note as context, so it does not depend on the agent calling `list_agents`.
- To be decided: an agent reading other threads' snapshots. All threads of a clone share one object store, which the agent reads, so an agent in one thread can read the snapshots of every other thread, which are not encrypted. A teammate who can reach a private remote reads them anyway; the agent sees more only for snapshots that never left this clone (no remote, or a public one) of a thread whose participants differ from its own, so a teammate who drives the agent with a prompt or a merged file could reach work they were never given. A warning when an agent starts while such snapshots exist could come first; giving each agent only its own thread's objects would cost the sharing between threads and time at every start.
